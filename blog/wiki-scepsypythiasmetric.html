서빙의 기본 단위는 토큰인가, 갈림길인가
— Flide가 이끄는 '상태 포킹' 패러다임

자기회귀 토큰 생성과 KV 캐시를 공리처럼 여겨온 에이전틱 서빙 스택은, 결정 모델(Jev 계열)이 요구하는 '정확한 상태 포킹(exact state forking)' 앞에서 어떻게 바뀌어야 하는가. 이 글의 답은 "전면 대체"가 아니라 "이원 원시 연산(dual-primitive)으로의 재정의"다.

대상 논문 · Flide: Accelerating Decision Inference with Exact State Forking
참고 개념 · Scepsy · Pythia · SMetric · Jev · DecisionRank · Jev-Mobile · Wiki 엔티티 12종
🔍 이 글이 검증하는 Wiki Query

"현재 Wiki에서 에이전틱 서빙(Scepsy · Pythia · SMetric)과 하네스 런타임은 자기회귀적 토큰 생성과 KV 캐시를 최적화 대상으로 전제하는데, 에이전트의 System One 실행이 정확한 상태 포킹을 원시 연산으로 요구하는 결정 모델(Jev 계열)로 이동한다면, 서빙 인프라의 기본 단위가 '토큰 생성'에서 '상태 분기'로 재정의되어야 하는가?"

1지금의 서빙은 '이어 쓰기'의 세계입니다

현재의 LLM 서빙을 한 문장으로 요약하면 거대한 녹음실입니다. 요청 하나가 들어오면 테이프(컨텍스트)를 감아 올리고, 그 끝에 한 트랙씩 — 한 토큰씩 — 이어 녹음합니다. 요청이 끝나지 않으면 녹음은 멈추지 않고, 서빙 시스템이 경쟁하는 것은 결국 얼마나 많은 테이프를 동시에 감을 것인가(배칭), 이미 녹음된 앞부분을 어떻게 재활용할 것인가(prefix 공유), 테이프가 꽉 차기 전에 앞을 어떻게 요약해 덮어쓸 것인가(압축)입니다. 그리고 그 테이프 자체, 즉 "지금까지 녹음된 모든 것"이 바로 KV 캐시입니다.

이 세계관의 개념적 뿌리는 Wiki의 [[attention-carried-conversational-state]]에 기록되어 있습니다. 대화·세션의 상태가 어텐션 계산에 운반된다는 관점 — 곧 "상태 = 캐시"라는 전제입니다. 서빙이 최적화한다고 믿어온 것은 사실 '상태' 그 자체가 아니라, 상태가 운반되는 한 가지 형태의 효율이었던 셈입니다.

🗂 Wiki 증거 — '토큰 생성 + KV 캐시'는 구조적 기본값
  • [[attention-carried-conversational-state]] — 상태가 어텐션(KV 캐시)에 운반된다. "상태 = 캐시" 전제의 뿌리.
  • [[autocompaction]] — 컨텍스트 압축이 런타임의 핵심 연산이 된 것도, 상태가 토큰/컨텍스트 형태로만 존재하기 때문.
  • [[adaptive-inference]] — 이 엔티티의 SpecKV 논문은 적응성의 차원이 "압축(KV 캐시 상태)에 반응"하기까지 확장되었음을 보여준다. 적응성 논의조차 캐시·디코딩 파라미터를 대상으로 한다.
  • [[agent-loop-as-computation]] · [[agent-as-harness]] · [[agentic-harness-engineering]] — 하네스 루프는 토큰 스트림 위의 계산으로 취급되며, 제어 코드 역시 토큰 생성 흐름 위에서 "언제 정책·도구를 쿼리할지"를 결정한다.

Scepsy·Pythia·SMetric으로 대표되는 에이전틱 서빙 논문들도, 발췌 범위 밖이라 링크 없이 전제로 받아들이자면, 예외가 아닙니다. 이들의 최적화 대상 역시 자기회귀적 토큰 생성과 KV 캐시입니다. 이 세계에서 서빙이 노출하는 원시 연산(primitive)은 단 하나 — "다음 토큰 생성"이며, 모든 에이전트 요청은 선형의 토큰 스트림으로 환원됩니다. 문제는, 이 단일 원시 연산이 공리처럼 여겨지고 있다는 점입니다.

현재 서빙 스택이 최적화해온 것은 '상태'가 아니라, 상태를 운반하는 한 가지 형태 — 캐시 — 의 효율이다. — 섹션 1의 요지

2System One의 단위는 토큰이 아니라 '결정'입니다

에이전트의 하루를 들여다보면, 인간의 인지에서 차용한 구분이 그대로 보입니다. 계획을 세우고 글을 쓰고 도구를 조율하는 느리고 반추적인 실행 — System Two. 그리고 어떤 도구를 부를지, 어느 경로로 라우팅할지, 후보 중 무엇을 고를지를 순식간에 판단하는 빠르고 반복적인 실행 — System One입니다. 최근 논문들의 흐름은 이 System One의 단위가 토큰이 아니라 범주적 결정(categorical decision)임을 일관되게 보여줍니다.

Decision models such as Jev … providing lightweight and reliable categorical reasoning for rapid System One execution. — Flide: Accelerating Decision Inference with Exact State Forking

Wiki의 증거는 세 갈래로 모입니다. Flide는 Jev 계열 결정 모델이 System One을 담당한다고 명시하며, 그 추론을 가속하는 핵심으로 정확한 상태 포킹을 제시합니다. DecisionRank는 decision model이 "choices or scores를 직접 예측하여 자기회귀 디코딩 지연을 회피"한다고 기록합니다. 그리고 [[access-planning-gap]] 엔티티에 기록된 Jev-Mobile은 Jev를 모바일 GUI 에이전트의 실행기로 실제 배치합니다. 즉 이것은 실험실 아이디어가 아니라, 이미 기기 위에서 도는 실행 모델입니다.

이 변화를 가장 잘 보여주는 비유는 게임의 세이브 파일입니다. 자기회귀 모델에게 갈림길은 부담스럽습니다. 분기마다 문장을 처음부터 다시 '이어 써서' 각 시나리오를 재현해야 하니까요. 반면 결정 모델 + 포킹의 세계에서는 갈림길 앞에서 세이브 파일을 통째로 복사해 둔 뒤, 복사본마다 다른 선택을 시험해보고, 가장 잘 나온 세이브로 돌아가 이어서 플레이하면 됩니다. 체스로 말하자면, 다음 수를 '글로 설명'하는 대신 보드판 자체를 복제해 몇 수를 미리 두어보는 것입니다.

여기서 두 가지가 결정적입니다. 첫째, 결정 모델의 상태는 KV 캐시가 아닙니다. 상태의 운반체 자체가 다르므로, 탐색의 원시 연산도 "다음 토큰 생성"이 아니라 상태의 정확한 복제·분기가 됩니다. '정확한(exact)'이라는 수식은 장식이 아닙니다 — 근사적으로 비슷한 상태가 아니라 비트 단위로 동일한 복제여야, 분기별 평가 결과가 신뢰할 수 있고 재현 가능해지기 때문입니다. 둘째, 모델이 lightweight이기 때문에 상태가 작고, 따라서 포킹이 '경제적으로' 성립하는 원시 연산이 된다는 점입니다. 복제 한 번이 공짜가 아니라 충분히 싸다면, 탐색의 경제가 통째로 뒤집힙니다.

상태 S → fork → S₁S₂S₃… Sₖ → evaluate → 최적 분기 S* → commit

Flide가 그리는 System One 실행: 토큰을 잇는 대신, 세계를 복제하고 골라낸다.

3네 가지 균열 — 재정의가 필요한 이유

그렇다면 왜 '성능 최적화 팁' 수준이 아니라 서빙의 기본 단위를 다시 정의해야 할까요. Wiki 증거는 네 개의 균열을 가리킵니다. 각 균열은 서로 다른 층 — 메모리, 실행 전략, 스케줄링, 패러다임 — 에서 동시에 발생하고 있다는 점에서, 부분修补가 아닌 구조적 응답을 요구합니다.

1

상태 운반체의 교체 — 값 의미론 스냅샷

exact forking은 값 의미론(value semantics)의 스냅샷을 요구합니다. KV 캐시의 prefix 공유는 "불변 접두사 + append"라는 공유이지 분기가 아닙니다. 복사 노트의 앞장에 책갈피를 꽂고 각자 이어 쓰는 것이 아니라, 노트 전체를 통째로 복사해 각자 따로 쓰는 것입니다. [[agent-sandbox-state-management]]가 다뤄야 할 관리 대상 자체가 "공유되는 캐시"에서 "분기 가능한 전체 복사본"으로 바뀐다는 뜻입니다.

2

추측 실행의 그레인 상승 — 토큰에서 액션으로

기존의 speculative decoding은 토큰 수준의 '찍어맞히기'입니다. 그러나 [[action-level-speculation]]이 예고했던 액션 수준의 추측 실행이 포킹과 결합하면, 토큰 추측을 대체하는 fork-then-evaluate 탐색이 가능해집니다. 다음 글자를 여러 개 미리 써보는 대신, 다음 '행동' 자체를 여러 개 시연하는 것입니다.
