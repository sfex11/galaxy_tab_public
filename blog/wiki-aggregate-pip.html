Section 01

1차 진단은 맞았다 — 하지만 증상을 원인으로 착각했다

최근 연구 생태계에서 에이전트 구조적 출력의 비용 병목을 진단하는 논의가 활발하다. 특히 "Tool Attention Is All You Need: Dynamic Tool Gating and Lazy Schema Loading"(2026-04-26)은 다중 서버 MCP 배포 환경에서 파이프라인 전체 레이턴시의 병목이 개별 LLM 호출 자체가 아니라 스키마 축적에 의해 결정된다는 사실을 명확히 보여주었다.

이 진단은 의미가 있다. 기존에는 "모델 추론이 느리다"는 식의 단일 지점 분석에 갇혀 있었는데, 파이프라인 전체를 조망하여 병목의 위치를 '서빙 계층'으로 올려놓았기 때문이다. 하지만 이 재정의가 여전히 표층적 병목에 머물러 있다는 것이 핵심적인 비판이다.

비유

병원 응급실에서 환자가 계속 기다리고 있다. 누군가 "수술실이 부족해서 그래"라고 진단했다. 수술실 확충은 분명 도움이 된다. 하지만 정작 환자의 상태를 이미 파악하고 있는 분류 담당 간호사의 정보가 수술실 배정에 전혀 활용되지 않고 있다면, 수술실을 아무리 늘려도 근본적 해결은 아니다. 간호사는 이미 "이 환자는 수술이 필요 없어"라고 알고 있는데, 시스템은 그 정보를 무시하고 모든 환자를 수술실 대기열에 넣고 있는 것이다.

스키마 축적이 병목이라는 진단은 "수술실이 부족하다"는 관찰에 해당한다. 맞는 말이지만, 왜 불필요한 스키마가 축적되는지에 대한 질문으로 이어지지 않으면 해법이 엉뚱한 방향으로 수렴한다. 그 방향이 바로 "스키마 로딩을 최적화하자"인데 — 이는 병목을 제거한 것이 아니라 형태를 바꾼 것에 불과할 수 있다.

"스키마 축적은 증상이지 원인이 아니다. 더 근본적인 원인은 파서가 이미 예측한 구조 정보가 KV 관리에 조건화되지 않는 간극에 있다." — Wiki 질문자의 핵심 지적

Wiki의 bottleneck-misattribution 엔티티가 정확히 이 현상을 지칭한다. 병목을 잘못 귀인하는 것. aggregate-pipeline-serving이 "스키마 축적이 병목"이라고 진단한 것 자체가, 더 근본적인 원인인 파서-모델 간 구조적 가시성의 미활용을 은폐하는 2차적 오귀인일 수 있다.

Section 02

파서는 이미 알고 있다: 구조적 가시성의 미활용 간극

제약 디코딩(constrained decoding)의 파서는 토큰을 생성하기 이전에 이미 다음에 올 구조를 예측한다. JSON 스키마로 출력한다고 가정해 보자. 파서는 현재 "name": "홍길동", "age"까지 생성했다면, 다음이 콜론과 숫자 값이 될 것을 이미 알고 있다. 객체의 어떤 필드가 남았는지, 배열의 몇 번째 요소를 처리 중인지 — 이 모든 구조 정보가 파서 상태에 이미 존재한다.

그런데 현재 시스템은 이 정보를 KV 캐시 관리에 전혀 활용하지 않는다. 모델은 파서가 이미 알고 있는 구조적 진행도를 무시한 채, 이전 토큰들의 KV 캐시를 일괄적으로 유지한다. 마치 네비게이션이 "앞으로 500m 후 좌회전"이라고 알려주고 있는데, 운전자가 그 정보를 무시하고 매번 지도를 처음부터 다시 펼치는 것과 같다.

파서 전이 상태
(구조 예측 완료)
구조적 가시성 단절
KV 캐시 관리
(파서 정보 미반영)
↓
불필요한 캐시 유지
(메모리 & 연산 낭비)

대상 논문 "Parser States Already Know: Structure-Conditioned KV Persistence for Structured Generation"의 제목 자체가 이 간극을 정확히 가리킨다. "파서 상태는 이미 알고 있다" — 그런데 시스템은 듣지 않는다.

여기서 '구조적 가시성(structural visibility)'이라는 개념이 핵심적이다. 파서가 예측한 생성 구조가 모델의 KV 관리 레이어까지 보인다면, 더 이상 생성될 구조와 무관한 이전 레이어의 KV 엔트리를 안전하게 드롭할 수 있다. 이는 단순한 캐시 최적화가 아니라, 이미 계산된 정보의 흐름을 시스템 하위 계층까지 연결하는 문제다.

🔍
구조적 가시성이란 무엇인가

파서의 전이 상태(현재 JSON의 어떤 필드, 어떤 깊이, 어떤 타입을 처리 중인지)가 KV 캐시 지속성(persistence) 결정에 입력으로 사용될 수 있는가? 현재는 불가능하다. 파서와 KV 관리는 독립적으로 동작하며, 둘 사이에 정보 경로가 존재하지 않는다. 이것이 '가시성의 미활용'이다.

Section 03

같은 패턴, 다른 얼굴: 알고리즘-시스템 번역 간극

이 간극은 완전히 새로운 현상이 아니다. Wiki의 algorithm-system-translation-gap 엔티티가 이미 동일한 패턴을 다른 영역에서 포착했다.

Crab의 사례: 의미론 → OS 스냅샷

"Crab: A Semantics-Aware Checkpoint/Restore Runtime for Agent Sandboxes"(2026-05-02)는 에이전트의 의미론적 의존 그래프를 OS의 체크포인트 메커니즘으로 번역할 때 발생하는 비효율을 다룬다. 에이전트는 "이 변수와 저 변수 사이에 의존관계가 있다"는 의미론적 정보를 이미 가지고 있는데, OS 체크포인트는 이를 모른 채 전체 메모리 스냅샷을 찍는다.

질문자의 사례: 파서 전이 → KV 캐시 지속성

동일한 패턴이다. 파서는 이미 "이 구조 요소는 끝났다"는 정보를 가지고 있는데, KV 캐시 관리는 이를 모른 촤 일괄 유지한다.

구조적 정보 하위 시스템 관리 간극의 결과
의미론적 의존 그래프
(Crab)		 OS 체크포인트
전체 스냅샷		 불필요한 메모리 복사
파서 전이 구조
(본 논의)		 KV 캐시 지속성
일괄 유지		 불필요한 캐시 유지

두 사례의 공통 구조는 명확하다: 상위 레벨에서 이미 계산된 구조적 정보가 하위 시스템의 관리 결정에 번역되지 않는다. 이 간극을 메우는 것이 최적화의 실제 공격면이다.

비유

건축 설계사가 이미 "이 벽은 비하중 벽이라 언제든 철거 가능하다"라고 도면에 표시해 두었다. 그런데 해체 현장의 작업자는 그 도면을 보지 못하고, 모든 벽을 동등한 '철거 대상'으로 분류한 뒤 하나하나 시험해 본다. 설계 정보가 현장 관리 결정에 번역되지 않으면, 이미 알고 있는 정보를 다시 '발견'하는 비용이 발생한다.

SpecKV의 시사점: 내부 상태 기반 적응

adaptive-inference 엔티티에서 "SpecKV: Adaptive Speculative Decoding with Compression-Aware Gamma Selection"(2026-05-05)은 적응적 추론의 입력을 외부 환경 반응에서 내부 시스템 상태 반응으로 확장했다. 압축 상태라는 내부 신호에 반응하여 추론 전략을 조정하는 것이다.

질문자의 제안은 이를 한 단계 더 밀어붙인다: 적응의 입력을 파서가 예측한 생성 구조로 확장하는 것. 압축 상태가 내부 신호로 유효하다면, 파서 전이가 예측하는 구조적 진행도 역시 동등한 내부 신호로 활용 가능하다는 논리다. SpecKV가 "압축률을 보고 판단한다"면, 파서-캐시 조건화는 "구조 진행도를 보고 판단한다"가 된다.

Section 04

파서-캐시 조건화: 새로운 최적화 차원의 발견

지금까지의 논의를 하나의 메커니즘으로 통합하면, 다음 개념이 도출된다.

🆕
파서-캐시 조건화 (Parser-Cache Conditioning)

제약 디코딩의 파서 전이가 생성 구조를 예측하므로, 이를 KV 지속성 결정에 조건화하여 불필요한 캐시를 드롭하는 메커니즘.

이 개념은 현재 Wiki에 자립적 슬러그로 존재하지 않는 새로운 연결이다. 세 엔티티의 교집합에 위치한다.

  • aggregate-pipeline-serving — 스키마 축적이 파이프라인 병목이라는 진단 제공
  • algorithm-system-translation-gap — 상위 구조 정보가 하위 시스템 관리에 번역되지 않는 간극 패턴 제공
  • adaptive-inference — 내부 시스템 상태에 반응하여 추론을 적응시키는 패러다임 제공

이 세 가지가 만나는 지점이 바로 파서-캐시 조건화다. 구체적으로 어떻게 동작할까?

작동 원리의 개념적 스케치

⚙️
단계별 메커니즘

1. 파서 전이 관찰: 제약 디코딩 파서가 현재 상태 전이를 수행할 때, 어떤 구조 요소가 종료되었는지 감지한다. 예: JSON 객체의 특정 필드 완료, 배열 요소 종료.

2. 구조적 의존도 평가: 종료된 구조 요소에 해당하는 이전 토큰들의 KV 엔트리가, 앞으로 생성될 토큰들과 얼마나 의존관계가 있는지 평가한다. 파서의 문법 지식을 기반으로 이 평가는 저비용으로 수행 가능하다.

3. 조건부 캐시 드롭: 의존도가 낮은 KV 엔트리를 안전하게 드롭한다. 이는 무작위 드롭이 아니라, 파서의 구조 예측에 조건화된 드롭이다.

4. 지속성 보장: 여전히 필요한 KV 엔트리(예: 아직 닫히지 않은 객체의 키 정보)는 유지한다.

중요한 점은 이 메커니즘이 외부에서 추가 정보를 로딩하지 않는다는 것이다. 이미 파서 내부에 존재하는 정보를 활용할 뿐이다. 이것이 "스키마 로딩 최적화"와 근본적으로 다른 이유다. 스키마 로딩 최적화는 외부 정보의 처리 효율을 높이는 것이지만, 파서-캐시 조건화는 이미 내부에 있는 정보의 활용도를 높이는 것이다.

"최적화의 실제 공격면은 외부 스키마 로딩이 아니라 파서-모델 간 구조적 가시성의 미활용에 있다." — 원 질문의 핵심 명제
Section 05

병목 전이에서 진정한 공격면으로: 패러다임 전환의 필요성

Wiki의 bottleneck-transference 엔티티는 병목이 제거된 것이 아니라 다른 형태로 옮겨간 현상을 지칭한다. "스키마 축적이 병목이니 로딩을 최적화하자"는 접근은 정확히 이 전이 패턴에 해당할 위험이 있다.

스키마 로딩 병목은 줄었지만, 파서가 이미 가진 구조 정보를 버리고 KV 캐시를 무조건 유지하는 비효율이 잔존한다. 병목의 형태가 바뀌었을 뿐, 본질 — 상위 계층 정보가 하위 계층 관리에 반영되지 않는다 — 은 그대로다.

비유

회사에서 부서 간 협업이 느리다. 누군가 "회의실 예약 시스템이 병목이다"라고 진단하고, 예약 시스템을 자동화했다. 회의실 잡는 시간은 줄었다. 하지만 정작 회의에 필요한 선행 정보가 다른 부서에서 이미 준비되어 있는데도 매번 회의에서 처음부터 논의된다면, 회의 자체의 비효율은 해결되지 않은 것이다. 회의실 예약을 빠르게 한 것이 협업의 근본 문제를 해결한 착각을 준다.

패러다임 전환: 외부 최적화에서 내부 가시성으로

현재 패러다임은 "외부에서 들어오는 것을 어떻게 효율적으로 처리할까"에 맞춰져 있다. 스키마 로딩을 줄이고, 툴 호출을 게이팅하고, 파이프라인을 병렬화한다. 모두 유효한 최적화지만, 같은 방향의 개선이다.

필요한 전환은 "내부에 이미 있는 것을 어떻게 시스템 전체에 보이게 할까"로 방향을 틀는 것이다. 파서가 아는 것을 KV 관리가 보게 하고, 의미론적 의존을 OS가 보게 하고, 구조적 진행도를 캐시 정책이 보게 하는 것. 이것이 algorithm-system-translation-gap이 제시하는 간극을 메우는 근본적 접근이다.

파서-캐시 조건화는 이 전환의 구체적 사례다. 새로운 논문을 기다릴 필요 없이, 기존 엔티티들의 교집합에서 이미 도출 가능한 설계 공간이다. 다만, 이 메커니즘을 직접 검증한 논문이 현재 Wiki에 없으므로 새로운 연결로 기록되어야 한다.

결론적으로, 에이전트 구조적 출력 최적화의 실제 전장은 스키마 로딩이 아닌 정보의 수직적 흐름에 있다. 상위 계층(파서)에서 하위 계층(KV 캐시 관리)으로 구조적 정보가 얼마나 깊이, 얼마나 빠르게 전달되는가. 이 가시성의 정도가 곧 최적화의 상한선을 결정한다. 스키마를 줄이는 것은 병목을 옮기는 것이고, 파서의 눈을 KV 관리에 연결하는 것이 병목을 해체하는 것이다.
