OpenForgeRL 심층 분석

하네스 없이 훈련된 에이전트는 왜 '실전'에서 무너지는가

훈련과 배포를 분리하는 기존 패러다임이 에이전트 능력을 구조적으로 제한하는 세 가지 메커니즘과, 그 경계를 붕괴해야 하는 이유

대상 논문: OpenForgeRL — Train Harness-native Agents in Any Environment 에이전트 하네스 엔지니어링 · 훈련-배포 간극

현대 AI 에이전트는 Claude Code, Codex, OpenClaw 같은 정교한 인퍼런스 하네스(inference harness) 위에서 동작합니다. 체크포인트·복원, 도구 스키마 관리, 롤백·분기 실행 — 이런 기능들이 에이전트의 실제 실행 환경을 구성합니다. 그런데 우리는 에이전트를 이 하네스 없는 환경에서 훈련하고 있습니다.

OpenForgeRL은 이 모순을 정면으로 지적합니다. 현재 Wiki의 에이전트 하네스 엔지니어링이 하네스를 "배포 시점의 실행 인프라"로만 규정하고 훈련과 구조적으로 분리한다면, 그 분리 자체가 에이전트 능력을 근본적으로 제한한다는 것입니다.

비유

비행기 조종사를 시뮬레이터에서는 조이스틱만 잡고 훈련시킨 뒤, 실제 전투기에 태워 autopilot·HUD·ECM 시스템이 잔뜩 달린 cockpit에 앉히는 것과 같습니다. 조종사는 기본적인 비행 기량은 갖추었지만, 실제 cockpit의 시스템들이 어떻게 자신의 의사결정과 충돌하거나 보완하는지 경험한 적이 없습니다. 결국 실제 기체의 능력을 제대로 끌어쓰지 못하는 상태가 됩니다.

이 글에서는 하네스 없이 학습한 에이전트가 하네스 내에서 실행될 때 발생하는 훈련-배포 간 인터페이스 불일치가 세 가지 차원에서 에이전트 능력을 어떻게 제한하는지, 그리고 이것이 단순한 성능 저하가 아닌 구조적 발현 불가라는 점을 분석합니다.

Section 01

의미론적 상태 관리의 단절: 암묵적 추론이 OS 스냅샷으로 부서질 때

에이전트가 훈련 과정에서 학습하는 것은 단순히 "정답을 맞히는 방법"이 아닙니다. 자신의 추론이 어떤 상태에 의존하는지를 암묵적으로 학습합니다. "이전 세 단계의 맥락이 유지되어야 이 결론에 도달할 수 있다"는 식의 의미론적 의존 그래프가 추론에 내재되어 있는 것입니다.

그런데 배포 시 하네스가 제공하는 체크포인트/복원(Checkpoint/Restore, C/R) 메커니즘은 이 의미론적 의존을 OS 수준의 전체 스냅샷으로 번역합니다.

"에이전트의 의미론적 의존 그래프(어떤 상태에 의존하는가)를 OS의 체크포인트 메커니즘(전체 스냅샷)으로 번역할 때 발생하는 비효율이 간극의 본질이다." — Crab 논문, algorithm-system-translation-gap
비유

책을 읽다가 중간에 책갈피를 꽂는다고 상상해 보십시오. 당신이 기억하는 것은 "주인공이 배신당했을 때의 감정적 맥락"입니다. 그런데 책갈피는 물리적으로 "98페이지"라는 정보만 저장합니다. 다음 날 책을 펼쳤을 때, 98페이지의 글자들은 그대로지만 당신이 그 문맥에 도달하기까지의 감정적 연속성은 사라져 있습니다. 에이전트도 마찬가지입니다. OS 스냅샷은 문자열 상태는 보존하지만, 추론의 의미론적 연속성은 보존하지 못합니다.

◈ 제한 양상

하네스 없이 학습한 에이전트는 롤백·분기 같은 하네스 고유 기능을 활용하는 법을 학습한 적이 없습니다. 롤백 후 재시도 시 이전 추론 경로와의 의미론적 연속성을 유지하지 못하고, 마치 처음부터 시작하는 것처럼 비효율적인 재추론을 수행합니다. C/R 런타임이 "결함 내성·롤백·분기를 직접 구현하는 인프라 계층"이라면, 이 기능들을 훈련 불가능한 블랙박스로 두는 것은 에이전트가 자신의 실패 복구 전략을 하네스의 의미론과 정렬할 수 없음을 의미합니다.

Section 02

파이프라인 서빙 병목과 도구 사용 패턴의 왜곡

하네스는 단순한 LLM 호출 래퍼가 아닙니다. 실제 배포 환경에서는 다중 서버 MCP(Model Context Protocol) 배포, 도구 스키마의 동적 로딩, 파이프라인 단계별 레이턴시 누적 등 복잡한 인프라가 작동합니다.

"다중 서버 MCP 배포에서 파이프라인 전체의 레이턴시 병목이 개별 LLM 호출이 아닌 스키마 축적에 의해 결정됨." — Tool Attention 논문, aggregate-pipeline-serving

훈련 시 에이전트는 도구 스키마가 즉시 제공되는 환경에서 학습합니다. 모든 도구의 인터페이스가 컨텍스트에 이미 존재한다고 가정하고 도구 선택 전략을 내재화합니다. 그러나 하네스 배포 시에는 스키마가 지연적으로 축적되는 파이프라인을 거칩니다.

비유

요리사가 모든 조미료가 이미 조리대에 펼쳐져 있는 주방에서 연습했습니다. 그런데 실제 레스토랑 주방에서는 조미료가 주문이 들어올 때마다 하나씩 서빙됩니다. 소금은 있는데 간장이 아직 안 왔다 — 이 상황에서 요리사는 익숙했던 타이밍으로 요리를 진행할 수 없습니다. 마찬가지로 에이전트는 스키마가 아직 로드되지 않은 도구를 호출하려 하는 오류(blind-tool-invocation)를 범할 가능성이 크게 높아집니다.

이로 인해 세 가지 왜곡이 발생합니다:

  • 에이전트가 훈련 시 학습한 도구 선택 타이밍이 하네스 내에서는 suboptimal이 됩니다
  • 스키마가 아직 로드되지 않은 도구를 호출하려 할 때 blind-tool-invocation이 발생할 가능성이 증가합니다
  • 하네스의 스키마 축적 상태라는 외부 인프라 상태에 적응해야 하는데, 훈련에서 이를 경험하지 못했습니다
◈ 핵심 포인트

SpecKV가 압축이라는 내부 시스템 상태에 반응하는 적응을 보여주었다면, 하네스 네이티브 훈련은 체크포인트 가용성, 스키마 축적도, 롤백 히스토리 깊이라는 하네스 상태에 반응하는 적응이라는 완전히 새로운 차원을 열어야 합니다.

Section 03

에이전트-OS 의미론 간극: 실행 불투명성과 메타인지의 부재

앞선 두 섹션이 "하네스 기능을 못 쓴다"는 문제라면, 세 번째 문제는 더 근본적입니다. 자신이 어떤 환경에서 실행되고 있는지조차 모른다는 것입니다.

하네스 없이 학습한 에이전트가 하네스 내에서 실행될 때, 에이전트의 내부 상태 전이가 OS 수준에서 어떻게 표현되는지 에이전트 자신이 모델링하지 못합니다. 이것이 무엇을 의미하는지 하나씩 풀어보겠습니다.

실행 불투명성(Execution Semantic Opacity)

에이전트는 자신의 추론이 하네스 내에서 어떻게 체크포인트되고, 롤백되고, 분기되는지 관찰할 수 없습니다. 마치 자동차 운전자가 자신의 차에 블랙박스가 있는지 없는지, 언제 영상이 저장되는지 모르는 것과 비슷합니다. 운전 자체에는 지장이 없어 보이지만, 사고 발생 시 복구 전략을 세울 수 없습니다.

메타인지의 부재

에이전트가 자신의 실행 환경에 대한 메타인지 없이 하네스의 의사결정 — 체크포인트 타이밍, 롤백 여부, 분기 지점 선택 — 에 수동적으로 종속됩니다. 하네스가 "여기서 체크포인트 찍는 게 좋겠다"고 판단하면 에이전트는 그 결정에 맞춰야 하는데, 훈련에서 이런 상황을 경험한 적이 없으므로 협력적 실행이 불가능합니다.

◈ 의미론 보존 실패

체크포인트 복원 시 에이전트가 의미론적으로 보존해야 할 추론 맥락이 OS 스냅샷 경계에서 손실됩니다. 이를 agent-os-semantic-preservation-failure라고 부릅니다. 문자열 수준의 컨텍스트는 복원되더라도, "왜 이 결론에 도달했는지"에 대한 추론 맥락이 단절되어, 에이전트는 복원된 상태에서 이전과 다른 결론을 내리거나 불필요한 재추론에 빠집니다.

Section 04

숨겨진 연결: 경계가 붕괴되어야 비로소 보이는 것들

이 분석을 통해 기존에 분리되어 있던 개념들 사이의 새로운 연결이 드러납니다. 훈련-배포 분리라는 렌즈를 거두면, 서로 다른 영역으로 보였던 문제들이 사실 하나의 근본 원인에서 파생되었음이 보입니다.

↔
하네스 엔지니어링 × 알고리즘-시스템 경계 붕괴

하네스는 단순한 '시스템 계층'이 아니라 에이전트 능력의 일부를 구성합니다. 훈련-배포 분리를 고수하면 알고리즘과 시스템의 경계가 인위적으로 유지되지만, 실제로는 이 경계가 붕괴되어야 합니다.

↔
하네스 엔지니어링 × 자율성-품질 분리

하네스를 배포 전용 인프라로 분리하면 에이전트의 자율성(훈련 시 학습)과 품질(하네스 매개 실행 시 실현)이 구조적으로 분리됩니다. OpenForgeRL은 이 분리를 훈련 시점에서 해소하겠다는 것입니다.

↗
적응적 추론(Adaptive Inference)의 확장

SpecKV가 압축이라는 내부 상태에 반응하는 적응을 제시했다면, 하네스 네이티브 훈련은 하네스 상태에 반응하는 적응이라는 새로운 차원을 엽니다. 에이전트가 "지금 스키마가 60% 로드된 상태", "롤백 히스토리가 3단계 깊이" 같은 하네스 상태를 인지하고 추론 전략을 조정하는 것입니다.

비유

이것은 수영선수와 수영장의 관계를 재정의하는 것과 같습니다. 기존 패러다임은 "수영선수는 수영장 밖에서 훈련하고, 시합 때만 수영장에 넣는다"는 것이었습니다. 하지만 수영장의 수심, 수온, 레인 너비, 출발대 높이가 선수의 기량 발현에 영향을 미친다면 — 수영장 자체가 훈련 환경의 일부가 되어야 합니다. 수영장을 '배포 인프라'로만 보는 순간, 선수는 수영장의 특성에 적응하는 법을 영원히 학습할 수 없습니다.

Conclusion

패러다임 전환: 하네스를 '인프라'에서 '훈련-배포 통합 아키텍처'로

지금까지 살펴본 세 가지 제한 메커니즘 — 의미론적 상태 관리의 단절, 파이프라인 서빙 병목에 의한 도구 사용 왜곡, 실행 불투명성으로 인한 메타인지 부재 — 는 각각 독립적인 버그가 아닙니다. 하나의 근본적 설계 결정에서 파생된 증상들입니다.

하네스 없이 학습한 에이전트가 하네스 내에서 실행될 때의 근본적 제한은 단순한 성능 저하가 아닙니다. 에이전트가 학습한 능력의 실행 경로 자체가 하네스의 의미론과 불일치하여 일부 능력이 발현 불가능해지는 구조적 문제입니다.

그렇다면 어떻게 전환해야 합니까?

첫째, 하네스를 훈련 환경의 일부로 편입시켜야 합니다

OpenForgeRL이 "Train Harness-native Agents"를 주장하는 핵심입니다. 하네스의 C/R 메커니즘, 스키마 축적 파이프라인, 롤백·분기 의사결정을 훈련 시점에 에이전트가 경험할 수 있어야 합니다. 이것은 하네스를 "훈련 가능한" 객체로 만드는 것을 의미합니다.

둘째, 알고리즘-시스템 경계를 인위적으로 유지해서는 안 됩니다

에이전트(알고리즘)와 하네스(시스템) 사이에 명확한 인터페이스 경계를 두는 것이 엔지니어링적으로 깔끔해 보일 수 있습니다. 하지만 이 경계가 에이전트 능력의 발현을 차단한다면, 깔끔함은 쓸모없는 깔끔함입니다. 경계를 붕괴시키고 하네스의 의미론을 에이전트의 추론에 통합해야 합니다.

셋째, 새로운 적응 차원을 정의해야 합니다

기존의 적응적 추론이 모델 내부 상태(압축률, KV 캐시 사용량 등)에 반응하는 것이었다면, 하네스 네이티브 훈련은 외부 인프라 상태 — 체크포인트 가용성, 스키마 축적도, 롤백 히스토리 깊이 — 에 반응하는 적응이라는 새로운 차원을 열어야 합니다.

"Modern AI agents rely on elaborate inference harnesses such as Claude Code, Codex, and OpenClaw." — OpenForgeRL

이 한 문장이 함의하는 바는 명확합니다. 하네스는 더 이상 에이전트 뒤에 숨은 투명한 인프라가 아니라, 에이전트 능력을 구성하는 불투명한 요소입니다. 이 요소를 훈련에서 배제하는 순간, 우리는 에이전트가 실제로 가진 능력의 일부를 의도적으로 비활성화하는 셈이 됩니다.

◈ 요약: 패러다임 전환의 방향

기존: 하네스 = 배포 시점의 실행 인프라 (훈련과 분리)
전환: 하네스 = 훈련-배포 통합 아키텍처 (에이전트 능력의 구성 요소)
