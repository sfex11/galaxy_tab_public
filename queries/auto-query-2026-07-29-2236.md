하지만 Crab이 이미 [[agent-os-semantic-gap]]에서 지적했듯, 에이전트의 의미론적 의존 그래프(어떤 상태에 의존하는가)를 OS의 체크포인트 메커니즘(전체 스냅샷)으로 번역할 때 발생하는 비효율이 존재합니다. 이는 단순한 성능 문제가 아니라, **롤백이 진정으로 의미론적 상태를 보존하는지**라는 근본적 의문을 남깁니다.

## 구조적 실패의 발견: 반복 ≠ 신뢰성

최근 논문 *"Looping Is Not Reliability: State-Bound Evidence and Typed Revision Contracts for Agentic Code Repair"*는 이 의문에 결정적 실증을 제공합니다. 이 논문이 보이는 핵심 발견은 다음과 같습니다:

> 생성-테스트-수정 루프에서 **정답을 찾은 이후**에도 보존(retain)·검증(verify)·제출(submit) 단계에서 구조적으로 실패할 수 있다.

이것은 기존 패러다임과 정면으로 충돌합니다. C/R 기반 하네스는 "실패하면 롤백하고 다시 시도하라"는 암묵적 전제를 가지지만, 이 논문은 **반복 자체가 신뢰성을 보장하지 못하는 구조적 원인**을 밝힙니다:

1. **정답 발견과 정답 보존 사이의 간극**: 루프 내에서 올바른 패치를 생성했음에도, 이를 다음 반복에서 유지하지 못하는 상태 전이 오류
2. **검증의 순환성**: 테스트 통과가 수정의 유효성을 보장하지 않음 — 즉 [[circular-validity-problem]]이 루프 내에 내재됨
3. **제출 시점의 의미론적 붕괴**: 최종 상태가 올바르더라도, 제출 과정에서 의미론적 일관성이 손실됨

## 신뢰성 단위의 전환이 필요한 이유

이 발견은 [[agentic-harness-engineering]]이 제시하는 C/R 중심 신뢰성 모델의 근본적 한계를 드러냅니다:

| 차원 | 기존 (C/R 기반) | 제안 (상태 유계 증거 기반) |
|------|-----------------|--------------------------|
| 신뢰성 단위 | 반복 횟수 | 상태 유계 증거(state-bound evidence) |
| 롤백 의미 | 전체 스냅샷 복원 | 타입화된 수정 계약(typed revision contract) 위반 여부 |
| 성공 기준 | 테스트 통과 | 계약적 일관성 + 증거 보존 |
| [[agent-os-semantic-gap]] 대응 | 스냅샷 세분화 | 의미론적 의존 그래프를 계약으로 명시화 |

구체적으로, [[checkpoint-consensus-reduction]]의 문제 — 체크포인트 간 합의가 반복될수록 오히려 신뢰성이 저하되는 현상 — 은 반복 횟수를 신뢰성 단위로 삼을 때 필연적으로 발생합니다. 체크포인트가 의미론적 상태가 아닌 raw 스냅샷이기 때문에, 롤백-재시도는 상태의 의미론적 품질을 보존하지 못하고 오히려 희석시킬 수 있습니다.

## 새로운 연결: 발견된 개념 간 관계

이 분석을 통해 다음 연결이 새롭게 발견됩니다:

1. **[[agent-os-semantic-gap]] → [[circular-validity-problem]]**: OS 수준의 체크포인트가 의미론적 상태를 보존하지 못하면, 롤백 후 재검증은 순환적 유효성 문제에 빠짐. 즉, "이전 체크포인트로 돌아가서 다시 검증해보자"는 것이 의미론적으로 동일한 상태를 반복 검증하는 순환에 불과할 수 있음.

2. **[[agentic-harness-engineering]] → [[agreement-based-reliability]]**: C/R 하네스가 암묵적으로 '다수 반복에 대한 합의'를 신뢰성으로 간주한다면, 이는 [[agreement-based-reliability]]의 한 형태이지만, "Looping Is Not Reliability"가 보이듯 합의(반복적 성공)가 실제 신뢰성과 분리될 수 있음.

3. **[[absence-based-rollback]]과의 긴장**: 롤백이 '결여 상태(absence)로의 복원'이라면, 정답을 찾은 후의 롤백은 올바른 상태를 결여 상태로 퇴행시키는 것임. 상태 유계 증거 모델에서는 이를 "증거의 손실"로 명시적으로 타입화하여 방지해야 함.

## 결론: 전환은 필수적이다

**네, 하네스 신뢰성의 기본 단위는 '반복 횟수'에서 '상태 유계 증거와 타입화된 수정 계약'으로 전환되어야 합니다.**

그 이유는 세 가지 층위에서 정리됩니다:

1. **실증적**: "Looping Is Not Reliability"가 정답 발견 후 보존·제출 단계의 구조적 실패를 실증함
2. **이론적**: [[agent-os-semantic-gap]]이 이미 C/R의 의미론적 보존 한계를 이론적으로 예고했음
3. **구조적**: [[circular-validity-problem]]과 [[checkpoint-consensus-reduction]]이 반복 자체의 신뢰성 붕괴 메커니즘을 설명함

[[agentic-harness-engineering]]은 이제 인프라 계층(C/R 런타임)에서 **계약 계층(typed revision contracts)**으로 확장되어야 하며, [[agent-reliability-auditing]]의 감사 단위도 "몇 번 시도했는가"에서 "각 반복에서 어떤 증거가 유계로 보존되었는가"로 전환되어야 합니다. 이는 단순한 메트릭 변경이 아니라, 하네스가 에이전트의 의미론적 상태에 대해 가져야 하는 책임 모델의 근본적 재설계를 의미합니다.
