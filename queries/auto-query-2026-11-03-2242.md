## 1. 전제 검증: "토큰 생성 + KV 캐시"는 현재 서빙의 구조적 기본값

(Scepsy·Pythia·SMetric 논문은 제공된 발췌 범위 밖에 있어 링크 없이 전제로만 받아들이지만,) 현재 서빙 스택이 [[concepts/autoregressive-generation.md|autoregressive generation]]과 KV 캐시를 최적화 단위로 삼는다는 전제는 Wiki의 다음 개념들과 정합한다:

- [[concepts/attention-carried-conversational-state.md|attention carried conversational state]] — 대화·세션 상태가 어텐션(KV 캐시)에 운반된다는 관점이 "상태 = 캐시"라는 서빙 전제의 개념적 뿌리다. 서빙이 최적화하는 것은 결국 이 상태 운반체의 효율이다.
- [[entities/autocompaction.md|autocompaction]] — 컨텍스트 압축이 런타임의 핵심 연산이 된 것도 상태가 토큰/컨텍스트 형태로만 존재하기 때문이다.
- [[concepts/adaptive-inference.md|adaptive inference]] — 이 엔티티의 SpecKV 논문은 적응적 추론의 결정 차원이 "압축(KV 캐시 상태)에 반응"하는 것까지 확장되었음을 보여준다. 에이전틱 서빙의 적응성 논의조차 캐시·디코딩 파라미터를 대상으로 한다.
- [[concepts/agent-loop-as-computation.md|agent loop as computation]] · [[concepts/agent-as-harness.md|agent as harness]] — 하네스 루프가 토큰 스트림 위의 계산으로 취급되며, [[entities/agentic-harness-engineering.md|agentic harness engineering]]의 제어 코드도 토큰 생성 흐름 위에서 "언제 정책/도구를 쿼리할지"를 결정한다.

## 2. Jev 계열 결정 모델이 깨는 가정

최근 논문 흐름은 System One 실행의 단위가 토큰이 아니라 **범주적 결정**임을 보여준다:

- **Flide: Accelerating Decision Inference with Exact State Forking** — "Decision models such as Jev … providing lightweight and reliable categorical reasoning for rapid System One execution"이라 명시하고, 정확한 상태 포킹을 추론 가속의 핵심으로 삼는다.
- **DecisionRank** — decision model이 "choices or scores를 직접 예측하여 자기회귀 디코딩 지연을 회피"한다고 명시한다.
- **Jev-Mobile** ([[concepts/access-planning-gap.md|access planning gap]] 엔티티에 기록) — Jev를 모바일 GUI 에이전트의 실행기로 배치한다.

핵심은: 결정 모델의 상태는 KV 캐시가 아니며, 탐색의 원시 연산이 "다음 토큰 생성"이 아니라 **상태의 정확한 복제·분기**라는 점이다. 모델이 lightweight이기에 상태가 작고, 포킹이 경제적으로 성립하는 원시 연산이 된다.

## 3. 재정의가 필요한 근거

1. **상태 운반체의 교체** — exact forking은 값 의미론(value semantics) 스냅샷을 요구한다. KV 캐시 prefix 공유(불변 접두사 + append)와 달리 분기 가능한 전체 복사본이 필요하며, [[concepts/agent-sandbox-state-management.md|agent sandbox state management]]의 관리 대상 자체가 바뀐다는 뜻이다.
2. **추측 실행의 그레인 상승** — [[concepts/action-level-speculation.md|action level speculation]]이 예고한 "액션 수준 추측 실행"이 포킹과 결합하면, 토큰 수준 speculative decoding을 대체하는 fork-then-evaluate 탐색이 가능해진다.
3. **스케줄링 단위의 트리화** — 에이전트 요청이 선형 토큰 스트림이 아닌 분기된 상태 트리가 된다. [[concepts/aggregate-pipeline-serving.md|aggregate pipeline serving]] 관점에서도 스케줄 단위가 포크 노드로 이동해야 한다.
4. **[[concepts/autoregressive-paradigm-confinement.md|autoregressive paradigm confinement]]의 해소 경로** — Wiki가 이미 개념화한 "자기회귀 패러다임 갇힘"에 대해, 결정 모델 + 포킹은 탈출 경로다. 서빙이 토큰 생성에 묶여 있으면 이 탈출이 인프라 수준에서 막힌다.

## 4. 그러나 '대체'가 아닌 '이원화'여야 하는 근거

1. **System Two는 여전히 자기회귀적** — 계획·도구 사용·언어 생성은 토큰 생성에 머문다. [[concepts/agent-loop-as-computation.md|agent loop as computation]] 루프 안에 두 실행 모드가 혼재하므로 서빙은 두 원시 연산을 모두 노출해야 한다.
2. **라이프사이클의 결합** — DecisionRank 자체가 generative LLM에서 decision model로 지식을 이전하는 on-policy distillation이다. 훈련 시간 루프([[concepts/agent-loop-as-training-time.md|agent loop as training time]])는 토큰 기반으로 유지되므로, 서빙만 단독으로 재정의하면 훈련-서빙 상호 운용이 깨진다.
3. **[[concepts/access-planning-gap.md|access planning gap]]의 경고** — 포킹이 "전망(lookahead) 접근"을 값싸게 만들어도, 그 전망을 최적 결정으로 번역하는 것은 구조적으로 어려울 수 있다(ℓ-스텝 예지 접근과 계획 능력의 간극). 즉 상태 분기는 필요조건이지 System One 실행 품질을 담보하지 않는다.

## 5. 서빙 인프라 재설계의 구체적 함의

- **스케줄러**: 토큰 배치 → 상태 트리 스케줄링
- **캐시/메모리**: KV 캐시 페이징 → 포크 가능한 불변 스냅샷 + delta
- **하네스 API**: 제어 코드가 `fork(state) → evaluate(branches) → commit(branch)`를 명령하는 인터페이스 ([[concepts/agent-as-harness.md|agent as harness]]의 확장)
- **트레이스/감사**: 선형 [[concepts/append-only-trace-enforcement.md|append only trace enforcement]]가 트리 구조로 확장되어야 하며, exact 복제는 수치 재현성은 보장해도 분기 상태의 의미 감사는 [[concepts/agent-execution-semantic-opacity.md|agent execution semantic opacity]]·[[concepts/agent-reliability-auditing.md|agent reliability auditing]]의 새 과제가 된다
- **컴팩션**: [[entities/autocompaction.md|autocompaction]] 대상이 결정 모델 상태로도 확장되어야 한다

## 6. 새로 발견된 개념·연결 (신규 엔티티 후보)

- **state-fork-as-primitive** (신규): Flide가 원천 정의. "서빙 기본 단위" 논쟁의 앵커.
- **dual-primitive-serving** (신규): 토큰 생성(System Two) + 상태 분기(System One)의 병존 서빙. → [[concepts/agent-native-serving.md|agent native serving]], [[concepts/agent-editing-serving-stack.md|agent editing serving stack]]과 연결.
- **state-tree-scheduling** (신규): 포크 트리 단위 스케줄링.
- **기존 엔티티 간 신규 연결**:
  - Flide ↔ [[concepts/action-level-speculation.md|action level speculation]]: 포킹은 액션 수준 추측 실행의 실현 메커니즘
  - Flide ↔ [[concepts/agent-editing-world-model.md|agent editing world model]]: "예측(토큰 생성)" 대신 "편집/분기(상태 연산)"를 원시 연산으로 삼는 공통 패러다임 — 에이전트가 세계 모델을 편집하듯 서빙도 상태를 편집하는 단위로 이동
  - Jev 계열 ↔ [[concepts/attention-carried-conversational-state.md|attention carried conversational state]]: "상태 운반체"의 분리(어텐션 상태 vs 결정 모델 상태) — 이 엔티티 정의의 확장 필요
  - 결정 모델 ↔ [[concepts/action-tokenization.md|action tokenization]]: 연속 행동을 이산 토큰으로 번역하는 '표현 계약'과, 토큰 없이 범주 결정을 내리는 경로의 대비

**요약**: Wiki의 증거는 "토큰 생성 → 상태 분기"로의 **단일 대체**가 아니라, 결정 모델의 System One을 위해 **상태 분기를 제1급 원시 연산으로 승격**하되 자기회귀 생성과 병렬 노출하는 방향 — 즉 서빙 인프라의 기본 단위 재정의를 지지하되, 그 형태는 이원화여야 함을 보여준다.

## 핵심 통찰

System One 서빙의 기본 단위는 '토큰 생성'에서 '상태 분기'로 이동해야 하지만, System Two 자기회귀 추론과 토큰 기반 훈련 루프와의 공존 때문에 서빙은 전면 대체가 아닌 이원 원시 연산(dual-primitive)으로 재정의되어야 한다.
