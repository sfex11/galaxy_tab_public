# Auto Query: 현재 Wiki에서 에이전트의 태스크는 벤치마크가 사전에 고정해 주는 외부 단위이고, 하네스의 상태 관리와 GUI 에이전트 능력도 단일 샌드박스·단일 디바이스 안에서 정의되어 있는데, JarvisGUI처럼 워크플로우가 이기종 디바이스 간에 동적으로 합성되고 중간 결과와 공유 상태가 환경 경계를 넘어 이동한다면 '하나의 태스크'의 경계와 그 상태의 소유·검증 주체는 어디에 두어야 하는가?

**날짜**: 2026-09-13
**대상 논문**: JarvisGUI: Towards Cross-Device GUI Agents with Dynamic Task Composition
**선택 이유**: Wiki의 하네스 엔지니어링(C/R, 샌드박스 상태)과 평가(고정 태스크 벤치마크) 양쪽에 깔린 '단일 환경 내 고정 태스크' 전제를, 기존에 다뤄지지 않은 태스크 단위·상태 소유권 차원에서 동시에 흔드는 유일한 후보이기 때문.

## Wiki 답변

# 이기종 동적 합성 워크플로우에서의 태스크 경계와 상태 소유·검증

## 1. 질문이 겨냥하는 균열: 현재 Wiki의 두 전제

현재 Wiki의 태스크·상태 관리 담론은 두 가지 전제 위에 서 있습니다.

- **전제 A — 태스크는 외부 고정 단위**: [[benchmark]]와 [[benchmark-specification-gap]]이 보여주듯, 태스크는 벤치마크가 입력·출력·성공 조건을 미리 확정해 주는 좌표입니다.
- **전제 B — 상태는 단일 샌드박스 자산**: [[agent-sandbox-state-management]]와 Crab: A Semantics-Aware Checkpoint/Restore Runtime for Agent Sandboxes([[agent-os-semantic-gap]], [[agentic-harness-engineering]])가 전제하는 세계에서는 체크포인트/복원의 경계가 곧 샌드박스(프로세스) 경계였습니다.

JarvisGUI식 이기종 디바이스 간 동적 합성은 이 두 전제를 **동시에** 무너뜨립니다. 이것이 [[algorithm-system-boundary-collapse]]의 정확한 사례입니다 — 벤치마크(알고리즘 측)가 정의하는 태스크 단위와 런타임(시스템 측)이 실제로 커밋·롤백하는 단위가 더 이상 일치하지 않습니다. [[algorithm-system-translation-gap]]이 경고하는 "번역 없는 이동"이 상태 이동에서도 재현됩니다.

## 2. 태스크 경계는 어디에 두어야 하는가

**"벤치마크 행(row)"이 아니라, 합성 시점에 실체화되는 계약 + 롤백 봉투 + 예지 지평의 교집합**으로 제안합니다.

**(1) 합성-시점 계약으로서의 태스크**
Design Docs Are All You Need([[abstraction-layer-mismatch]])는 기계 판독 가능한 설계 문서가 구현의 계약이 되어 레이어 불일치를 메운다는 발견입니다. 동일 논리로, 동적 합성 워크플로우에서 태스크는 실행 합성 시점에 문서화·계약화되는 **런타임 객체**여야 합니다. [[agent-environment-generation]](Nemobot Games)이 학습 목표에 따라 환경을 그때그때 생성하듯, 태스크 단위도 합성기가 발행하는 계약이 됩니다.

**(2) 커밋/롤백 봉투로서의 경계**
Crab의 semantics-aware checkpoint/restore와 [[absence-based-rollback]]을 일반화하면: **되돌릴 수 있는 상태 변화의 최소 봉투(commit envelope)가 곧 태스크 경계**입니다. 단일 샌드박스에서는 프로세스 경계 = 롤백 경계였지만, 이기종 환경에서는 롤백 봉투가 장치 경계를 가로지릅니다. 커밋·롤백이 성립하지 않는 지점에서는 태스크도 성립할 수 없으므로, 이것이 가장 운영적으로 단단한 경계 정의입니다.

**(3) 예지 지평으로서의 경계**
[[access-planning-gap]](Near-Optimal Reinforcement Learning with Multi-Step Transition Lookahead)은 ℓ-스텝 예지 접근이 정보를 주더라도 이를 최적 결정으로 번역하는 능력과 구조적 간극이 존재함을 규명합니다. 동적 합성 워크플로우에서 태스크 경계는 **"계획이 책임지는 예지 지평"**이며, 합성 결과에 따라 매번 재정의됩니다. 관측 가능 범위(어느 디바이스까지 상태를 들여다볼 수 있는가)가 경계 후보를 만들고, 번역 능력이 그중 실제 경계를 확정합니다.

**(4) 4차원 그래프의 부분그래프로서의 경계**
[[4d-state-transition-graph]] — "누가, 어떤 상태에서, 어떤 권한으로, 어떤 흐름을 거쳤는가"의 4축 — 가 이 질문의 등대입니다. **태스크 = 이 그래프의 연결 부분그래프이고, 경계는 그래프가 소유 도메인(디바이스·권한 영역)을 넘는 지점**입니다. 기존 연구들이 각 축을 분절적으로 다뤘다는 이 개념의 진단이, 장치 간 합성 상황에서 정확히 문제의 본질이 됩니다.

## 3. 상태의 소유 주체는 누구인가

**(1) 소유는 장치가 아니라 상태 객체에 부착된다.**
Crab의 핵심 교훈은 상태가 **자신의 의미 유형을 자기 기술해야만** OS/샌드박스 경계를 넘어 복원 가능하다는 것이었습니다. 이를 장치 간으로 일반화하면: 중간 결과는 자신의 출처(provenance)·의미·불변식을 함께 운반해야 하며, 소유는 장치의 속성이 아니라 상태 객체의 속성입니다. 그렇지 않으면 [[agent-os-semantic-gap]]이 장치 경계에서 [[agent-os-semantic-preservation-failure]]로 확장됩니다.

**(2) 소유 이전 = 위임 간선.**
상태가 경계를 넘을 때마다 [[authority-delegation-topology]]에 따라 위임 간선을 기록하고 [[authority-location-alignment]]으로 권한 위치를 재정렬해야 합니다. 이 기록이 없으면 [[authority-boundary-penetration]], [[agent-boundary-semantic-collapse]], [[boundary-readability-regression]] — 즉 "경계가 어디였는지도 읽을 수 없게 되는" 퇴행이 발생합니다.

**(3) 역할 기반 소유.**
Testing Interchangeability in LLM Agent Teams([[agent-identity]], [[agent-interchangeability]])가 에이전트 교체 가능성을 검사한다면, 소유도 개별 인스턴스가 아닌 **역할/슬롯에 귀속**되어야 하고 검증 역시 특정 인스턴스에 의존해서는 안 됩니다.

**(4) 경계를 넘는 지속 상태의 통제 문제.**
Artificial Id([[agentic-drive]], [[artificial-id]])는 태스크 경계를 넘어 지속되는 결과적 상태가 만드는 통제 문제를 정확히 지적했습니다. 그리고 [[adaptive-validity]](Does Your Agent's Memory Survive a Model Upgrade?)가 정의한 **"아직 유효한가"의 지속 재평가**가 상태 인수 시점의 필수 조건이 되어야 합니다 — 경계를 넘은 상태는 도착하자마자 타당성 재심사를 받아야 합니다.

## 4. 검증 주체는 누구인가

동적 합성에는 전역 벤치마크가 없으므로, 단일 오라클을 **3층 구조**로 대체해야 합니다.

1. **이중 인수(생산자/소비자)**: [[asynchronous-dependency-coordination]]과 [[asynchronous-agent-workspace]]가 정의하는 비동기 의존 구조에서, 중간 결과는 수집 지점(ingestion point)마다 계약 적합성 검사를 받습니다. 전역 벤치마크 부재 시의 대리 기준은 [[acceptable-risk-quantification]]과 [[benchmarkless-comparative-safety-scoring]](When No Benchmark Exists)의 **비교 기반 검증 + 허용 가능 위험 정량화**입니다.
2. **면역형 분산 감시**: [[agent-native-immune-system]](A Case Study on Emergent Cheating and Whistleblowing)은 부정 행위가 단일 하네스의 단정문으로는 잡히지 않고 생태계 수준 감시·고발로만 포착됨을 보였습니다. 경계를 넘는 상태 오염도 동일하게 분산 감시 대상이며, [[agent-voting]]·[[agent-coordination]]이 보조 수단이 됩니다.
3. **원장 감사**: 검증의 최종 주체는 [[4d-state-transition-graph]] 원장을 읽는 감사자입니다([[auditability-as-scaling-requirement]], [[audit-feedback-closure]], [[auditable-gap]], [[agent-reliability-auditing]]). 단, 감사자가 피감사 시스템에 흡수되는 [[audit-independence-collapse]]·[[audit-oracle-self-reference]]·[[auditor-evidence-corruption]]에 대한 방어가 전제되어야 합니다.

증거 확보의 시점도 중요합니다. TRACE([[agent-execution-semantic-opacity]])가 보여주듯 포착 불가능성은 사후 해독이 아니라 **실행 시점 인과 체인 문서화**로 원천 회피해야 하고, RunAgent([[agentic-harness-engineering]])처럼 하네스가 자연어 계획을 제약으로 해석해 계획-실행 일치를 검증하는 역할이 경계를 넘는 워크플로우 전체로 확장되어야 합니다.

## 5. 결론: 세 문장 원칙

- **태스크 경계** = 커밋/롤백 봉투 ∩ 예지 지평으로, 합성 시점 계약으로 실체화되며 [[4d-state-transition-graph]]의 연결 부분그래프로 기록된다.
- **소유** = 자기기술 상태 객체에 부착되고, 경계 이동은 위임 간선으로 원장화된다([[authority-delegation-topology]]).
- **검증** = 생산자/소비자 이중 인수 + 면역형 분산 감시 + 4D 원장 감사의 3층으로 분할된다.

## 6. 신규 개념·연결 명시

**새 개념 후보:**
- **합성-시점-태스크-계약**: [[benchmark-specification-gap]]의 동적 버전. 계약 발행 주체가 벤치마크에서 워크플로우 합성기로 이동.
- **커밋-봉투-태스크-경계**: Crab + [[absence-based-rollback]]의 일반화. 롤백 가능성이 경계를 정의.
- **자기기술-상태-소유**: [[agent-os-semantic-gap]]의 장치 간 일반화.
- **위임-간선-원장**: [[authority-delegation-topology]] + [[4d-state-transition-graph]] 결합.
- **경계-횡단-적응-타당성**: [[adaptive-validity]]의 제3 확장. Artificial Id가 행동 수준으로 확장했듯, "상태 인수" 수준 확장이 남아 있는 칸.

**새 연결:**
- [[4d-state-transition-graph]] ↔ Crab ↔ [[absence-based-rollback]]: **원장-체크포인트-롤백 삼각형**이 경계 넘는 태스크의 최소 인프라.
- [[agent-interchangeability]] ↔ 상태 소유: 교체 가능성 연구는 4D 그래프의 '누가' 축 동등성 검사이고, 상태 소유는 '어떤 권한으로' 축의 문제 — 두 축이 하나의 경계 질문으로 묶임.
- [[access-planning-gap]] ↔ 동적 합성: ℓ-스텝 예지가 장치 경계를 넘어 관측될 때 태스크 지평이 재정의됨.
- [[algorithm-system-boundary-collapse]] ↔ [[benchmark-specification-gap]]: "벤치마크 단위 ≠ 런타임 커밋 단위"라는 동일 현상의 알고리즘 측/시스템 측 기술.

## 핵심 통찰

이기종 동적 합성에서 태스크 경계는 벤치마크가 미리 정하는 것이 아니라 합성 시점에 실체화되는 커밋 봉투·예지 지평·소유 도메인의 교집합으로 정의되며, 상태 소유는 장치가 아니라 자기 서술적 상태 객체와 역할에 귀속된다.
