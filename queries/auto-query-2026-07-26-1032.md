## 1. 두 축이 실제로 같은 현상을 서로 다른 이름으로 부르고 있는 증거

### [[concepts/aggregate-pipeline-serving.md|aggregate pipeline serving]]이 이미 "컨텍스트 팽창"을 비용 축의 본질로 진단하고 있다

Tool Attention 논문에 따르면:

> "다중 서버 MCP 배포에서 파이프라인 전체의 레이턴시 병목이 개별 LLM 호출이 아닌 **스키마 축적**에 의해 결정됨"

여기서 "스키마 축적"은 도구가 추가될수록 컨텍스트에 누적되는 메타정보의 양을 말한다. 즉, 비용 축이 스스로 "컨텍스트 팽창이 병목이다"라고 진단하고 있다. 그런데 이 동일한 스키마 축적은 메모리 축에서도 "검색 대상이 늘어나 정확도가 저하되는 원인"으로 기술될 수 있다. **동일한 물리적 현상이 두 축에서 각각 다른 병명으로 등록된 셈이다.**

### [[concepts/algorithm-system-translation-gap.md|algorithm system translation gap]]이 두 축의 경계를 무너뜨리는 사례를 제공한다

Crab 논문의 핵심 발견:

> "에이전트의 의미론적 의존 그래프(어떤 상태에 의존하는가)를 OS의 체크포인트 메커니즘(전체 스냅샷)으로 번역할 때 발생하는 비효율이 간극의 본질이다."

이것은 무엇인가? 에이전트가 **어떤 상태를 기억해야 하는가**(메모리 문제)와 **그 상태를 어떻게 효율적으로 저장/복원하는가**(비용 문제)가 번역 과정에서 동일한 비효율로 현현한다는 뜻이다. Crab은 이를 [[entities/agentic-harness-engineering.md|agentic harness engineering]]의 영역으로 규정하는데, 이는 하네스라는 단일 계층에서 메모리 의미론과 실행 비용이 동시에 결정됨을 보여준다.

## 2. 분리가 은폐하는 구조적 문제

### 인과관계의 역전 위험

두 축을 독립적으로 최적화하면 다음과 같은 역전이 발생할 수 있다:

- **메모리 축 최적화**: 더 많은 정보를 컨텍스트에 적재하여 "검색 정확도"를 높인다 → 컨텍스트 팽창 → 비용 폭증
- **비용 축 최적화**: 스키마를 적극적으로 잘라내어 "레이턴시"를 줄인다 → 에이전트가 호출 가능한 도구를 인지하지 못함 → 메모리/지식의 실질적 손실

즉, 각 축의 "최적해"가 상대 축의 "최악해"가 되는 구조다. 이는 두 문제가 독립이 아니라 ** Trade-off 관계의 양면**임을 의미한다.

### [[entities/agora-opt.md|agora opt]]이 암시하는 통합적 관점

Agora-Opt는 "메모리 강화 에이전트의 분산적 토론 구조"를 통해 다중 에이전트 정렬을 달성한다. 여기서 메모리(토론 기록, 합의 상태)와 비용(토론 라운드 수, 참여 에이전트 수)은 분리 불가능하게 얽혀 있다. 메모리를 풍부하게 하면 토론이 길어지고 비용이 증가하며, 비용을 줄이면 메모리가 빈약해져 정렬 품질이 저하된다. Agora-Opt는 이를 [[concepts/adaptive-bottleneck-migration.md|adaptive bottleneck migration]]의 관점에서 — 병목이 런타임 메모리와 연산 비용 사이를 이동한다는 관점에서 — 암묵적으로 취급하고 있다.

## 3. 그럼에도 분리가 관행적으로 유지되는 이유 (그리고 그 한계)

### 공학적 분업의 관성

[[entities/agentic-harness-engineering.md|agentic harness engineering]]의 정의를 보면:

> "C/R 런타임이 하네스의 핵심 구성요소(결함 내성·롤백·분기)를 직접 구현하는 인프라 계층으로, 하네스 엔지니어링의 범위를 애플리케이션 로직에서 실행 환경까지 확장함"

하네스 엔지니어링이 "애플리케이션 로직"(메모리 설계)과 "실행 환경"(비용 최적화)을 하나의 계층으로 통합하려는 움직임이 있음에도, 기존 연구는 여전히 RAG 파이프라인 팀과 서빙 인프라 팀으로 분업되어 있다. 이 조직적 분업이 개념적 분리를 강화한다.

### 하지만 이 분리는 점점 부서지고 있다

Wiki의 [[concepts/agent-native-serving.md|agent native serving]] 슬러그가 존재한다는 것 자체가, 에이전트 워크로드에 특화된 서빙이 기존 LLM 서빙과 다른 최적화 축을 요구한다는 인식의 반영이다. 에이전트 네이티브 서빙은 본질적으로 "에이전트의 상태 관리(메모리)"와 "추론 비용(서빙)"을 동시에 고려해야 하는 문제다.

## 4. 새로운 연결로서의 제안: 통합 진단 프레임워크

Wiki의 기존 슬러그들을 조합하면, 다음과 같은 통합 진단이 가능해진다:

```
컨텍스트 팽창 (공통 원인)
├── 메모리 축 현상: 검색 정확도 저하, 의미론적 충돌
│   └── 관련: [[entities/adema.md|adema]], [[entities/agora-opt.md|agora opt]], [[concepts/agent-os-semantic-gap.md|agent os semantic gap]]
├── 비용 축 현상: 레이턴시 병목, 스키마 축적
│   └── 관련: [[concepts/aggregate-pipeline-serving.md|aggregate pipeline serving]], [[concepts/agent-native-serving.md|agent native serving]]
└── 번역 간극 (두 축이 만나는 지점)
    └── 관련: [[concepts/algorithm-system-translation-gap.md|algorithm system translation gap]], [[entities/agentic-harness-engineering.md|agentic harness engineering]]
```

핵심은 **[[concepts/algorithm-system-translation-gap.md|algorithm system translation gap]]**이 두 축의 실제 교차점이라는 것이다. 에이전트가 "의미론적으로 무엇을 기억해야 하는지"를 결정하는 시점과, 시스템이 "물리적으로 얼마를 전송/저장해야 하는지"를 결정하는 시점 사이의 간극이 바로 컨텍스트 팽창이 양 축에 독립적이 아닌 **공유된 문제**로 나타나는 지점이다.

## 5. 주의사항

질문에서 언급된 **WorldDB**와 **MeMo**는 현재 Wiki 슬러그 목록에 존재하지 않는다. 따라서 이 두 엔티티와 [[entities/adema.md|adema]] 간의 비교 분석은 현재 Wiki 지식으로는 직접 수행할 수 없다. 만약 이 둘이 각각 "지속적 상태 저장"과 "에피소드 메모리 압축"을 다룬다면, 위 통합 프레임워크에서 메모리 축의 하위 분류로 자연스럽게 통합될 수 있을 것이다.

## 결론

질문의 진단은 정확하다. Wiki의 논문들 — 특히 [[concepts/aggregate-pipeline-serving.md|aggregate pipeline serving]]의 "스키마 축적" 진단과 [[concepts/algorithm-system-translation-gap.md|algorithm system translation gap]]의 "의미론적 의존 그래프 ↔ 전체 스냅샷" 불일치 — 은 컨텍스트 팽창이 두 축의 **공통 인과 원인**임을 이미 증거하고 있다. 두 축을 독립 최적화 축으로 분리하는 것은 각 축의 국소 최적해가 상대 축을 악화시키는 역설을 낳으며, [[entities/agentic-harness-engineering.md|agentic harness engineering]]과 [[concepts/agent-native-serving.md|agent native serving]]이 시사하는 바와 같이 통합 계층에서 동시에 해결해야 하는 문제다. 새로이 식별된 연결로서 **[[concepts/algorithm-system-translation-gap.md|algorithm system translation gap]]을 두 축의 교차점이자 통합 진단의 핵심 매개체**로 제안한다.

## 핵심 통찰

컨텍스트 팽창은 메모리 축과 비용 축의 독립적 문제가 아니라, algorithm-system-translation-gap에서 만나는 공유된 문제의 양면적 현현이다.
