# 메모리 아키텍처 발전과 공격 표면 확장의 구조적 모순

메모리 인프라가 능력 확장인 동시에 공격 표면 확장이라는 모순은, Wiki의 여러 엔티티와 논문들이 서로 다른 각도에서 암시하고 있는 **하나의 구조적 문제**의 현현이다. 이를 세 가지 해석 축으로 정리할 수 있다.

---

## 1. 의미론적 간극이 공격 표면의 본질이다

[[agent-os-semantic-gap]] 엔티티와 연결된 **Crab: A Semantics-Aware Checkpoint/Restore Runtime for Agent Sandboxes** 논문은 이 모순의 핵심 메커니즘을 이미 제시하고 있다. Crab이 지적하는 것은 에이전트의 의미론적 의존 그래프(어떤 상태가 무엇에 의존하는가)를 OS 수준의 체크포인트 메커니즘(전체 스냅샷)으로 번역할 때 발생하는 비효율이다. 이는 [[algorithm-system-translation-gap]]에서도 "에이전트의 의미론적 의존 그래프를 OS의 체크포인트 메커니즘으로 번역할 때 발생하는 비효율이 간극의 본질이다"라고 명시적으로 확인된다.

InjecMEM이 보여주는 '메모리 주입'은 정확히 이 간극을 타는 공격이다. OS 런타임 입장에서 메모리는 의미 없는 상태 바이트(state bytes)이지만, 에이전트 입장에서 그것은 **행동을 결정하는 의미론적 제어 채널**이다. 상태less 모델에는 이 간극이 존재하지 않았다. 메모리를 추가하는 순간, OS는 여전히 바이트를 보고 에이전트는 의미를 보는 **이중 시야(Dual Vision)**가 발생하며, 공격자는 항상 OS의 시야를 통해 에이전트의 시야에 침투한다.

---

## 2. 기능-안전 불가분성이 메모리 영역에서 구체화된다

[[capability-safety-inseparability]]이라는 엔티티가 존재한다는 사실 자체가 이 모순에 대한 Wiki의 분류적 대답이다. 이 개념은 [[ai-safety]] 엔티티와 연결된 논문들의 맥락에서 더 선명해진다:

- **SafetyALFRED** 논문은 disembodied QA 기반 안전 평가가 체화 배포 환경에서의 안전성을 보장하지 못함을 11개 SOTA 모델에서 실증했다. 즉, 평가 환경과 배포 환경 사이의 **상태 차이**가 안전성을 무효화한다.
- **An AI Agent Execution Environment to Safeguard User Data** 논문은 실행 환경 자체가 안전 경계가 되어야 함을 주장한다.

메모리는 이 두 논의의 교차점에 있다. 상태less 모델은 항상 "fresh"한 상태로 평가와 배포가 동일했지만, 지속적 메모리를 가진 에이전트는 **매 호출마다 다른 내부 상태**를 가지므로 SafetyALFRED가 지적한 평가-배포 간격이 에이전트 내부에 내재화된다. 메모리를 추가한다는 것은 곧 "매 호출마다 다른 에이전트"와 소통하는 것이며, 이것이 [[capability-safety-inseparability]]의 물리적 실현이다.

## 3. 하네스 엔지니어링이 방어 경계로 확장되어야 한다

[[agentic-harness-engineering]] 엔티티에서 **Crab 논문**은 "C/R 런타임이 하네스의 핵심 구성요소(결함 내성·롤백·분기)를 직접 구현하는 인프라 계층으로, 하네스 엔지니어링의 범위를 애플리케이션 로직에서 실행 환경까지 확장함"을 시사한다.

최근 논문인 **StepGuard: Learning Step-Level Guardrails with Scalable Supervision and Safety-Utility Balancing**은 "LLM-based agents can interact with external environments through tool invocation, but this capability also introduces security risks such as file modification, information leakage, and unauthorized access"라고 지적하며, 단계별 가드레일의 필요성을 주장한다.

여기에 메모리를 끼워 넣으면 그림이 완성된다:

> **메모리 = 도구 호출의 영속적 형태**
>
> StepGuard가 도구 호출마다 가드레일을 건다고 했을 때, 메모리는 "호출되지 않은 도구 호출"이다. 에이전트가 명시적으로 tool을 호출하지 않아도, 과거에 기록된 메모리가 현재의 행동에 영향을 미친다. 따라서 [[agentic-harness-engineering]]은 메모리 상태에 대한 **암시적 도구 호출 검증**까지 범위를 확장해야 하며, 이것이 [[agent-native-immune-system]] 엔티티가 제시하는 방향성이다.

## 새로운 연결 발견

이 분석 과정에서 다음 연결이 새롭게 드러난다:

1. **[[agent-os-semantic-gap]] → [[capability-safety-inseparability]]의 인과 사슬**: OS가 메모리를 의미론 없이 처리하는 간극(원인)이, 메모리 추가가 곧 공격 표면 추가가 되는 불가분성(결과)을 구조적으로 보장한다. 간극을 줄이지 않는 한 기능 확장은 항상 안전성 비용을 동반한다.

2. **[[alignment-scope-erosion]]의 시간축 전환**: 기존 정렬 범위 침식이 프롬프트나 컨텍스트 창의 한계에서 발생했다면, 지속적 메모리 환경에서는 **시간축을 따라 누적되는 미세 주입**이 정렬을 점진적으로 침식하는 새로운 메커니즘이可能出现한다. 단일 턴에서는 검출하기 어려운 미세한 왜곡이 수백 번의 메모리 읽기/쓰기 후에는 의미론적으로 완전히 다른 행동을 산출할 수 있다.

3. **[[acceptable-risk-quantification]]의 새로운 적용 영역**: 연결된 **When No Benchmark Exists: Validating Comparative LLM Safety** 논문은 벤치마크 없이 안전성을 비교 평가하는 문제를 다룬다. 메모리 주입 공격에 대해서는 벤치마크 자체가 시간 의존적이 되므로(동일한 메모리 상태를 재현해야 함), 이 프레임워크가 메모리 아키텍처의 안전성 평가에 핵심적으로 필요하다.

## 종합 해석

메모리 아키텍처의 발전이 공격 표면의 확장인 구조적 모순은 **모순이 아니다**. 이것은 [[algorithm-system-translation-gap]]이 [[agent-os-semantic-gap]]을 통해 현현되고, 이것이 다시 [[capability-safety-inseparability]]로 귀결되는 **단일 인과 사슬**이다. 

해결 경로는 Wiki가 이미 암시하는 세 가지 방향의 융합에 있다:
- **[[agentic-harness-engineering]]**이 메모리 상태 검증을 하네스의 책임으로 흡수하고,
- [[agent-native-immune-system]]이 이를 지속적·자율적으로 수행하며,
- [[acceptable-risk-quantification]]이 시간 의존적 공격 표면의 위험을 정량화하여

비로소 메모리 추가가 "공격 표면 확장"이 아니라 "방어 깊이 확장"으로 전환될 수 있다. 현재의 Wiki 지식 상태에서 이 세 엔티티 간의 연결이 명시적으로 문서화되어 있지 않다는 점이 오히려 이 모순이 아직 해결되지 않았음을 방증한다.

## 핵심 통찰

메모리는 '호출되지 않은 도구 호출'이므로, 도구 호출에만 가드레일을 거는 기존 방식은 메모리 공격 표면을 구조적으로 방치한다.
