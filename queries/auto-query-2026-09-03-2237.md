## 1. 결정적 실증: CordisBench가 이미 이 축을 벤치마크화하고 있다

최근 논문 목록의 **"CordisBench: Can Language Models Reason About Component Lifecycles in Dynamic Agent Harnesses?"**가 정확히 이 질문의 무대다. 초록에 따르면 동적 에이전트 하네스는 "언어 모델이 자신의 실행을 형성하는 소프트웨어를 변경하도록" 허용하며, 이 유연성은 "로컬 플러그인 변경이 의존성을 통해 전파될 수 있는" **새로운 추론 부담(reasoning burden)** 을 만든다.

핵심은 이 논문의 프레이밍 자체다. 벤치마크 제목이 "변경을 *수행*하는가"가 아니라 "컴포넌트 라이프사이클을 *추론*하는가"로 되어 있다는 것 — 즉 변경 수행 능력과 파급 추론 능력이 **이미 별도의 평가 축으로 분리**되어 있으며, 전용 벤치마크의 존재는 그것이 독립적 검증 대상으로 인정받기 시작했다는 사실적 증거다.

## 2. 왜 두 능력이 분리되어야 하는가 — Wiki의 구조적 근거

**(a) 국소 타당성 ≠ 시스템 타당성**

[[aggregate-pipeline-serving]]의 Tool Attention 논문(2026-04-26 노트)은 다중 서버 MCP 배포에서 "파이프라인 전체의 레이턴시 병목이 개별 LLM 호출이 아닌 **스키마 축적**에 의해 결정됨"을 보였다. 이는 시스템 차원의 속성이 구성요소의 국소 속성이 아니라 그 *누적·구성*에서 창발한다는 구조적 사실이다. 플러그인 변경의 국소적 성공(로드 성공, 로컬 테스트 통과)이 파급 효과에 대한 정보를 거의 주지 않는 것과 동형의 논리이며, [[bottleneck-misattribution]]이 지적하는 "병목의 잘못된 귀속" 오류가 변경 검증에서도 재현될 위험이 있다.

**(b) 하네스의 안전망 자체가 변경 대상이 되는 재귀성**

Crab 논문에 대한 두 노트가 핵심 증거다:

- [[agentic-harness-engineering]](2026-05-03): "C/R 런타임이 하네스의 핵심 구성요소(결함 내성·롤백·분기)를 직접 구현하는 인프라 계층으로, 하네스 엔지니어링의 범위를 애플리케이션 로직에서 실행 환경까지 확장"
- [[algorithm-system-translation-gap]](2026-05-02): "에이전트의 **의미론적 의존 그래프**(어떤 상태에 의존하는가)를 OS의 체크포인트 메커니즘(전체 스냅샷)으로 번역할 때 발생하는 비효율이 간극의 본질"

동적 하네스에서 에이전트가 컴포넌트를 바꾸면, Crab류 C/R 런타임이 롤백·분기의 근거로 삼는 **그 의존 그래프 자체가 에이전트에 의해 재작성된다**. 검증 인프라가 검증 대상 내부로 들어오는 재귀 구조이며, 롤백이 여전히 "안전망"으로 기능하려면 변경 전후의 의존 구조 변화를 정확히 기술하는 능력 — 곧 라이프사이클 파급 추론 — 이 전제되어야 한다. 이 번역과 상태 정합성의 무대는 [[agent-os-semantic-gap]]과 [[agent-sandbox-state-management]]이다.

**(c) 자기 진화의 층위가 다르다**

SkillOS·MOSS·WikiSkill류 자기 진화는 스킬·소스 아티팩트 축적을 통한 **응용층** 확장이고, 동적 하네스 수정은 실행 기반(substrate) 자체의 변경이다. [[bilevel-self-evolution]]이 시사하는 다층 진화 관점에서 하네스 수정은 한층 아래의 진화로서 파급 범위가 넓고 되돌리기 어렵다. 한 층의 검증("스킬이 동작한다")이 다른 층의 파급("의존 컴포넌트가 오염된다")을 보장하지 못한다는 것은 [[abstraction-layer-mismatch]]의 문제다.

## 3. 새로운 검증 대상의 구체적 분해

제안된 능력은 최소 네 개의 하위 검증 항목으로 나뉜다:

1. **의존성 전파 예측** — 변경이 어떤 컴포넌트·상태에 닿는가. [[algebraic-taint-confinement]]류의 형식적 전파 추적, 그리고 RunAgent([[agentic-language]], [[agentic-harness-engineering]])가 보여주는 제약 기반 계획 해석 경로에 의존·정리(cleanup) 계약을 제약으로 인코딩하는 방식이 접점이 된다.
2. **cleanup 의무 추론** — 제거·교체 후 잔존 상태의 정합성. 미이행된 cleanup은 고아 상태(stale 스키마, 누수)로 귀결되는데, Tool Attention의 "스키마 축적이 병목" 발견은 잔존物이 시스템 성능을 좌우함을 이미 보여준다.
3. **인증 연속성 추론** — 변경 후 어떤 사전 보장이 생존하는가. [[certification-monitoring-discontinuity]]가 다루는 "인증된 상태와 런타임 상태의 단절"의 범위를 아는 것이 곧 파급 추론이다.
4. **수용 가능 변경 위험의 정량화** — 파급을 사전에 완전히 예측할 수 없을 때의 임계값 설정. [[acceptable-risk-quantification]]과 그 근간 논문 *When No Benchmark Exists*(벤치마크 부재 시 비교 검증 방법론), [[ai-risk-regulation]]의 인증 가능성 번역이 방법론적 뼈대를 제공한다.

## 5. 새로 발견된 개념·연결 (Wiki 등록 제안)

- **change-lifecycle-reasoning (신규 개념)**: 변경 수행과 분리된, 의존성 전파·cleanup·인증 연속성 추론 능력. CordisBench가 최초 벤치마크, Crab이 인프라 측 전제 조건.
- **harness-self-modification reflexivity (신규 개념)**: 검증 인프라(C/R) 자체가 변경 대상에 포함되는 재귀성. "변경 불가 코어(freeze zone)" 또는 불변 조건의 필요성을 시사.
- **기존 엔티티 간 신규 연결**:
  - [[aggregate-pipeline-serving]] ↔ 하네스 수정: 국소 변경의 창발적 시스템 효과라는 동형 구조
  - [[adaptive-inference]] ↔ 파급 추론: SpecKV(2026-05-05)가 제시한 "압축이라는 **내부 시스템 상태**에 반응하는 적응"은 파급 추론의 전조 — 적응 대상이 상태에서 시스템 구성으로 확장되는 계보
  - 최근 논문 *"Adaptive Critical Token-Aware Retrieval for Repository-Level Code Generation"* ↔ 동적 하네스: 자기 런타임에 대한 컴포넌트 수정은 " live 저장소를 대상으로 하는 저장소 수준 코드 생성"으로 볼 수 있으며, 저장소 일관성 추론이 곧 파급 추론의 한 형태
  - [[behavior-infrastructure-dual-cost-model]]: 변경 비용을 행동 변화와 인프라 변화로 이중 계상해야 파급 추론의 평가 설계가 가능

## 6. 유보 조건

- 이것이 **모델 일반 능력**(CordisBench의 입장)인지 **하네스 설계 속성**(Crab의 입장)인지는 열려 있다. 실용적 답은 이중화이며, 어느 쪽에 검증 책임을 배분할지가 후속 연구 과제다.
- 벤치마크의 외적 타당성: 합성 의존성 그래프에서의 추론이 실제 런타임 전파로 전이하는지는 [[benchmark-specification-gap]]의 관점에서 별도 검증이 필요하다.

**결론**: 그렇다. 변경 수행 능력과 라이프사이클 파급 추론 능력은 분석 단위自가 다르고(국소 vs 창발), 검증 인프라의 건전성 조건이며(재귀성), 진화 층위가 다르다(응용 vs 기반). 그리고 이 Wiki는 이미 그 분리를 CordisBench(능력 측)와 Crab(인프라 측)의 쌍으로 형상화하기 시작한 상태다.

## 핵심 통찰

변경 수행 능력과 변경 파급 추론 능력은 이미 CordisBench를 통해 별도 평가 축으로 분리되고 있으며, 안전망의 근거(의존 그래프) 자체가 에이전트에 의해 재작성되는 재귀 구조 때문에 롤백이 안전망으로 기능하려면 라이프사이클 파급 추론이 필수 전제다.
