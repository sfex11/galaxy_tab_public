## 1. 의미론적 상태 관리의 단절: 학습된 추론 의존성 vs. OS 수준 스냅샷

훈련 시 에이전트는 자신의 추론 과정이 어떤 상태에 의존하는지를 **암묵적으로** 학습합니다. 그러나 배포 시 하네스가 제공하는 체크포인트/복원(C/R) 메커니즘은 이를 OS 수준의 전체 스냅샷으로 번역합니다.

Wiki의 [[algorithm-system-translation-gap]]이 Crab 논문을 통해 구체화한 바와 같습니다:

> "에이전트의 의미론적 의존 그래프(어떤 상태에 의존하는가)를 OS의 체크포인트 메커니즘(전체 스냅샷)으로 번역할 때 발생하는 비효율이 간극의 본질이다."

하네스 없이 학습한 에이전트는 롤백·분기 같은 하네스 고유 기능을 활용하는 법을 학습한 적이 없습니다. [[agentic-harness-engineering]]이 Crab을 통해 시사한 대로, C/R 런타임이 "결함 내성·롤백·분기를 직접 구현하는 인프라 계층"이라면, 이 기능들을 **훈련 불가능한 블랙박스**로 두는 것은 에이전트가 자신의 실패 복구 전략을 하네스의 의미론과 정렬할 수 없음을 의미합니다.

**제한 양상**: 에이전트는 롤백 후 재시도 시 이전 추론 경로와의 의미론적 연속성을 유지하지 못하고, 마치 처음부터 시작하는 것처럼 비효율적인 재추론을 수행합니다.

## 2. 파이프라인 서빙 병목과 도구 사용 패턴의 왜곡

하네스는 단순한 LLM 호출 래퍼가 아닙니다. [[aggregate-pipeline-serving]]이 Tool Attention 논문을 통해 밝힌 것처럼:

> "다중 서버 MCP 배포에서 파이프라인 전체의 레이턴시 병목이 개별 LLM 호출이 아닌 스키마 축적에 의해 결정됨"

훈련 시 에이전트는 도구 스키마가 즉시 제공되는 환경에서 학습하지만, 하네스 배포 시에는 스키마가 지연적으로 축적되는 파이프라인을 거칩니다. 이로 인해:

- 에이전트가 훈련 시 학습한 **도구 선택 타이밍**이 하네스 내에서는 suboptimal이 됩니다
- 스키마가 아직 로드되지 않은 도구를 에이전트가 호출하려 할 때 [[blind-tool-invocation]]이 발생할 가능성이 증가합니다
- [[adaptive-inference]]에서 SpecKV가 보여준 '내부 시스템 상태에 반응하는 적응'과 유사하게, 하네스의 스키마 축적 상태라는 **외부 인프라 상태**에 적응해야 하는데 훈련에서 이를 경험하지 못했습니다

## 3. 에이전트-OS 의미론 간극으로 인한 실행 불투명성

[[agent-os-semantic-gap]]이 Crab 논문에서 식별한 문제는 단순한 기술적 비효율을 넘어섭니다. 하네스 없이 학습한 에이전트가 하네스 내에서 실행될 때:

- 에이전트의 내부 상태 전이가 OS 수준에서 어떻게 표현되는지 에이전트 자신이 모델링하지 못합니다
- 이는 [[agent-execution-semantic-opacity]]로 이어져, 에이전트가 자신의 실행 환경에 대한 **메타인지** 없이 하네스의 의사결정(체크포인트 타이밍, 롤백 여부 등)에 수동적으로 종속됩니다
- [[agent-os-semantic-preservation-failure]]가 발생할 가능성이 높아집니다: 체크포인트 복원 시 에이전트가 의미론적으로 보존해야 할 추론 맥락이 OS 스냅샷 경계에서 손실됩니다

## 새로운 개념적 연결 발견

이 분석을 통해 다음 연결이 새롭게 드러납니다:

**[[agentic-harness-engineering]] ↔ [[algorithm-system-boundary-collapse]]**: OpenForgeRL의 지적은 하네스가 단순한 '시스템 계층'이 아니라 에이전트 능력의 일부를 구성한다는 것을 의미합니다. 훈련-배포 분리를 고수하면 알고리즘(에이전트)과 시스템(하네스)의 경계가 인위적으로 유지되지만, 실제로는 이 경계가 **붕괴**되어야 에이전트가 하네스 네이티브 능력을 발휘할 수 있습니다.

**[[agentic-harness-engineering]] ↔ [[autonomy-quality-decoupling]]**: 하네스를 배포 전용 인프라로 분리하면, 에이전트의 자율성(훈련 시 학습)과 품질(하네스 매개 실행 시 실현)이 구조적으로 분리됩니다. OpenForgeRL이 "Train Harness-native Agents"를 주장하는 것은 이 분리를 훈련 시점에서 해소하겠다는 것입니다.

**[[adaptive-inference]]의 확장**: SpecKV가 압축이라는 내부 상태에 반응하는 적응을 제시했다면, 하네스 네이티브 훈련은 **하네스 상태(체크포인트 가용성, 스키마 축적도, 롤백 히스토리 깊이)에 반응하는 적응**이라는 새로운 적응 차원을 열어야 합니다.

## 핵심 결론

하네스 없이 학습한 에이전트가 하네스 내에서 실행될 때의 근본적 제한은 **단순한 성능 저하가 아니라, 에이전트가 학습한 능력의 실행 경로 자체가 하네스의 의미론과 불일치하여 일부 능력이 발현 불가능해지는 구조적 문제**입니다. 이는 [[agentic-harness-engineering]]을 "배포 시 인프라"에서 "훈련-배포 통합 아키텍처"로 재정의해야 함을 시사합니다.

## 핵심 통찰

하네스 없이 학습한 에이전트의 능력 제한은 단순한 성능 저하가 아니라 학습된 능력의 실행 경로 자체가 하네스 의미론과 불일치하여 일부 능력이 발현 불가능해지는 구조적 문제이므로, 하네스를 배포 전용 인프라에서 훈련-배포 통합 아키텍처로 재정의해야 함.
