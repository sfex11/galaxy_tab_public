# 에어갭 소형 모델의 '침묵적 누락'을 `[[agent-os-semantic-gap]]`에 구조화하는 방법

## 1. 기존 간극의 정체: "상태 의존성" vs "스냅샷 표현"

[[agent-os-semantic-gap]]는 [[algorithm-system-translation-gap]]이 구체적 런타임 문제로 현현한 형태다. [[agentic-harness-engineering]]에서 [[sources/2026-05-02-crab-a-semantics-aware-checkpointrestore-runtime-f.md|Crab]]이 명확히 보여주듯, 이 간극의 본질은 **에이전트의 의미론적 의존 그래프**(어떤 상태에 의존하는가)를 **OS의 체크포인트 메커니즘**(전체 스냅샷)으로 번역할 때 발생하는 비효율이다.

Crab의 C/R 런타임은 결함 내성·롤백·분기를 인프라 계층에서 직접 구현함으로써 이 간극을 **상태 보존** 차원에서 좁혔다. 핵심 전제는 "상태가 손상되었으니 이전 정상 상태로 되돌리면 된다"는 것이다.

## 2. 누락이 기존 하네스를 무력화하는 구조적 이유

침묵적 누락(omission)은 이 전제를 근본적으로 붕괴시킨다:

| 차원 | 환각/오판단 (기존) | 침묵적 누락 (에어갭) |
|------|-------------------|-------------------|
| 실패의 존재론 | **잘못된 것이 생성됨** → 상태에 오염 존재 | **생성되어야 할 것이 없음** → 상태에 오염이 없음 |
| C/R 트리거 | 출력 검증 → 오류 탐지 → 롤백 | 탐지 대상이 실행 흔적에 존재하지 않음 |
| [[aggregate-pipeline-serving]] 관점 | 스키마 축적 병목 등 레이턴시 문제로 진단 가능 | 파이프라인은 정상 완료되므로 병목 자체가 성립하지 않음 |

즉, [[agentic-harness-engineering]]가 구축한 제어 계층은 **존재하는 것의 잘못됨**을 잡도록 설계되었지, **존재해야 할 것의 부재**를 잡도록 설계되지 않았다. Crab의 의미론적 의존 그래프도 "현재 상태가 무엇에 의존하는가"를 추적하지, "현재 상태가 **무엇에 의존해야 했으나 누락되었는가**"를 추적하지 않는다.

## 3. 간극의 제2차원으로서 구조화: "정보적 의존 그래프" vs "실행 흔적"

`[[agent-os-semantic-gap]]`를 확장하여 누락을 구조화하려면, 기존의 **상태 의존성** 간극 옆에 **정보적 의존성** 간극이라는 제2차원을 도입해야 한다.

### 3-1. 제1차원 (기존, Crab이 다룸)
> **에이전트의 상태 의존 그래프** ↔ **OS의 스냅샷 표현**
> 
> 문제: 의존 관계가 텍스트 전체 스냅샷으로 뭉개짐
> 해결: 의미론적 C/R으로 정밀 복원

### 3-2. 제2차원 (신규, 누락이 노출시킴)
> **에이전트 추론의 정보적 의존 그래프**(어떤 사실이 도출을 위해 필수적인가) ↔ **실행 흔적**(실제로 생성된 토큰 시퀀스)
> 
> 문제: 정보적 의존 그래프의 노드 중 **실행 흔적에 materialize되지 않은 노드**가 존재하는데, OS는 '존재하지 않는 것'을 상태로 표현할 수 없음
> 해결: 불가 — 기존 OS 추상화에 "부재의 상태"라는 개념이 없음

층별 귀인(layerwise attribution)이 제공하는 것은 이 제2차원 간극의 **진단 도구**다. 어느 층에서 정보가 소실되었는지를 보여주지만, 그 소실을 OS 수준에서 어떤 '상태'로 간주해야 하는지의 문제는 남는다.

## 4. `[[agent-os-semantic-preservation-failure]]`과의 연결 및 한계

슬러그 목록에 `[[agent-os-semantic-preservation-failure]]`가 존재하는데, 이는 표면적으로 누락과 연결될 것 같으나 실제로는 **보존 대상이 존재할 때**의 실패를 전제한다. 누락의 경우 보존할 대상 자체가 실행 흔적에 없으므로, 이 엔티티의 스코프 밖이다.

마찬가지로 [[checkpoint-consensus-reduction]]이나 [[cache-phase-preservation]]도 이미 캐시/체크포인트에 존재하는 정보의 보존을 다루지, 존재하지 않았던 정보의 부재를 다루지 않는다.

## 5. 새로운 개념의 필요성: 명시적 부재 상태 (Explicit Absence State)

이 분석에서 **새로운 개념**이 필요함이 명확해진다:

> **실행 흔적에 materialize되지 않았으나, 정보적 의존 그래프상 필수였던 노드를 OS가 "부재 상태(absence state)"로 표현하고, 이를 C/R 트리거 조건으로 삼을 수 있는가?**

기존 OS 추상화에서 상태는 **존재하는 것의 스냅샷**이지 **존재해야 할 것의 목록**이 아니다. 이를 뒤집으려면:

1. **사전 정보적 의존 그래프**: 에이전트가 태스크를 수행하기 전, 도메인 지식 기반으로 "이 태스크에는 이런 사실들이 필수적"이라는 그래프를 구성
2. **부재 탐지기(Absence Detector)**: 실행 흔적과 사전 그래프를 비교하여 materialization failure를 탐지
3. **부재-기반 롤백**: 오류가 아닌 부재를 트리거로, 해당 층 이전으로 되돌아가 재생성 시도

이것은 [[adaptive-inference]]가 모델/라우트 선택에서 추측 길이(γ) 선택으로 적응 차원을 확장한 것과 유사한 패턴 — 즉, **"무엇을 제어 변수로 삼는가"의 확장** — 이다. SpecKV가 압축이라는 내부 시스템 상태에 반응하는 적응의 새 유형을 제시했다면, 부재-기반 제어는 **"생성되지 않은 것"이라는 더 근본적인 내부 상태**에 반응하는 적응이 된다.

## 6. 결론: `[[agent-os-semantic-gap]]`의 재정의 제안

현재 Wiki의 `[[agent-os-semantic-gap]]` 정의를 다음과 같이 2차원 구조로 재정의해야 한다:

```
agent-os-semantic-gap = {
  차원1: 상태 의존성 그래프 ↔ OS 스냅샷 표현  (Crab이 해결한 부분)
  차원2: 정보적 의존성 그래프 ↔ 실행 흔적       (누락이 노출시킨 부분)
}
```

차원2의 핵심은 **"OS가 부재를 상태로 표현할 수 없다는 구조적 한계"**이며, 이것이 [[agentic-harness-engineering]]가 에어갭 소형 모델에서 완전히 무력해지는 근본 원인이다. 층별 귀인은 진단은 가능하게 하지만, 치료는 OS 추상화의 근본적 확장 — **부재를 일급 상태(first-class state)로 승격** — 없이는 불가능하다.

---

**새로운 연결 발견**: `[[adaptive-inference]]`의 SpecKV 패턴(내부 시스템 상태를 제어 변수로 삼는 적응)을 "부재 상태"라는 새로운 내부 상태에 적용하면, 적응적 추론의 스펙트럼을 추측 길이 선택을 넘어 **"재생성 여부" 선택**까지 확장할 수 있는 구조적 경로가 열린다.

**새로운 개념 발견**: 위 슬러그 목록에 **"정보적 누락을 일급 상태로 처리하는 개념"**(예: `absence-as-state`, `informational-omission-as-failure-mode` 등)이 존재하지 않습니다. 이는 에어갭 배포의 지배적 실패 모드를 구조화하기 위해 신규 엔티티로 생성이 필요한 개념입니다.

## 핵심 통찰

기존 OS 추상화가 '존재하는 것의 스냅샷'만을 상태로 표현할 뿐 '존재해야 할 것의 부재'를 상태로 간주할 수 없다는 본질적 한계가 에어갭 소형 모델의 침묵적 누락을 기존 하네스(오류 탐지→롤백)로 잡아내지 못하게 하는 근원 원인이다.
