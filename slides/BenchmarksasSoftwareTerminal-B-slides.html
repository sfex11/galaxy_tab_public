Benchmarks as Software

Terminal-Bench와 지속적 벤치마크(Continuous Benchmarks)를 위한 주장

E. Kelly Buchanan · Crystal Zhou · Scott W. Linderman · Christopher Ré

Stanford University · Cornell University

벤치마크는 왜 낡아가는가?

  • 코딩 에이전트는 LLM 배포 중 가장 경제적으로 중요한 분야 → 신뢰할 수 있는 평가가 필수
  • 출시 당시 정밀하게 검증된 벤치마크조차 시간이 지나면 노화(stale)됨
  • 모델이 향상되면 기존 검증기(verifier)가 거부하는 유효한 해법을 발견
  • 평가 인프라 변화가 작업·테스트에 내재된 가정을 무효화
벤치마크 점수와 측정하려는 능력 사이의 격차가 누적되는 현상을 벤치마크 유지보수 부채(benchmark maintenance debt)라고 정의한다.

유지보수 부채의 3가지 실패 원인

에이전트 작업 생애주기(저작 → 실행 → 검증) 전반에서 발생

지시–검증 불일치

설계자가 예상하지 못한 유효한 풀이 경로를 검증기가 거부하거나, 과제를 풀지 않고도 테스트를 통과하는 지름길 존재

instruction–verification mismatch

환경 문제

패키지·API·웹사이트 등 외부 상태에 의존하는 과제가 출시 후 상태 변화로 인해 능력과 무관하게 실패

environment issues

과제 드리프트

에이전트·하네스·인프라의 변화에 따라 과제의 원래 의도와 실제 측정 대상이 어긋남

task drift

사례: Terminal-Bench 2.0의 경험

출시 전 철저한 검증

  • 인간 검수
  • LM 지원 감사
  • 익스플로잇(해킹) 테스트

그럼에도 불구하고

50+

수개월 내 이슈 트래커에 task defect 태그가 붙은 오픈 리포트가 작업 스택 전반의 가정 차이를 아우르며 축적

출시 시점의 광범위한 검증만으로는 이후의 감사와 수리 필요성을 제거할 수 없다.

기존 접근법 vs. 본 연구의 접근법

접근법예시한계
환경 고정 의존성 버전 고정 재현성 ↔ 사실성(fidelity)의 상충
작업 필터링 SWE-Bench Verified, WebArena Verified 정밀도 ↔ 커버리지의 상충, 벤치마크 축소
벤치마크 갱신 LiveCodeBench, LiveBench 오염은 줄이지만 출시 후 망가진 과제는 수리하지 않음
수리 기반 지속적 검증 본 논문 필터링이 아닌 수리(repair)로 유효성 회복

ABC 체크리스트, Docent·LangSmith 같은 감사 도구들을 하나의 지속적 검증 워크플로우로 통합

지속적 검증 워크플로우

1
증거 수집
에이전트가 작업 파일·기존 실행 트레이스·커뮤니티 리포트를 수집
2
감사
감사 에이전트가 명세 충실도·테스트·리소스·리스크 원칙을 적용하고 인용된 수리 초안 작성
3
자동 검증
수리가 증거와 대조되고, /oracle이 과제를 재구축해 참조 솔루션 실행
4
인간 게이트
Draft PR 제출 후 유지보수자 검토가 검증된 릴리스를 승인

핵심: 커뮤니티 리포트 + 에이전트 지원 분류 + 인간 재판(adjudication)을 결합해 벤치마크 검증 자체를 지속적 프로세스로 전환

수리(Repair) 규칙: 증상이 아닌 원인을 고쳐라

근본 원인 해결

  • 과제 지시를 명확화하여 유효성 실패 해소
  • 오라클(검증기) 자체를 수리

증상만 지운 패치

  • 정규식을 무작정 완화
  • 수용 조건을 걷어내어 통과만 허용 → 지양
결함 리포트는 그 원인을 확정해 주지 않으며 특정 수리를 정당화하지도 않는다. 결함 확립 → 변경 검토 → 의도 보존 확인이라는 일관된 프로세스가 필요하다.

타임아웃이 주된 실패 원인

>50%

실패 시행의 50% 이상이 타임아웃 — 일부 하네스에서는 최대 ~68%

고정된 wall-clock·출력 토큰 예산은 결과를 실질적으로 바꿀 수 있다. 벤치마크 유지보수는 과제 아티팩트 수리만이 아니라 리소스 설정의 재검증을 포함해야 한다.

외부 타당성: Harbor-Index v0.1 감사

  • 동일한 워크플로우를 다른 벤치마크(Harbor-Index v0.1)에 적용하여 일반화 가능성 검증
  • Terminal-Bench에 국한되지 않는 범용 감사 방법론임을 확인
  • 지속적 검증 파이프라인(제안 전용 propose-only, 인간 게이트 유지)이 타 벤치마크에서도 동작

벤치마크는 종속성·인프라·에이전트가 함께 진화하는 생태계 속 소프트웨어이며, 그 가정은 시간이 지나면 반드시 재검증되어야 한다.

시사점 및 결론

지속적 검증

현대적 에이전트 도구로 커뮤니티 리포트·실행 트레이스·에이전트 분류·인간 재판을 결합한 유지보수 가능한 워크플로우가 실용적

순위 안정성

수리 후에도 순위 상관은 높지만(ρ = 0.958) 점수는 크게 이동 — 수리된 벤치마크의 점수를 보고해야 신뢰할 수 있음

벤치마크 유지보수 부채는 단순한 버그 누적이 아니라, 진화하는 생태계와의 정합성 문제다. 출시 시점 검증 + 지속적 감사 + 리소스 재검증이 유효한 평가의 필수 조건이다.
