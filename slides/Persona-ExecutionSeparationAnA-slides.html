Persona–Execution Separation

실행 감사 하에서 진화하는 LLM 에이전트를 위한 아키텍처 패턴

Yisen Xi · 독립 연구자, 베이징, 중국

문제 상황: 두 가지 상충하는 요구

LLM 에이전트가 조직의 자산에 대해 상태 변경 작업을 수행하면서 동시에 진화해야 할 때 발생하는 구조적 갈등

페르소나 자유 진화

운영자가 지속적으로 지시사항, 어조, 스킬 바인딩을 조정하여 시스템을 개선해야 함

  • 지시사항 자유 수정
  • 어조 및 자기 표현 변경
  • 스킬 바인딩 진화

실행 추적 가능성

모든 상태 변경 작업은 게이트되고, 기록되고, 감사 가능해야 함

  • 펀드 운영, 컴플라이언스
  • 실사(Due Diligence) 작업
  • 완전한 감사 추적

단일 신뢰 도메인은 두 요구를 동시에 저렴하게 충족시킬 수 없다.

단일 도메인의 딜레마

기존 에이전트 아키텍처에서 페르소나와 실행이 하나의 프로세스·신뢰 도메인을 공유할 때의 근본적 문제

엄격 통제 시

페르소나 수정마다 전체 실행 경로의 재검증이 트리거됨

→ 페르소나 동결, 진화 정체

관대 통제 시

실행이 더 이상 신뢰성 있게 추적되지 않음

→ 감사 추적 상실

LLM의 표현적 구분 불가능성(Representational Indistinguishability) 하에서 두 관심사가 동일한 도메인에 있으면 독립적인 조율이 불가능하다.

에이전트 아키텍처 스펙트럼

진화 자유도 vs. 실행 추적 가능성 — 두 축에서의 네 가지 위치

위치 아키텍처 진화 자유도 실행 추적 한계
(1) 단일 도메인 동결 직원 수준 동결 또는 완화 선택
(2) 에이전트 + 도구 자유 도구 수준 직원 수준 추적 없음
(3) 에이전트 + 서브에이전트 자유 종속 수준 추적이 오케스트레이터 종속
(4) PES (본 연구) 자유 드리프트 직원 수준 계약 브리지 비용

PES는 남은 한 모서리를 차지하며, 그 대가로 govern된 contract bridge를 지불한다.

세 가지 설계 목표

분리가 최저비용 해결책이 되는 세 가지 목표

G1

자유 드리프트

페르소나가 실행 재검증 없이 자유롭게 변경될 수 있어야 함

G2

실행 추적 가능성

모든 상태 변경 작업이 게이트·기록·감사 가능해야 함

G3

분리(Decoupling)

G1과 G2가 독립적으로 조율 가능해야 함

LLM 표현적 구분 불가능성 하에서, 세 목표를 모두 충족하는 단일 도메인 메커니즘은 타입화된 변경 객체, 외부 게이트, 안정적 감사 앵커를 재도입해야 하며, 이는 더 높은 결합 비용으로 PES를 재건축하는 것과 동일하다.

PES 패턴: 핵심 아이디어

두 얼굴, 한 직원 — 한 신원이 두 신뢰 도메인에 걸쳐 존재

표현면 (Expression Surface)

허용적 도메인 (Permissive Domain)

  • 페르소나가 거주하는 곳
  • 자유 드리프트 허용
  • 가벼운 추적만
  • 사용자가 에이전트를 보고 편집하는 곳

실행면 (Execution Surface)

제한적 도메인 (Restrictive Domain)

  • 실행이 수행·감사되는 곳
  • 무얼굴(Faceless) — 페르소나 없음
  • 완전한 게이팅과 추적
  • 조직 자산에 대한 상태 변경

두 도메인은 Governed Contract Bridge로 연결되며, 한 직원 신원이 연속적으로 유지된다.

Governed Contract Bridge

두 도메인 간의 정보 흐름을 통제하는 세 가지 메커니즘

1
승인 매트릭스
어떤 정보가 도메인 간에 이동할 수 있는지 정의
2
DLP (데이터 유출 방지)
등급화된 예외를 제외하고 데이터 본체는 제한적 도메인에 유지
3
감사 (Audit)
모든 도메인 간 이동이 기록되고 감사 가능

허용 → 제한 방향

승인된 승격(promotion) 채널을 통해서만 — 일방향 밸브

제한 → 허용 방향

상태 요약만 반환 — 데이터 본체는 제한적 도메인에 잔류

"에이전트가 도구를 호출하는 것"과의 차이

PES는 단순한 도구 호출 패턴과 근본적으로 다르다

측면 에이전트 + 도구 PES
관계 주인-종속 (Master–Servant) 한 직원, 두 얼굴
신원 도구에 직원 수준 신원 없음 도메인 간 연속적 신원
추적 도구 수준 로그 직원 수준 감사 추적
정보 흐름 통제되지 않음 Governed bridge (승인+DLP+감사)
페르소나 변경 영향 실행 측면에 영향 가능 실행 의미 불변 (bridge 강제 시)

사례 연구: FIA Workbench

금융 기관용 디지털 직원 플랫폼에서 한 달간의 의사결정 체인

P1
시드: 페르소나의 거점 확보

페르소나를 허용적 도메인에 단일 거점(Singly-homed)으로 배치

P2
계약: 흐름 방향의 통제

정보 흐름이 govern된 계약에 의해 규제되도록 설계

P3
채널: 승격 작업 지시

승격을 위한 전용 채널 도입

P4
결정화: 이중 얼굴 모델

하나의 직원이 두 도메인에서 각각 다른 얼굴을 가지는 모델로 확정

각 결정마다 기각된 대안이 기록됨

기존 아키텍처와의 비교

8개 오픈소스 플랫폼 + 학술 연구와의 체계적 비교

플랫폼 실행 자유도 통제된 정보 흐름 신원 분리
LangChain / Dify / n8n 도구 수준 없음 없음
AutoGen / CrewAI / Swarm 서브에이전트 부분 종속
보안 실행 클러스터 (2025–26) 의도-실행 분리 부분 없음
PES 자유 드리프트 Bridge 통제 연속적 신원

2022–2026 스캔 결과, G1–G3을 공동 충족하는 기존 아키텍처는 없었다.

메커니즘 검증 결과

세 가지 검증 프로토콜 (2026-08-21 실행)

V1 자유 드리프트 검증

5개 모델 구성에서 페르소나 교란 시

실행 측 재검증 없음

V2 추적 격리 검증

구조적 + 데이터 수준에서

페르소나 지문 없음

V3 필연성 탐침

분리 전 빌드 복원 후

누락에 의한 분리, 구조에 의한 것이 아님

V3 탐침: 분리 전 빌드에서 실행 경로는 누락(omission)에 의해 페르소나와 분리되어 있었으며, 후속 배선 변경이 격리를 역전시킬 수 있었다. PES는 이를 감사된 아키텍처 규칙으로 만든다.

이론적 기반

PES의 신뢰 도메인 분리는 세 가지 이론 체계에 뿌리를 둔다

정보 흐름 통제

Denning의 격자 모델 (1976)

보안 등급과 허용된 흐름 방향 → PES는 조직적 수준에서 이를 인스턴스화

Bell-LaPadula 모델

No-Read-Up / No-Write-Down

일방향 밸브의 이론적 근거 — 분류 레이블이 아닌 조직 도메인으로

변경 격리

Change Isolation (이론적 앵커)

한 관심사의 변경이 다른 관심사의 동작을 변경하지 않아야 한다는 원칙

적용 조건, 한계 및 향후 과제

적용 조건 (셋 모두 충족 시)

  • 다 사용자 배포 (Multi-user deployment)
  • 실행 감사 필요 (Execution audit)
  • 페르소나 변동 예상 (Expected persona churn)

한계

  • 단일 사례 (개발/파일럿)에 기반
  • 정식 보장(formal guarantee) 불가
  • 올바르게 구현된 bridge에 의존
  • 건강보험/공공행정은 추가 검증 필요

향후 과제

다중 사례 검증 · bridge 구현의 정규화 · 페르소나 드리프트의 자동 감지 · 도메인 간 신원 연속성의 형식화 · 보안 실행 클러스터와의 통합 경로 탐색

핵심 요약

기여 1: 아키텍처 패턴

페르소나와 실행을 두 신뢰 도메인에 분리하고, govern된 contract bridge로 연결

기여 2: 의사결정 체인 기록

FIA Workbench에서 한 달간 5개 결정과 기각된 대안의 문서화

기여 3: 기존 플랫폼 비교

8개 오픈소스 + 학술 연구에서 G1–G3 공동 충족 사례 없음

PES의 핵심 메시지

에이전트가 규제된 작업을 수행하게 되면, 페르소나 진화와 실행 추적 가능성의 결합은 아키텍처 문제이지 프롬프트 튜닝 문제가 아니다.

  • 페르소나는 단일 거점, 자유 드리프트
  • 실행은 무얼굴, 완전 감사
  • 신원은 연속적 유지
  • Bridge가 두 도메인의 계약을 강제
