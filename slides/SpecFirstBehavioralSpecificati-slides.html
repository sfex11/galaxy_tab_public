SpecFirst: 행동 명세 추출을
에이전트 기반 프로그램
합성의 일급 단계로

Behavioral Specification Elicitation as a First-Class Step
in Agent-Based Program Synthesis from Scratch

Yihao Chen, Shi Chang, Khaled Chawa, Feng Lin, Boyuan Chen, Shaowei Wang, Ahmed E. Hassan

문제 상황

기존 코드베이스 기반 작업

버그 수정, 기능 구현, 코드 완성 등 기존 코드가 있으면 LLM 에이전트가 강력한 성능을 발휘합니다.

  • 코드베이스가 컨텍스트를 제공
  • 구조와 동작의 참조점 존재

처음부터 프로그램 구성

자연어 문서와 실행 바이너리만 주어지면, 최신 모델도 1% 미만의 인스턴스만 해결합니다.

  • 아키텍처·언어 선택 필요
  • 행동 포락선 재구성 부담

ProgramBench 기준: GPT-5.5조차 인스턴스의 1% 미만만 완전 해결 — 처음부터 구성은 여전히 미해결 과제

기존 접근법의 세 가지 한계

1

불충분한 탐색적 프로빙

전용 탐색 단계가 없어 에이전트가 바이너리를 충분히 프로빙하기 전에 코딩으로 전환. 엣지 케이스, 에러 경로, 플래그 상호작용을 놓침.

2

긴 실행_horizon에서의 명세 손실

명시적 추출 없이 행동 의도를 암시적으로 유지해야 하며, 컨텍스트 드리프트와 토큰 압축(추론 토큰 제거 등)으로 인해 원래 명세가 점진적으로 퇴화.

3

앵커링 없는 오류 전파

추출된 명세가 안정적 참조점으로 없으면, 초기 오해나 잘못된 행동 가정이 턴마다 누적·전파되어 보정 불가.

핵심 아이디어: 요구사항 공학에서 영감

"전통 소프트웨어 공학에서는 명세 추출을 구현 이전의 일급 단계로 처리한다. 에이전트 기반 프로그램 구성에도 동일한 분해가 적용되어야 한다."

기존 프레임워크의 문제

SWE-agent, OpenHands 등은 문서 읽기, 행동 탐색, 코드 합성을 단일 루프에서 혼합 실행 — 계획·프로빙·코딩이 같은 턴 예산 내에서 자유롭게 전환됨.

Spec-driven 프레임워크와의 차이

OpenSpec, spec-kit은 명세 중심 철학을 공유하지만, 인간에게 프롬프트로만 의존하며 바이너리 프로빙을 통한 자동화된 행동 추출을 지원하지 않음.

SpecFirst 프레임워크 개요

1
Spec Agent
문서 + 바이너리 → 체계적 블랙박스 프로빙 → 구조화된 행동 명세(SPEC.md) 산출
2
Code Synthesis Agent
문서 + 바이너리 + SPEC.md → 구현에만 집중 → 소스코드 산출
3
평가
빌드 → 숨겨진 테스트 스위트 대비 테스트 통과율 측정
2

명확히 분리된 2단계 파이프라인

SPEC.md

구조화된 명세 산출물

0

단계 간 코드 작성 없음

Stage 1: Spec Agent 상세

바이너리 프로빙 전략

  • 문서에서 추출된 명령어 패턴으로 초기 프로빙
  • 다양한 입력 조합 체계적 탐색
  • 에러 경로, 엣지 케이스, 플래그 상호작용 발견
  • 단축키(바이너리 소스 읽기) 방지 제약 적용

명세 산출물 (SPEC.md)

  • 프로그램 목적 및 개요
  • 명령행 인터페이스 상세
  • 입력별 기대 출력 시나리오
  • 에러 처리 및 엣지 케이스
  • 문서에 없는 바이너리 고유 행동

핵심 원칙: Spec Agent는 코드를 단 한 줄도 작성하지 않으며, 오직 행동 이해에만 집중. 종료 조건 충족 시 SPEC.md를 산출하고 종료.

구조화된 명세

SPEC.md가 바꾸는 것

  • 문서 모호성이 코딩 시작 전에 해결됨
  • 문서-바이너리 간 행동 격차가 명시적으로 기록됨
  • 합성 과정 전체에서 안정적 행동 참조점 제공
  • 프로빙과 코딩의 경쟁이 원천 제거됨

기존 단일 루프 베이스라인(mini-SWE-agent)과 동일한 합성 에이전트를 사용하여 공정 비교 보장.

실험 설계

벤치마크

ProgramBench 전체 200개 인스턴스

  • 자연어 문서 + 실행 전용 바이너리만 제공
  • 숨겨진 테스트 스위트로 평가
  • 난이도 3단계 분류 (Easy/Medium/Hard)

평가 모델

2개 패밀리, 능력 차이 10배

  • Qwen3.5-397B-A17B
  • Qwen3.6-35B-A3B
  • GPT-5.5-high
  • GPT-5.4-mini

베이스라인

mini-SWE-agent (단일 루프)

평가 지표

Test Pass Rate + Exploration Coverage

통계 검정

Wilcoxon signed-rank test

RQ1: SpecFirst의 전반적 효과

모든 모델에서 일관되게 베이스라인 대비 향상 — 모두 통계적으로 유의미

RQ2: 난이도별 효과

Easy
+

이미 베이스라인이 높은 성능을 보이나, SpecFirst가 추가로 엣지 케이스 포착에 기여

Medium
+

가장 큰 절대적 향상 — 문서와 바이너리 간 격차가 큰 인스턴스에서 SPEC.md의 가치 극대화

Hard
+

상대적 향상률은 높으나 절대 Pass Rate는 여전히 낮음 — 복잡한 프로그램에는 추가 연구 필요

SpecFirst는 모든 난이도에서 일관되게 향상을 보이며, 특히 Medium 난이도에서 문서-바이너리 격차 해소 효과가 가장 크게 나타남.

RQ3 & RQ4: 행동 분석

RQ3: Spec Agent의 탐색 효과

  • 단일 루프보다 9.4%~18.5% 더 많은 바이너리 프로빙 수행
  • 코딩과의 경쟁 없이 순수 탐색에 집중
  • 문서에 누락된 행동을 체계적으로 발견

RQ4: 합성 에이전트 행동 변화

  • 사전 명세가 있으면 더 일찍 코드 작성 시작
  • 프로빙-코딩 교대가 아닌 지속적 구현 패턴
  • 더 크고 완전한 구현물 생산

핵심 발견: 명세 분해는 단지 "더 많이 탐색"하는 것뿐 아니라, 합성 에이전트의 턴 예산 할당 방식 자체를 구조적으로 변화시킴.

추가 논의

실패 사례 분석

  • Spec Agent가 복잡한 상태 의존성을 놓치는 경우
  • SPEC.md 명세 자체의 오류가 코드로 전파
  • 매우 복잡한 프로그램(Hard)은 여전히 과제

명세 형식의 중요성

  • 구조화된 마크다운 형식이 성능에 긍정적 영향
  • 형식이 명확할수록 합성 에이전트가 더 잘 활용

비용 고려

Spec Agent가 추가 턴을 소비하지만, 합성 에이전트의 프로빙 턴 감소로 부분 상쇄됨.

결론 및 기여 요약

1

SpecFirst 프레임워크 제안

처음부터 프로그램 구성을 위해 행동 명세 추출과 코드 합성을 명시적으로 분리한 최초의 에이전트 파이프라인.

2

대규모 실증 평가

ProgramBench 200인스턴스 × 4모델에서 일관된 향상 — Test Pass Rate +6.9%~21.3%, 모두 통계적으로 유의미.

3

행동 분석 통찰

사전 명세가 합성 에이전트의 턴 할당 방식을 구조적으로 변화시켜, 더 일찍 그리고 더 지속적으로 코드를 작성하도록 유도.

명시적 요구사항 공학 단계는 처음부터 프로그램 구성을 위한 효과적인 패러다임임이 실증적으로 입증되었다.
