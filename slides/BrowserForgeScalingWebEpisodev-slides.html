웹 에이전트의 인식 방식

텍스트 기반 (HTML / A11y 트리)

  • 취약성: 사이트마다 구조가 다르고, 리스타일 시 변경됨
  • 비용: 단일 페이지 A11y 트리가 수만 토큰에 달함
  • 요소 식별자로 정밀한 액션 가능

순수 GUI 기반 (스크린샷)

  • 견고성: 사이트 간 형태가 균일함
  • 효율성: 고정된 낮은 토큰 비용
  • 사람의 인터랙션 방식과 정렬
순수 GUI 에이전트는 두 가지 단점을 회피하지만, 대규모 고품질 상호작용 궤적이 필수적

오픈 웹 URL 수집 및 정제

수집 단계

  • Common Crawl에서 대규모 URL 추출
  • 도메인 중복 제거
  • 안전성 필터 (유해 콘텐츠 제외)

정제 단계

  • 실제 도달 가능성 (HTTP 응답 확인)
  • 렌더링 가능성 (브라우저에서 로드 성공)
  • 상호작용 가능 요소 존재 여부

결과: 수십만 개의 실제, 도달 가능한 고유 웹사이트 확보

병렬 브라우저 샌드박스 오케스트레이션

설계 원칙

  • 공유 작업 큐: 모든 샌드박스가 하나의 큐에서 URL을 소비
  • 동적 스케줄링: 완료된 샌드박스에 즉시 새 작업 할당
  • 고활용도 유지: 유휴 시간 최소화
  • 일회성 샌드박스: 오염 방지를 위해 사용 후 폐기

Proposer–Solver 이중 에이전트 루프

Proposer

페이지를 관찰하고 실행 가능한 태스크를 제안

  • 스크린샷 + A11y 트리 입력
  • 자연어 목표 + 성공 조건 생성
  • 태스크의 실행 가능성 판단

Solver

제안된 태스크를 수행하며 궤적 기록

  • 스크린샷만으로 페이지 인식
  • 클릭/입력/탐색 액션 수행
  • 단계별 추론과 액션 로깅

Proposer가 태스크를 만들고 → Solver가 실행하여 궤적을 수집 → 검증을 통과한 궤적만 코퍼스에 포함

궤적 정제 및 통일된 추론 형식

1
규칙 기반 필터링
실패 실행, 빈 궤적, 비정상 액션 제거
2
모델 기반 검증
LLM이 궤적의 논리적 일관성 평가
3
추론 형식 통일
생존 궤적을 단일 CoT 스타일로 재작성

통일된 Chain-of-Thought 형식

각 궤적의 추론을 일관된 구조(관찰 → 생각 → 행동)로 재작성하여, 학습 시 신호의 잡음을 줄이고 모델이 안정적인 추론 패턴을 학습하도록 유도

분석 및 제거 실험

스케일링 분석

  • 코퍼스 크기가 증가할수록 성능 단조 증가
  • 아직 포화 지점에 도달하지 않음
  • 더 많은 데이터 → 더 나은 성과

제거 실험

  • 오픈 웹 소스와 넓은 웹사이트 커버리지가 핵심 기여 요인
  • 학습 레시피 자체보다 데이터 다양성이 더 중요
  • 정제 파이프라인의 각 구성요소가 모두 기여

결론: 성능 향상의 원인은 "어디서" 데이터를 가져왔는지 (오픈 웹 + 다양성)

기여 요약

1
BrowserForge 프레임워크 — 병렬 브라우저 샌드박스를 오케스트레이션하여 고정 웹사이트 목록에서 데이터 규모와 다양성을 분리
2
Proposer–Solver 합성 루프 + 정제 파이프라인 — 비지도 오픈 웹 페이지를 실행 가능한 태스크와 필터링된 궤적으로 변환, 통일된 추론 형식 제공
3
