런타임 토폴로지 컨텍스트가
LLM이 생성한 쿠버네티스
보안 패치를 개선하는가?

Does Runtime Topology Context Improve
LLM-Generated Kubernetes Security Patches?

Farooq Shaikh · Dynatrace Research, Linz, Austria

문제 정의

기존 LLM 기반 보안 수정의 한계

기존 접근법

  • KSPM 발견 사항을 개별적으로 LLM에 프롬프트
  • 일반 하드닝 지식만으로 올바른 수정 가정
  • 리소스 스키마 유효성 검증에만 의존

치명적 결함

  • 런타임 서비스 의존성을 모름
  • 정적으로 "정확한" 패치가 실제로는 기능적 파급 반경 초래
  • 다운스트림 호출자 충돌, 호출 에지 단절
"패치가 런타임 서비스 의존성을 보존해야 할 때 이 가정은 붕괴한다 — 정적으로 준수된 수정이 파괴적인 기능적 파급 반경을 갖는다."
동기 부여 예시

정적으로 올바르지만, 실제로는 파괴적인 패치

Capability 제거

필수 Linux capability을 삭제 → 서비스 포트 바인딩 실패 → 모든 다운스트림 호출자 장애

Default-Deny NetworkPolicy

기본 거부 정책 적용 → 관측된 모든 호출 에지가 대상 서비스에서 단절

RBAC Role 축소

과도한 RBAC 역할 삭제 → 워크로드가 시작 시 사용하는 K8s API 접근 권한 상실

이 문제는 capability, network-policy, RBAC, secret, credential, pod-security-policy, 7개 구성 클래스 전체에 구조적으로 존재

핵심 아이디어

누락된 요소: 런타임 서비스 토폴로지

공격 파급 반경(보안 분석이 정량화하는 것)이 아닌, 기능적 파급 반경 — 라이브 클러스터 동작에 미치는 파괴적 영향

기존 도구의 한계

  • 공격 그래프: 정적 매니페스트 스냅샷 기반 → 라이브 호출 그래프와 불일치
  • 런타임 모니터: 개별 이벤트에 반응적 → 구조화된 토폴로지 컨텍스트 제공 불가
  • KSPM: 개별 리소스 단위 분석 → 서비스 호출 경로 상 위치 반영 안 됨

필요한 것

  • 어떤 서비스가 런타임에 서로 통신하는지
  • 어떤 컨테이너가 권한 포트를 바인딩하는지
  • 어떤 규정 준수 위반이 다중 홉 경로에 복합 리스크를 누적하는지

이전 연구에서는 토폴로지 컨텍스트 제공이 패치 정확도를 변화시키는지 통제 조건 하에서 측정한 바 없다.

주입 가능한 발견 사항

설계 원칙

  • 헬스케어 도메인 클러스터 — 현실적인 서비스 의존성 구조

의존성 클래스 TD/TI 토폴로지 의존성 예시
Credential TD 인터넷 노출 서비스의 잘못된 자격 증명

Pod-Security-Policy TD 필요한 권한 에스컬레이션 차단
Storage TI 스토리지 구성 — 서비스 호출과 무관

TD = 토폴로지 의존적 (패치가 호출 에지 보존 필요) · TI = 토폴로지 독립적 (독립 수정 가능)

규정 준수 가중치 서비스 그래프

  • 노드: K8s 서비스 · 에지: Istio 요청 카운터
  • 에지 가중치 = KSPM 심각도 (LOW ~ CRITICAL)
  • 인터넷 노출 서비스 + 취약한 백엔드 결합 → 단일 발견이 알지 못하는 고우선순위 경로

LLM 주석자

  • 각 홉을 MITRE ATT&CK for Containers 매트릭스에 대해 의미론적 검색으로 주석
  • STIX 번들 기반 기법 할당
  • 경로 우선순위 자동 정렬
핵심 차별점: 정적 매니페스트가 아닌 라이브 Istio 텔레메트리에서 에지를 구성 → 클러스터에서 실제 실행되는 서비스 상호작용 반영

토폴로지 효과 격리를 위한 요인 설계

실험 조건

  • Scanner-Only: KSPM 발견 사항만 프롬프트 (베이스라인)
  • +Topology: Istio 호출 에지 + 서비스 계정 바인딩 추가
  • TI 발견 사항을 통제군으로 사용 → 일반적 프롬프트 보강 효과 격리

  • 세 가지 모두 충족 시만 정확(correct)

실패 모드 분석 (RQ4)

토폴로지 제공 시에도 실패하는 경우

주요 실패 패턴

  • 토폴로지를 인식하더라도 과도하게 보수적인 패치 생성 — 필요한 에지까지 차단
  • RBAC: 세분화된 권한 최소화에 어려움 — 전체 역할 삭제 vs 정확한 권한 축소의 균형 실패
  • 다중 홉 의존성 체인에서 간접 의존성 누락

클래스별 실패율

  • RBAC: 52.4% 여전히 실패 — 세분화 권한 제어의 본질적 어려움
  • Pod-Security-Policy: 33.3% 실패
  • Credential / Network-Policy: 5% 실패 (거의 완전 해결)
RBAC은 권한의 정교한 최소화가 필요하여 토폴로지 정보만으로는 불충분 — 추가적인 권한 분석 메커니즘 필요
