왜 런타임 동작 추론이 중요한가?

  • 코딩 에이전트에서 LLM은 코드 생성뿐 아니라 프로그램 실행 방식에 대한 추론이 필요
  • 런타임 동작은 정적 소스 코드와 자연어 문서에 명시적으로 드러나지 않음
  • 제어 흐름, 데이터 의존성, 중간 상태, 예외 전파, 불변식은 함수·파일·프레임워크를 가로지르는 추론을 요구

SWE-Flux 개요

  • 12개 실제 Python 저장소에서 수집한 480개 인스턴스, 고정(pinned)된 저장소 버전 사용
  • 정답(gold answer)은 계측된 테스트 실행에서 자동 수집 — 수동 작성도, LLM 판정도 아님
  • 단일 테스트 질문과 다중 테스트 수준 질문을 모두 포괄
  • 제어 흐름, 루프, 프로그램 상태, 데이터 흐름, 예외, 불변식 등 7개 동작 카테고리 커버

차별점 1 결정론적 JSON 정답 → 자동·정확한 채점

차별점 2 실제 저장소 실행 기반 → 현실적 난이도

2단계 분류 체계 (Taxonomy)

Level 1 단일 테스트 실행 질문(S) vs 다중 테스트 집합 질문(M)

RQ2: 5가지 핵심 실패 패턴

  • Discovery 3 · 실행 경계 상실 — 너무 일찍 중단하거나, 실행되지 않을 동작까지 따라가는 경계 오류
  • Discovery 4 · 데이터 흐름 — 동적 추론 중 가장 어려운 유형
  • Discovery 5 · 수트 수준 추론 — 일부 테스트에서의 외삽이 아니라 전체 수트의 집계가 필요
  • Discovery 6 · 경로 ≠ 상태 — 올바른 실행 경로를 골라도 런타임 상태가 틀릴 수 있다
  • Discovery 7 · 정적 페리의 개입 — 런타임 증거보다 정적 사전 지식이 우선하는 오류

결론

코드 "생성"이 가능한 모델도 코드 "실행에 대한 추론"은 크게 뒤처져 있다 — 최고 모델도 37.71%에 그치며, 특히 데이터 흐름(6%)과 수트 수준 집계에서 취약하다
  • 실행 기반·결정론적 정답 수집으로 LLM 판정 편향 없는 평가 실현
  • 실패 분석이 모델 개선의 구체적 방향(경계 인식, 상태 추적, 집계)을 제시
  • 입력 교란 파이프라인으로 자동 갱신 가능한 벤치마크 생태계 확보
