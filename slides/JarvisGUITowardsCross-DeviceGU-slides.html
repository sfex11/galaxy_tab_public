왜 '기기 간' GUI 워크플로우인가?

실제 GUI 사용은 여러 기기와 플랫폼에 걸친 워크플로우가 빈번합니다 — 중간 결과 전송, 공유 상태 유지, 이기종 환경 간 조율이 필요합니다.

현실의 디지털 워크플로우

  • 스마트폰 · PC · 서버를 넘나드는 협업 동작
  • 기기 간 정보 전달 및 파일 공유
  • 멀티 플랫폼 실행 전반의 컨텍스트 유지

기존 벤치마크의 한계

  • 단일 기기·정적 정의 과제에만 집중
  • 교차 기기 능력 평가 불가
  • 실사용 준비도에 대한 지나치게 낙관적 판단

관련 연구 동향과 연구 공백

GUI 에이전트

  • 초기: 시각적 마크 기반 인터페이스 인코딩
  • 발전: 원시 스크린샷에서 직접 행동을 예측하는 End-to-End 방식
  • 최근: Grounding + 강화학습(정적/온라인 RL)으로 성능 향상

→ 그러나 대부분 한 시점에 단일 기기 스크린샷만 관측한다고 가정

GUI 에이전트 벤치마크

  • 정적 단일 스텝 → 멀티스텝 인터랙션 → 동적 가상 환경으로 진화
  • 그러나 대부분 단일 기기 설정에 머묾
  • CRAB: 교차 기기의 중요성을 인식했으나 단 18개 과제, 실제 파일·데이터 전송 미모델링

연구 공백 대규모·체계적 교차 기기 벤치마크 부재 → 실험실 평가와 실제 배치 사이의 격차

JarvisGUI의 3가지 핵심 기여

1

최초의 체계적 연구

정보·파일·실행 컨텍스트를 이기종 기기 간에 전송해야 하는 교차 기기 GUI 과제의 체계적 연구

2

슬롯 타입 기반 모델링

전이 가능한 엔티티와 과제 간 의존성을 명시적으로 모델링 → 신뢰 가능하고 확장 가능한 자동 과제 구성

3

다중 생태계 벤치마크

Android · Windows · Ubuntu를 아우르는 JarvisGUI — 현실적 다중 생태계 시나리오 평가

강력한 오픈소스 에이전트들의 평가 결과, 교차 기기 조율이 기존 벤치마크에 가려진 핵심 병목임을 밝혔습니다.

과제 정식화: 타입화된 파라미터 시스템

과제 𝒯 = (ℐ, 𝒪, D, Φ, P) — 입력 슬롯 ℐ, 출력 슬롯 𝒪, 자연어 템플릿 D, 평가 함수 Φ, 실행 플랫폼 P

정적 명세 vs 동적 구성

정적 플랫폼 P, 입력 슬롯 ℐ

동적 출력 𝒪 · 지시문 D · 평가 Φ — 구체 입력값 vℐ에 따라 매핑 M이 실행 시 실체화: (𝒪, D, Φ) ← M(vℐ)

실행 = 반복적 상태 전이

(ai, Mi) = Agent(si, D, Mi−1)

si+1 = Env(si, ai)

이기종 설정에서 상태 si는 여러 플랫폼 관측값의 집합

동적 평가: 최종 환경 상태를 검사해 성공 판정 — 한 과제의 출력 슬롯이 후속 과제의 입력으로 전달됨

시스템 아키텍처: 4계층 구조

1
인프라 계층

2
환경 제어 계층

모델 상호작용 계층

평가 함수 기반 동적 성공 판정

설계 목표: 재현 가능성 · 제어 가능성 + 고처리량 병렬 실행 + 다중 기기 협업 지원

타입 시스템과 조합형 과제 모델링

타입 시스템

슬롯 타이핑으로 전이 가능한 엔티티(파일 · 텍스트 · 연락처 등)를 명시적으로 표현

태스크 그래프

원자 과제들의 입출력 의존성을 그래프로 연결해 다단계 교차 기기 워크플로우를 자동 구성

전역 성공 기준

모든 원자 과제의 평가 함수와 기기 간 전이 무결성을 종합하여 최종 성공 판정

핵심 아이디어: 검증 가능한 원자 과제를 블록처럼 조립 → 안정적이고 확장 가능하며 검증 가능한 복합 교차 기기 과제 생성

자동화된 데이터 수집 파이프라인

1
템플릿 과제 주석
타입화된 원자 과제 템플릿 설계
2
샘플링 기반 자동 구성
타입 호환성에 따라 과제 그래프 자동 생성
3
값 전파
출력 값이 후속 과제 입력으로 전달되어 지시문 실체화
4
LLM-as-a-Judge
품질 평가 및 필터링으로 최종 데이터 확정

품질 관리

자동 검증 · 필터링으로 무의미한 조합 제거 및 실행 가능성 확보

효과

주석 비용을 낮추면서 대규모 복합 과제를 확보 — 확장성 있는 벤치마크 구축

벤치마크 구성: 이기종 3개 플랫폼

Android

모바일 플랫폼 과제 — 스마트폰 환경의 원자 및 복합 작업

Windows / Ubuntu

데스크톱 플랫폼 과제 — 두 데스크톱 OS에서의 작업 수행

교차 기기 전이

정보 전송 · 파일 공유 · 실행 컨텍스트 유지를 명시적으로 요구하는 과제

과제 유형: 단일 플랫폼 원자 과제 + 여러 기기에 걸친 복합 워크플로우 과제로 구성

모바일(녹색) · 데스크톱(주황) · 기기 간 전이(파랑)로 시각적으로 구분됩니다.

실험 설정

베이스라인

대표적인 오픈소스 GUI 에이전트 다수 — 최신 Grounding 및 RL 기반 모델 포함

에이전트 아키텍처

Planner–Grounder 2단계 구조 채택

스텝당 하나의 활성 플랫폼만 다루는 기존 패러다임 수용

평가 방식

가상 다중 OS 환경에서 원자 과제 성공률과 복합 워크플로우 완주율 측정

핵심 질문: 단일 기기에서 유능한 에이전트는 교차 기기 협업에서도 유능한가?

주요 결과: 4가지 핵심 발견

취약한 임계 경로

교차 기기 의존성은 단일 지점 실패로 전체가 무너지는 취약한 임계 경로를 만든다

인지·시각적 과부하

다중 기기 컨텍스트가 에이전트에게 인지적·시각적 과부하를 유발한다

논리적 의존성 장벽

과제 간 논리적 의존성이 워크플로우 완수를 가로막는다

플랫폼 편향

원자적 액션의 견고성에서 플랫폼 간 편향이 존재한다

핵심 시사점 단일 기기 능력과 교차 기기 역량 사이에 큰 격차 존재

오류 분석: 에이전트는 어디서 실패하는가

상태 전이 인식 부족

이전 기기에서 얻은 중간 결과를 다음 기기로 옮겨야 한다는 인식 자체가 부족

교차 플랫폼 추론 실패

이기종 UI와 동작 방식의 차이를 고려한 맥락적 추론의 한계

장기 의존성 관리 미흡

긴 워크플로우 전반에 걸친 의존성 추적과 컨텍스트 보존 실패

의의: 기존 벤치마크로는 보이지 않던 실질적 배치 장벽을 정량적으로 노출 — 지나치게 낙관적인 기존 평가 교정

결론

  • JarvisGUI: Android · Windows · Ubuntu를 아우르는 최초의 교차 기기 GUI 에이전트 동적 벤치마크
  • 타입 기반 원자 과제 모델링으로 복합 워크플로우의 자동 구성 · 동적 평가를 통합 프레임워크로 실현
  • SOTA 오픈소스 에이전트조차 상태 전이 인식 · 교차 플랫폼 추론 · 장기 의존성 관리에서 한계 노출
  • 코드 · 데이터 공개 예정 — GUI 에이전트의 실세계 배치를 위한 실용적 가이드라인 제시
기존 벤치마크에 보이지 않던 능력 격차를 드러내는 것이, 진정한 실사용 준비도 평가의 출발점입니다.
