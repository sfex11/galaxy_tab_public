배경: 왜 이 연구인가?

  • 데이터 주권 규제로 공공기관은 상용 클라우드 대신 오픈소스 모델의 온프레미스 배치가 필수
  • 에이전트는 기관이 제공하는 실시간(live) 정부 공공 API를 넘나드는 다단계 도구 호출 수행
  • 그러나 오픈소스 모델은 이 멀티스텝 설정에서 일관되게 저성능
  • 이 격차를 측정하는 기존 벤치마크가 전무
"에뮬레이션된 서비스나 LLM 사용자 시뮬레이터가 아닌, 실제 공공 API 위에서 벤치마크를 구축해야 한다."

두 가지 핵심 도전 과제

엔티티 코드 조회

단순 질의가 의존적 호출 체인으로 변환됨. 선행 호출의 출력(예: 코드)이 다음 호출의 입력으로 필요

모델 실패: 사전 조회 단계를 건너뜀

고카디널리티 응답

호출 하나가 0개~수십만 개 레코드 반환. 단일 바인딩 값이 존재하지 않아 데이터 축소 또는 fan-out 필요

모델 실패: 페이지네이션된 일부 결과로 조기 답변

Figure 1의 교훈 — 파인튜닝 전: API 키 조회 실패 + 첫 페이지만으로 불완전한 답변 / 파인튜닝 후: 출력 체이닝 + 다중 페이지 조회 + 결과 집계로 정확한 답변

평가 방법론: 3차원 평가

τ²-Bench의 reward_basis 방식 채택, RESPONSE/ENVIRONMENT는 BFCL 패러다임 따름

RESPONSE

모델의 최종 답변 검증 — 명확한 답이 요구되는 작업에 적용

ENVIRONMENT

호출 후 서버 상태 검증 — 결과가 시스템 상태에 의존하는 작업에 적용

ACTION

실행된 도구 호출 궤적 채점 — 모든 작업에 항상 포함

ACTION만으로는 불충분 — golden action을 포함해도 상태가 틀리거나, 반대로 다른 경로로 올바른 결과에 도달할 수 있음. 따라서 결과(RESPONSE·ENVIRONMENT)와 과정(ACTION)을 분리 평가

Phase A: 실행 기반 동적 그래프

  • 스켈레톤 그래프 — 2,318개 도구를 노드로 하는 방향 의존성 그래프. O(|V|²) 쌍 전체 LLM 채점은 불가능하므로 밀집 리트리버가 시그니처 임베딩으로 top-K 이웃 제한 동일 도메인 15 · 타 도메인 10
  • 엣지 제안 — 엣지 (u→v)는 u의 출력 필드가 v의 입력 파라미터에 바인딩됨을 의미. LLM 호출로 feasibility score se ∈ [0,1]과 binding set Be 산출
  • 실행 기반 업데이트 — 각 엣지를 실제 라이브 API 호출로 검증. 성공한 링크만 그래프에 유지
  • 동적 프루닝 — 실행에서 반복적으로 실패하는 엣지는 제거. 반복 루프가 진행될수록 실행 성공률이 상승하며 정제된 그래프 G⋆로 수렴

Phase B: 유형 기반 궤적 합성

핸드오프 유형 분류

그래프 위에서 각 output→input 핸드오프를 반환 값의 개수(카디널리티)로 라벨링 → 순차/비순차 궤적으로 구성

고카디널리티 해결

다중 레코드 응답을 유효한 순차 궤적으로 변환: bounded fan-out(범위 내 확장) 또는 deterministic reduction(결정론적 축소)

쿼리 생성 및 검증

각 궤적에 자연어 한국어 쿼리와 정답을 생성하고 검증 → 실행 가능한 멀티스텝 학습 데이터셋 완성
