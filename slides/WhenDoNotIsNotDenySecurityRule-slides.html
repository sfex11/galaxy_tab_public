"하지 마라"가 거부(deny)가 아닐 때

CLAUDE.md의 보안 규칙 vs 내장 통제의 간극 측정

Ting Yan

배경: 코딩 에이전트와 보안 지시

LLM의 발전으로 보안 경험이 적은 사람도 소프트웨어와 코딩 에이전트를 구축하게 되었고, 개발자는 자연어로 에이전트에 보안 규칙을 작성합니다.

"시크릿을 로그에 절대 쓰지 마라"
"프로덕션 데이터 삭제 전 반드시 물어봐라"
"리뷰 브랜치를 통해서만 푸시해라"

이 규칙들은 CLAUDE.md 같은 지시 파일에 평문으로 작성되지만, 어떤 규칙이 실제로 강제되는지 피드백이 없습니다.

핵심 구분: "do not" vs deny

"do not" — 자연어 지시

  • 모델이 해석하는 텍스트
  • 시크릿인지, 로그인지 모델이 판단
  • 확정적 실행 보장 없음
  • 프롬프트 주입에 취약

deny — 내장 통제

  • 플랫폼이 직접 차단
  • 명령 실행 전에 차단됨
  • 확정적(deterministic) 적용
  • 권한 규칙, 샌드박스 등

문제: 두 유형의 규칙이 동일한 자연어 형태로 작성되어, 개발자는 구별할 수 없습니다.

연구 질문

RQ: 공개 CLAUDE.md 파일에서 추출된 보안 규칙 중, 별도 코드 없이 동일한 규칙을 적용할 수 있는 내장 Claude Code 통제가 존재하는 비율은 얼마인가?

기존 연구들은 제품이 어떤 통제를 제공하는지 또는 개발자가 어떤 내용을 작성하는지를 따로 조사했지만, 작성된 규칙이 기존 통제와 얼마나 일치하는지는 측정하지 않았습니다.

관련 연구와 본 연구의 차이

결과: 규칙 유형별 분석

보안 이슈 유형 규칙 예시 내장 통제 가능성
명령 실행 제한 "npm publish 절대 실행 금지" 높음 — deny 규칙
파일 시스템 접근 "프로덕션 DB 파일 읽지 마라" 보통 — 샌드박스
시크릿 관리 "고객 시크릿을 로그에 넣지 마라" 낮음 — 모델 해석 의존
승인/인가 "리뷰 브랜치로만 푸시해라" 낮음 — 모델 해석 의존
파괴적 행동 "삭제 전 반드시 확인해라" 낮음 — 모델 해석 의존

특정 명령 차단은 통제와 잘 일치하지만, 맥락 판단이 필요한 규칙은 대부분 모델에 맡겨집니다.

논의: 사용 가능한 보안(Usable Security) 문제

CLAUDE.md는 쓰기 전용(write-only) 보안 채널입니다.

규칙 작성 — 개발자가 평문으로 보안 규칙을 씁니다

피드백 없음 — 파일도 에이전트도 강제 여부를 알려주지 않습니다

은폐된 분기 — 플랫폼 강제 규칙과 모델 해석 규칙이 같은 형태로 섞여 있습니다

거짓 안심 — "절대 쓰지 마라"라고 썼어도 시크릿이 로그에 닿을 수 있습니다

한계점

  • 추출 재현율 66.3% — 키워드 기반 추출이 적격 규칙의 약 1/3을 놓침
  • 단일 플랫폼 — Claude Code와 CLAUDE.md에만 한정
  • 시점 고정 — Claude Code 통제 목록을 2026-08-13에.freeze
  • LLM 분류기 의존 — 1차 분류에 모델 사용, 인간 검증은 샘플에만 적용
  • 공개 저장소 편향 — 사설/엔터프라이즈 CLAUDE.md는 포함되지 않음

이 한계들은 보고된 비율이 상한선에 가까울 가능성을 시사합니다 — 실제 간극은 더 클 수 있습니다.

기여 및 결론

기여 1: 간극 측정

  • 481개 공개 CLAUDE.md 분석
  • 4,661개 후보 → 870개 보안 규칙
  • 내장 통제 일치율: 4.4~16%
  • 범주별(인가, 파괴, 시크릿 등) 그룹화

기여 2: 문제 식별

  • CLAUDE.md = 쓰기 전용 보안 채널
  • 강제 규칙과 해석 규칙이 동일 형태
  • 피드백 루프 부재
  • 사용 가능한 보안 관점의 설계 문제

보안 도구는 사람이 안전한 선택을 하도록 돕아야 하며, 모든 보안 작업을 사용자에게 전가해서는 안 됩니다.
