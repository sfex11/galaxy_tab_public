기능 테스트 통과만으로는 충분하지 않다

Passing Functional Tests Is Not Enough for Software Engineering Agents

Xin He, Yanlin Wang†, Mingwei Liu, Jiachi Chen, Hongyu Zhang, Guanbin Li

Sun Yat-sen University · Zhejiang University · Chongqing University

arxiv.org/abs/2609.04167

배경: 리포지토리 수준 벤치마크의 발전

  • HumanEval, MBPP → 함수 수준 코드 생성 평가에서 출발
  • SWE-Bench → 실제 GitHub 이슈-PR 쌍으로 구성된 리포지토리 수준 수리 표준 벤치마크
  • SWE-Agent, OpenHands, Agentless → 실행 가능한 기능 테스트로 패치 평가하는 코딩 에이전트 등장
  • 이후 확장: 다국어, 엔터프라이즈 프로젝트, 보안, 멀티모달 등

그러나 기존 벤치마크는 단일 평가 기준을 사용 — "생성된 패치가 기능 테스트를 통과하는가?"

문제 제기: 기능적으로 올바른 패치 ≠ 수용된 패치

실제 소프트웨어 개발에서는 이슈를 해결하고 테스트를 통과해도 PR이 거절될 수 있습니다.

SWE-Gate 소개

리뷰 제약 준수를 기능 정확성과 함께 평가하는 최초의 리포지토리 수준 벤치마크

303

리포지토리 수준 수리 인스턴스

75

다양한 소프트웨어 도메인의 오픈소스 Python 리포지토리

6

소프트웨어 도메인

  • 실제 PR 리뷰 코멘트에서 자연어 제약을 추출
  • 실행 가능한 기능 테스트와 제약 테스트를 분리 제공
  • 비준수 패치(non-compliant)와 골드 패치(gold) 쌍 제공

구성 전략: Constraint-First

리뷰 제약은 독립된 규칙이 아니라 특정 기능·코드 맥락에 묶여 있으므로, 제약을 중심으로 인스턴스를 구성

1
리포지토리 선택
실제 리뷰 토론이 있는 오픈소스 리포지토리 선별
2
제약 추출
LLM 기반 처리로 원자적 리뷰 제안 추출 및 검증 가능한 제약 선택
3
인스턴스 합성
버그 패턴·엔지니어링 의도·적용 조건을 추상화하여 별도 리포지토리에 구현
4
품질 보증
기능/제약 테스트 분리 검증 및 비준수·골드 패치 확인
  • 원본 리뷰 요구의 진정성 보존 + 하나의 제약을 여러 맥락으로 확장
  • 직접적인 솔루션 암기(mitigation of memorization) 완화

인스턴스 구조와 평가 프로토콜

각 인스턴스는 이중 차원(dual-dimension) 평가를 지원합니다.

구성 요소역할검증 내용
기능 테스트이슈 해결 능력 측정보고된 이슈가 기능적으로 해결되었는가?
제약 테스트리뷰 제약 준수 측정기능적 수리가 추가 수용 요건을 충족하는가?
비준수 패치분리 가능성 시연기능은 통과하지만 제약은 위반
골드 패치공존 가능성 시연기능과 제약 모두 통과

LLM 기반 판정이 아닌 결정적(deterministic) 실행 테스트로 두 차원을 모두 평가 → 주관성·편향 제거

실험 설정

평가 모델

  • 서로 다른 능력 수준의 4개 LLM 백엔드
  • 동일한 Mini-SWE-Agent 스캐폴드 하에 평가

평가 지표

  • 기능 성공률: 기능 테스트 통과 여부
  • 완전 수리 성공률: 기능 + 제약 테스트 동시 통과

연구 질문 (RQ)

RQ1 이중 평가에서 코딩 에이전트는 어떻게 수행되는가? · RQ2 명시적 제약 안내가 수리 결과에 어떤 영향을 주는가? · RQ3 어떤 리뷰 제약 범주가 여전히 어려운가?

RQ1: 기능 통과 후에도 드러나는 실패

221

644개의 기능 테스트 통과 수리 중 221개(약 34%)가 리뷰 제약 위반으로 실패

기능 전용 평가가 숨기는 것

  • 기능 테스트 통과 ≠ 완전한 수리 요건 충족
  • 에이전트의 실제 수용 가능성을 과대평가
  • 이슈 해결 능력과 제약 준수 능력은 분리된 차원

Answer to RQ1: 기능 전용 평가는 리포지토리 수준 수리 능력을 실제보다 높게 측정합니다.

RQ2: 명시적 제약 안내의 효과

리뷰 제약을 프롬프트에 명시적으로 제공하면 수리 결과가 어떻게 달라지는가?

긍정적 효과

제약 안내는 에이전트가 수용 요건을 인식하고 준수하는 패치를 생성하도록 유도하여 제약 준수율 개선

남는 한계

그럼에도 불구하고 일부 제약은 여전히 충족되지 않아, 안내만으로 완전한 해결이 되지 않음

Answer to RQ2: 명시적 제약 안내는 수리 품질을 향상시키지만, 제약 준수 실패를 완전히 해소하지는 못합니다.

RQ3: 여전히 어려운 제약 범주

리뷰 제약을 유형별로 분석한 결과, 범주에 따라 난이도 편차가 뚜렷합니다.

구현 관례

리포지토리 고유 컨벤션은 암묵적 지식을 요구하여 에이전트가 파악하기 어려움

호환성 유지

기존 인터페이스를 변경하지 않는 설계는 추가적인 엔지니어링 판단 필요

의미론 보존

예외 동작 등 확립된 의미를 유지하면서 기능을 구현하는 것이 어려움

Answer to RQ3: 프로젝트 맥락에 의존하는 제약(관례·호환성·의미론)이 에이전트에게 가장 큰 도전 과제로 남습니다.

결론

"기능 테스트를 통과하는 것이 전부가 아니다" — SWE-Gate는 리뷰 제약 준수라는 새로운 평가 차원을 열어, 코딩 에이전트의 실제 수용 가능성을 더 정확하게 측정합니다.

  • 기능 성공과 제약 준수는 분리 가능한 평가 차원
  • 644개 기능 통과 수리 중 221개(34%)가 제약 위반 → 기존 평가의 과대평가 확인
  • 미래 방향: 제약 준수 능력을 갖춘 에이전트 설계와 학습으로 확장
