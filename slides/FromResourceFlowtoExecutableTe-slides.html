Petri-Net 유도 LLM 테스트 생성

동시성 상태유지 Rust API를 위한 접근법

Kaiwen Zhang, Guanjun Liu

Tongji University, Shanghai, China

동시성 상태유지 API: 왜 테스트가 어려운가

1

강한 상태 의존성

많은 결함은 유효한 접두사가 비자명한 자원 구성을 확립한 후에만 나타남

2

의미적 규율 필요

접두사가语义적으로 유효하지 않으면 이후 관찰은 무의미해짐

3

부분 순서 수준의 동시성

긴 순차열은 노출해야 할 경쟁을 우연히 직렬화하면 무용함

Rust의 타입 시스템은 광범위한 메모리 오류를 제거하지만, 라이브러리가 상위 수준 프로토콜을 준수함을 증명하지는 않는다.

기존 접근법의 한계

모델 기반 테스팅

  • 합법적 상태·자원 흐름·경계 조건 기술 가능
  • 의미적 제어 우수

추상 시나리오 → 실행 코드 변환에 대량의 수작성 코드 필요

직접 LLM 프롬프팅

  • 코딩 부담 감소
  • 빠른 프로토타입 가능

사전조건 위반, 얕은 테스트, 동시성을 우연한 순차열로 축소

핵심 간극: 형식적 시나리오 설계와 저비용 테스트 구체화 사이의 빈틈

SyncPetri: 핵심 설계 원칙

모델은 의미를 작성하고, LLM은 코드를 작성한다

Petri Net의 역할

  • 의미적 의도 지정
  • 자원 흐름 표현
  • 도달 가능성·충돌·버그 관련 돌연변이 명시

LLM의 역할

  • 라이브러리 특정 문법 실현
  • 태스크 스캐폴딩 작성
  • 단언(assertion) 작성

의미적 책임은 LLM 외부에 유지하면서, 코드 실현은 저비용으로 유지

Petri Net 자원 모델: mpsc 예시

유계(bounded) mpsc 채널의 추상 장소(Place) 정의

장소 (Place) 의미
LiveSender(s)송신자 핸들 s가 존재하며 송신측 연산 가능
LiveReceiver(r)수신자 핸들 r이 존재하며 수신 또는 종료 가능
Open(c) / Closed(c)채널 c가 열림 / 수신 측에서 닫힘
Permit(s,c)송신자 s가 채널 c에 예약된 퍼밋 보유
Cap(c,n)채널 c에 n개의 예약되지 않은 버퍼 슬롯
Buf(c,n)채널 c의 추상 버퍼 항목 수
Obs(x)계측이 방출하는 런타임 관찰 토큰

송신자, 수신자, 퍼밋, 버퍼, 관찰 의무를 색인 있는 토큰과 전이로 표현

버그 모델: 4가지 결함 패밀리

Bpre 사전조건 위반

추상 선행조건이 위반되었음에도 연산이 부정하게 성공

예: 닫힌 채널로 송신 성공

Bstate 사후 상태 불일치

연산 실행 후 자원 회계, 소유권 이전, 정리 로직이 명세와 다름

예: 퍼밋 회계 불일치

Brace 경쟁 민감도

스케줄 의존적 인터리빙이 상위 프로토콜이 금지하는 관찰 순서를 노출

예: 값 업데이트 후 알림 누락

Blive 활성성·블로킹

영구 블로킹, 깨우기 누락, 종단 프로토콜 상태 도달 후 비종료

예: close 경쟁 후 비종료

SyncPetri 5단계 파이프라인

1
자원 모델
API 자원·수명주기·인과 의존성을 색인 Petri Net으로 정식화
2
시나리오 합성
합법적 깊은 상태, 준법적 경계, 부분 순서 동시 시나리오 도출
3
LLM 구체화
제약 프롬프트 + 구조적 수리 루프로 실행 가능한 Rust 코드 생성
4
스케줄 탐색
Petri 유도 스케줄 형성으로 고충돌 동시성 골격 우선 탐색
5
오라클 판정
다층 의미 오라클로 합성 실패와 의미적 위반 구분

시나리오 합성: 3가지 패밀리

합법적 깊은 상태

Petri Net의 도달 가능한 마킹에서 비자명한 자원 구성을 확립한 후 테스트 관찰 수행

예: 퍼밋 획득 → 수신자 종료 → 퍼밋 기반 송신 검증

준법적 경계 탐색

의도적으로 하나의 전이 조건을 위반하여 사전조건 집행 결함(Bpre)을 프로브

예: 닫힌 채널에 일반 송신 시도

부분 순서 동시성

인과 독립 전이들을 병렬 태스크로 배치하여 스케줄 의존적 경쟁(Brace) 노출

예: 송신과 close를 동시에 실행

LLM 구체화: 프롬프트 계약과 수리 루프

프롬프트 계약 (Prompt Contract)

  • 추상 시나리오 단계를 구조화된 템플릿으로 제공
  • 어댑터 스키마로 API 호출 패턴 규정
  • LLM은 문법·스캐폴딩만 담당, 의미적 선택 불가

구조적 수리 루프

  • 생성 코드를 정적 분석으로 검증
  • 구조적 불일치 발견 시 피드백과 함께 재생성
  • 시나리오 자체는 변경하지 않고 코드만 수정

국소 충실성 (Local Faithfulness): 각 추상 단계가 구체적 Rust 연산에 일대일로 대응되어야 함 — LLM이 단계를 생략·재배열·추가 불가

Petri 유도 스케줄 탐색

Loom과 호환되는 하니스(harness)를 위해 Petri Net의 충돌 구조를 활용한 스케줄 형성

고충돌 골격 우선

Petri Net에서 전이 간 충돌(conflict)이 많은 스케줄 순서를 우선적으로 선택하여 경쟁 민감 버그 노출 확률 극대화

Loom과의 통합

스케줄 형성이 Loom의 내부 검색을 대체하지 않고, 하니스 선택을 개선하여 더 진단적 유용한 인터리빙을 탐색하도록 유도

목표: 길이가 아닌 부분 순서 구조에서 진단 가치가 발생

다층 의미 오라클

합성 실패(우리의 파이프라인 문제)와 의미적 위반(라이브러리 버그)을 명확히 구분

구조 오라클

생성 코드가 어댑터 스키마와 일치하는지 검증 — 불일치 시 합성 실패로 분류

결과 오라클

런타임 반환값이 Petri Net 마킹에서 예상한 결과와 일치하는지 확인

불변량 오라클

API 수준 불변량(자원 회계 일관성 등) 위반을 탐지

활성성 오라클

종단 프로토콜 상태에서 비종료·영구 블로킹 탐지

평가: 연구 질문과 프로토콜

RQ1

아티팩트 제약 프롬프트가 실행 가능한 Tokio 코드를 생성할 수 있는가?

RQ2

생성된 러너가 스케줄 민감적 구조를 보존하는가?

RQ3

피드백 수리가 시나리오 변경 없이 구체적 불일치를 복구할 수 있는가?

RQ4

아티팩트 경계가 일반 파이프라인을 대상 특정 모델로부터 격리하는 데 충분한가?

평가 차원: 실행 가능성 · 구조적 충실성 · 깊은 상태 도달 가능성 · 경계 실패 수율 · 충돌 커버리지

기여 요약과 한계

5가지 기여

  • 자원 운반 전이에 대한 Petri-Net 유도 시나리오 합성의 형식화
  • 추상 Petri-Net 단계를 구체적 Rust 실행에 연결하는 어댑터 스키마와 국소 충실성 계약
  • 합법 도달, 준법적 경계 돌연변이, 부분 순서 동시성을 통합하는 시나리오 표현
  • 생성 실패와 의미적 실패를 구분하는 제약 구체화 루프와 다층 오라클
  • Loom 호환 하니스를 위한 Petri 유도 스케줄 형성 방법

명시적 한계

  • 자원 모델, 어댑터, 시나리오 불변량은 수동 작성 필요
  • 스케줄 형성은 Loom의 내부 검색을 개선할 뿐 대체하지 않음
  • 완전 자동 동시성 검증이 아닌, 모델링 노력과 의미적 제어 간 트레이드오프
