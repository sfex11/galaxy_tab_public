연구 배경: LLM 기반 연구 자동화의 숨은 가정

자동화되는 과학 워크플로우

  • 연구 아이디어 발상부터 실험 실행, 코드 생성까지 LLM이 지원
  • 단계들이 연구 에이전트 안에서 결합되는 추세
  • 신뢰할 수 있는 실행은 아이디어가 방법을 충분히 명시한다는 가정에 의존

명세 격차의 위험

  • 방법을 정의하는 선택이 누락·모호·모순되면?
  • 에이전트는 명확히 하거나, 근거 없는 가정을 조용히 도입
  • 결과: 작동하지만 전혀 다른 방법을 구현하는 코드 → 재현성 실패

핵심 개념: Codification Readiness

아이디어가 새롭고 가치 있는가가 아니라, 제안된 방법이 의도대로 구현될 준비가 되었는가를 묻는 문제

Codification-Ready

유능한 구현자나 코딩 에이전트가 지원되지 않는 가정 없이 충실한 초기 구현(실험 프로토타입)을 만들 수 있음

Not Ready

두 유능한 구현자가 실질적으로 다른 방법 정의 선택을 할 수 있으나, 어느 쪽이 의도인지에 대한 증거가 없음

그럴듯한 구현은 미해결 선택을 감출 뿐 — 신뢰할 수 있는 모델은 격차를 찾아내고 해결에 필요한 정보를 요청해야 한다

660

단일 결함(single-defect)

163

실제(real-world) 격차
GitHub 이슈 + 재현성 보고서

497

통제된 합성 격차
구현-준비 완료 참조에 주입

각 인스턴스에는 목표 결함 + 근거가 뒷받침되는 해결책 + Level-1 3개 / Level-2 10개 범주 라벨이 포함

데이터 수집: 자연 발생 격차 + 통제된 합성

실제 격차 (163개)

  • 구현자들이 실제로 마주친 명세 격차
  • GitHub 이슈 스레드 + TMLR 재현성 보고서
  • 논문·코드베이스·재현 아티팩트에서 근거가 뒷받침되는 해결책 확보

통제된 합성 인스턴스 (497개)

  • 독립 검증된 성공적 재현이 있는 논문에서 참조 확보
  • 구현-핵심 세부사항 정확히 하나만 변경
  • 정밀한 반사실(counterfactual) 목표 제공

인간 검증: 맹검 리뷰 + 독립 재주석으로 라벨 신뢰성 확보

3가지 평가 태스크

1
Readiness 판단
명세만 보고 구현 준비 여부를 판단 (Task 1)
2
결함 위치 찾기
결함 힌트 없이 병목 지점을 국소화 (Task 2)
3
명확화 행동 생성
결함이 주어지면 해결에 필요한 정보를 도출 (Task 3)

병목 발견(blocker discovery)과 병목 파악 후의 행동(action)을 의도적으로 분리

결함 분류 체계: Level-1 3개 · Level-2 10개

모호성(Ambiguity)

  • 모호한 정의
  • 모호한 절차

불완전성(Incompleteness)

  • 방법 절차 / 모델 구조
  • 데이터 명세
  • 설정 프로토콜
  • 평가 명세

불일치(Inconsistency)

  • 상충하는 목적
  • 상충하는 모델 설계
  • 상충하는 형식 정의

벤치마크 검증: 품질은 어떻게 보장되었나

맹검 리뷰
구현 지향적 명세 명확화를 측정함을 확인

통제된 합성 인스턴스도 자연 발생 격차의 타당성과 워크플로우 개연성을 보존

실험 설정

평가 대상

13

최신 LLM 13개 모델 전수 평가

주요 지표

  • Task 1: Macro-F1, UnsafePass, 근거 점수
  • Task 2: 위치 정확도(Loc-Acc), Macro DRR
  • Task 3: Macro-CAS, 충분성, 무가정(No-Assumption)

주요 결과: 극적인 격차

9.6%

Macro Defect Recovery Rate
실제 인스턴스 — 힌트 없이 결함을 찾아 복구

80.6%

Macro Clarification Action Success Rate
결함이 주어졌을 때 — 필요한 정보 도출 성공

같은 최고 성능 모델 — 결함을 찾는 것은 거의 실패하지만, 결함을 알려주면 유용한 명확화를 수행

오라클 연구: 명세 격차가 진짜 병목임을 입증

14% 98%

Gold resolution(결핍된 정보)을 제공하자
다운스트림 codification-ready 비율이 14% → 98%로 급등

해석: 모델의 실패는 코드 작성 능력 부족이 아니라, 구현에 필요한 정보가 명세에 없기 때문 — 명세 격차의 해소가 자동화 신뢰성의 선결 조건

오류 분석: 병목은 어디에 있나

  • 모든 평가 모델에서 결함 위치 찾기(localization)가 주요 병목
  • 준비성 판단이 근거에 충분히 근거하지 못하는 경향 (약한 근거 기반)
  • 위치 찾기 실패는 주로 잘못된 목표 선택에서 비롯
  • 명확화 오류는 주로 범위 부족 — 결함은 겨눴으나 완전히 해결하지 못함
  • 필수 연산을 사소한 세부사항으로 취급하는 사례 등 대표적 실패 유형 확인

"안내받으면 잘한다" — 그러나 독립적으로 막힌 지점을 찾아내는 능력이 결여

결론

  • Codification readiness를 발상(ideation)과 실행(execution) 사이의 빠진 연결고리로 형식화
  • 준비성 판단 · 결함 위치 찾기 · 명확화 행동 생성의 3가지 평가 기능 정의
  • 실제 격차 163개 + 통제 합성 격차 497개 = 근거 기반 660 인스턴스 벤치마크 공개
  • 결함 위치 찾기가 주 병목 — 오라클 정보 제공 시 codification-ready 14% → 98%
  • 코딩 전 명세 명확화가 신뢰할 수 있는 연구 자동화의 핵심 단계
