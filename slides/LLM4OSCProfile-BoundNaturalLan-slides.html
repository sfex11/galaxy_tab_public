Profile-Bound Natural Language Control with Deterministic Validation for Open Sound Control

Yuan-Yi Fan — Los Angeles, yyf@yuanyifan.com

문제 정의

OSC는 실시간 파라메트릭 제어의 지배적 프로토콜이지만, LLM이 OSC를 생성할 때 치명적 결함이 발생합니다.

01

주소 환각
존재하지 않는 OSC 주소를 생성

02

타입 태그 오처리
인자 유형(f, i, s)을 잘못 매핑

03

의역 실패
다른 표현의 같은 의도를 인식 못함

라이브 공연·가상 프로덕션에서 이러한 오류는 용인 불가합니다.

Open Sound Control (OSC)

실시간 오디오·미디어 제어를 위한 UDP 기반 와이어 프로토콜

핵심 과제

각 기기마다 고유한 주소 테이블 → 수동 매핑은 복잡도에 따라 불가능

LLM4OSC 아키텍처 개요

제안–검증–송신(Propose–Validate–Send) 파이프라인

1
자연어 입력
"게인을 반으로 줄여줘"
2
NL 백엔드
B0~B3가 Intent JSON 제안
3
Refine + Gate
심볼릭 보정·검색 게이트
4
Tier 3
결정론적 검증→클램핑→인코딩→UDP 송신

설계 불변성: 확률적 컴포넌트는 제안만 하고, Tier 3가 결정하고 송신한다. Intent JSON과 와이어 바이트 사이에 ML 모델이 없다.

디바이스 프로파일과 Intent JSON

프로파일 P = (D, V, M)

  • device_id, version, patterns
  • 각 패턴: address, type_tags, slots, ranges
  • 검색 메타데이터: tags, description
  • 인간이 커밋, 명시적 버전 바인딩

프로파일이 폐쇄 세계: M 외 주소는 전송 불가

Intent JSON 계약

  • 성공: kind:intent + pattern 필드 + args
  • 거부: kind:refusal + 사유 열거

거부 사유: unknown_pattern, ambiguous_pattern, missing_slot, out_of_range

예시: {"kind":"intent","pattern_id":"gain_set","address":"/gain","type_tags":"f","args":[0.5]}

검색, 정제, 게이트

검색 (Retrieval)

토큰 오버랩 랭킹: tags(×3) + description → Top-k=8 패턴 추출. B0와 동일 랭킹 사용.

슬롯 채우기 (Slot Fill)

퍼센트("반"→0.5), 음이름(A440), 팬 센터 구문, 트랜스포트 키워드를 결정론적으로 파싱

NL 정제 (Refine, B1–B3)

LLM 제안 후, 검색이 pattern_id 오버라이드, 슬롯 채우기가 원본 NL에서 args 재추출. 피드백은 다른 LM이 아닌 결정론적 프로파일 정책에서 옴.

검색 게이트 (Retrieval Gate, B1–B3)

Top score=0 → unknown_pattern / 동점 → ambiguous_pattern / 필수 슬롯 불가 → missing_slot → OOV wrong-send 차단

NL 백엔드 비교 (B0–B3)

ID 메커니즘 역할 Refine + Gate
B0 검색 + 슬롯 채우기 프로덕션 기본값 —
B1 Qwen2-0.5B zero-shot 사전학습 하한선 적용
B2 B1 + 8개 few-shot 프롬프트 상한선 적용
B3 B1 + LoRA 파인튜닝 선택적 미세조정 적용

LoRA 설정: r=8, α=16, 1 epoch, Apple MPS, ~270 train / 67 val rows, frozen goldens 제외

어댑터 가중치는 gitignored, 모델 카드에 레시피 기록

의미 정확도

pattern_id, address, args 일치

Wrong-Send Rate

불일치인데 Tier 3 통과하여 전송될 비율

Paraphrase Gap

(acc_literal − acc_paraphrase) × 100

릴리즈 게이트: wrong-send = 0% 이고 semantic accuracy ≥ 90%

결과: Track C 전체 현황

게이트 적용 후 모든 백엔드가 프리즌 게이트 통과 — 111 pytest 케이스 전부 패스

B3+refine+gate 100% 100% 0 0% ~3.6 s

B0가 라이브 제어 기본값 유지 — 지연 차이 ~10⁵배

B2: 62.5% → 100% 회복 분석

2026-06-28 베이스라인: raw B2는 리터럴 62.5% / 의역 62.5%에 non-zero wrong-send

변경 사항 B2에 미치는 효과
프로파일 태그 + 슬롯 파서 검색 가능; 인자가 LLM 단위 파싱에 의존하지 않음
NL 정제 (B1–B3) 잘못된 pattern_id 오버라이드; args 재추출 → 의역 62.5%→100%
검색 게이트 거부를 B0와 정렬 → 리터럴 게이트 통과

핵심 통찰

의역 회복은 태그/슬롯 + 정제가 주도 (해당 스위트에 거부 없음)

주의

LLM 후처리 정책이 B1/B2를 B3 정확도에 맞춤 — 가중치의 성과가 아닌 아키텍처의 특성

역사적 추적 및 스위트 상세

스냅샷 B2 리터럴/의역 게이트 비고
2026-06-28 62.5% / 62.5% 불통과 Raw LLM
2026-06-29 — — B0 100%/100%; B3 거부 실패
2026-07-07 100% / 100% 통과 + 검색 게이트

LoRA-only (정제 없음) 실험

의역 62.5%에 37.5% wrong-send — 초기 B2와 동일한 실패 클래스. 정제가 없으면 LoRA만으로는 안전하지 않다.

핵심 발견 (F1–F5)

F1

Wrong-Send Rate의 판별력

정책 적용 전, 역사적 B2는 B1보다 정확도가 높았으나 여전히 wrong-send 발생

F2

프로파일 엔지니어링으로 의역 해결

LoRA 없이도 의역 게이트 통과 가능 (lora_recommended=false)

F3

심볼릭 정제가 B2 도약 설명

62.5% → 100%는 정제가 주도, 가중치 변경이 아님

F4

검색 게이트는 거부 안전에 필수

LLM 경로에서 게이트 없이는 OOV/모호/누락 wrong-send 발생

F5. 동일 정확도 ≠ 동일 프로덕션 선택: 라이브 제어에서는 지연 때문에 B0 우선

논의 및 한계

핵심 관점

NL 제어를 폐쇄 API 위의 인터페이스 컴파일로 취급. 작은 프리즌 스위트에서 정책(프로파일+정제+게이트)이 가중치(few-shot/LoRA)보다 지배적.

한계

  • 소규모 벤치마크 (8+8+4, 기기 1개)
  • 프로파일 엔지니어링 교란 변수
  • 정제+게이트가 약한 LLM 제안을 masking
  • LLM 지연 ~3–4s vs <50ms 목표
  • 사용자 연구 없음, 합성 LoRA 데이터 (~270행)

향후 과제

100–500+ 케이스 + 2번째 기기 확장 | 정제 vs 게이트 vs LoRA 개별 제거 실험 | wrong-send 인지 훈련 | MCP 서버 인터페이스 | 다중 인자/번들 스키마 v2

결론

  • LLM4OSC: 프로파일 기반 NL→OSC 변환에 결정론적 Tier 3 검증 제안
  • Wrong-Send Rate이 정확도가 숨기는 불안전한 성공을 드러냄
  • 풍부한 프로파일 + 슬롯 파서로 LoRA 없이 의역 게이트 통과
  • 역사적 few-shot B2는 NL 정제 후에만 100% 달성
  • LLM 경로의 거부 안전에는 검색 게이트 필수
  • B0가 라이브 제어 기본값으로 유지

"진실을 계약에 두고, wrong-send를 측정하며, 검색이 비면 거부하라."
