코딩 에이전트를 위한 컴팩트 문서화

A Benchmark, an Optimizer, and Why It Does Not Transfer

Md Shohel Arman (Daffodil International University) · Igor Molybog (University of Hawai'i at Mānoa)

"자연어 문서가 코딩 에이전트의 이슈 해결에 도움이 될까?
그것을 만들고 평가할 도구를 만들어 답을 찾았다 — 답은 '아니오'였다."

연구 동기: 왜 문서인가?

현실의 제약

  • 충분히 큰 저장소는 전체를 에이전트 컨텍스트에 넣는 것이 불가능하거나 지나치게 비용이 큼
  • 에이전트는 전부 읽지 못한 파일을 편집해야 함
  • 컨텍스트 속 고수준 설명이 코드의 의도와 계약을 대신 전달

결함 있는 지도

  • 실제 저장소에서 에이전트는 이미 이런 방식으로 동작 중
  • 불완전하거나 잘못된 설명은 "결함 있는 지도"처럼 작동
  • 가설: 고충실도 설명이 읽지 못한 소스를 대신하면 실제 이슈 해결에 도움이 될 것이다

4단계 연구 접근

1
문서화의 가치 규명
문서가 도움 되는 조건과 가치를 좌우하는 두 속성(완전성·컴팩트함)을 밝힘
2
왕복 벤치마크
설명으로 재생성한 코드가 원본 테스트를 통과하는지 측정, 암기 통제
3
설명 작성기 최적화
벤치마크를 최적화 신호로 사용해 완전한 충실도에 도달, 미확인 파일로 일반화
4
다운스트림 검증
연구의 동기였던 질문: 더 나은 문서가 실제 이슈 해결에 도움이 되는가?

핵심 주장: "완전성, 길이 아닌" — 설명 품질에 관한 주장은 성립. 다만 다운스트림(이슈 해결) 주장은 성립하지 않음.

기존 왕복 연구는 진단 도구였다면, 본 연구는 왕복 점수를 최적화 목표로 전환

문서는 언제 도움이 되는가?

문서는 코드가 노출하지 않는 의도(intent)나 계약(contract)을 담고 있을 때만 도움이 된다. 읽을 수 있는 코드를 재진술하는 설명은 아무것도 추가하지 않는다.

실험 예시: 접근 제어 정책 엔진

  • is_allowed는 단순히 규칙을 공급 순서대로 훑어 첫 매치 반환
  • 진짜 계약 — "우선순위로 평가하되, 같은 우선순위면 deny가 allow에 우선" — 은 설명에만 존재, 코드 동작엔 전혀 보이지 않음
  • 이 계약을 지키는 resolve 메서드 추가 과제에서, 설명 제공 시 성공이 뒤집힘

가치를 좌우하는 두 속성

  • 완전성 (Completeness) — 코드의 의도와 계약을 빠짐없이 담는가
  • 컴팩트함 (Compactness) — 완전성을 해치지 않는 선에서 짧게

왕복(Roundtrip) 벤치마크 설계

1
원본 코드
실제 저장소의 파일 + 원본 테스트 스위트
2
설명 작성 (Describer)
코드를 자연어 설명으로 변환
3
코드 재생성
설명 만으로 코드를 다시 생성
4
원본 테스트 실행
재생성 코드가 원본 테스트를 통과하면 점수 부여 (동등성 오라클)

암기(오염) 통제
모델이 원본 코드를 이미 알고 있는지 차단

압축 측정
설명 길이 대비 충실도 정량화

테스트를 오라클로
SWE-bench의 단일 파일·테스트 오라클 규율 계승

벤치마크 결과: 완전성, 길이가 아니다

발견

  • 충실도의 주요 동인은 완전성
  • 완전성을 넘어선 장황함은 아무것도 추가하지 않음
  • 완전성만 유지되면 압축해도 성능 손실 없음

검증

  • 외부 문서화 도구(OpenWiki)와 비교하여 벤치마크 타당성 확인
  • 길이가 충실도를 해치는지 별도 실험 — 길이 그 자체는 해가 되지 않음
  • 문서 압축·시그니처 중심 연구 결과와 정합적인 통제된 설명 제공

uplift tracks completeness, while verbosity beyond completeness adds nothing.

설명 작성기(Describer) 최적화

1
벤치마크를 최적화 신호로 — 왕복 충실도 점수를 피드백으로 사용하는 자기개선 루프 구축
2
프롬프트 진화 — 후보 지시문 생성·선택, 이전 점수를 컨텍스트에 반영해 반복 개선
3
완전한 충실도 도달 — 발견된 설명 작성 프롬프트가 재생성 충실도 100% 달성
4
일반화 확인 — 학습에 쓰이지 않은 미확인(held-out) 파일에서도 동일 성능

수렴한 프롬프트의 성격

완전하면서(complete) 컴팩트한(compact)

이것이 의미하는 것

이 Null은 진짜인가? — 검증 장치들

긍정 대조군(Positive Control) — 평가 파이프라인이 실제 개선이 존재할 때 이를 탐지할 수 있음을 사전에 확인 → null이 평가의 맹점이 아님을 입증
모델 약함이 원인 아님 — 약한 모델과 강한 모델 모두에서 동일한 null → 능력 부족 탈풍
외부 벤치마크 확인 — SWE-ContextBench 기반 실험에서도 같은 결론 → 자체 픽스처의 편향 아님
파일 편집 없이도 — 파일을 로드하지 않고 편집하는 조건에서도 결론 유지

소스 없음 문서 = 코드의 대체재 → 큰 향상

소스 있음 문서 = 중복 정보 → 향상 없음, 길면 미약한 손해

3가지 기여

1 왕복 벤치마크

설명 작성기(describer)를 "설명만으로 재생성한 코드가 원본 테스트를 통과하는가"로 채점 + 압축 측정 + 암기 통제

2 통제된 분석 + 자기개선 루프

완전성과 길이의 효과를 분리해 규명, 벤치마크를 신호로 작성기를 최적화하여 완전한 충실도 도달 및 held-out 일반화

3 대규모 다운스트림 검증 (부정적 결과)

다중 모델·다중 저장소 실험에서 긍정 대조군으로 검증된 강건한 null, 문서가 도움이 되는 경계의 특정

결론

성립한 것

  • 충실도는 완전성이 좌우, 길이가 아님
  • 왕복 점수는 설명 작성기 최적화 신호로 유효
  • 최적화된 문서는 소스가 없을 때 강력한 대체재

성립하지 않은 것

  • 소스가 있는 표준 에이전트 환경에서 문서의 이슈 해결 향상 효과 없음
  • 검색 기반 컨텍스트도 동일하게 무효
  • 긴 문서는 오히려 약간의 악영향

문서화의 가치는 코드와의 정보적 거리가 결정한다 — 코드 너머의 지식이 없다면, 좋은 문서는 좋은 에이전트를 더 좋게 만들지 않는다.
