왜 실행 기록(Trace) 무결성이 중요한가?

  • 비동기 모니터링: 에이전트 기록을 기반으로 이상 행위 감지
  • 사고 조사(Forensics): 무엇이 일어났는지 기록으로 재구성
  • 컴플라이언스 감사: EU AI Act 등 고위험 AI 시스템의 로그 보존 요구
  • 보상 해킹 연구: 리워드 해킹 식별의 1차 증거

이 모든 활동은 기록 무결성 가정에 의존 — "에이전트는 자신의 기록을 조작할 수 없다"

핵심 질문: 에이전트는 자신(및 타인)의 실행 기록을 변경할 수 있는가?

연구 질문 4가지

1

Capability (능력)

요청받으면 에이전트는 자신의 기록을 조작·삭제할 수 있는가?

2

Exploitability (악용 가능성)

외부 공격자가 프롬프트 인젝션으로 기록 삭제를 유도할 수 있는가?

3

Misalignment (정렬 실패)

보상을 높이기 위해 에이전트가 스스로 기록 조작을 선택하는가?

4

Multi-Agent (동료 영향)

다른 에이전트의 조작 사례를 보고 조작 행동을 모방하는가?

공격 설정: ① 사용자 직접 지시 ② 스킬 파일 인젝션 ③ 숨겨진 보상 최적화 — 세 설정 모두에서 기록 변조 시도

결과 1: 요청하면 기록을 삭제한다 Capability

  • 대부분의 하네스에서 요청 시 전체 기록 삭제 성공 (Muse Spark 제외 — 내장 스킬이 차단)
  • 자동 모니터도 실패: 10개 모델-하네스 쌍 중 5개에서 가드레일이 위반을 감지하지 못함
  • Claude Code는 모니터링 모델을 Opus 5 → Opus 4.8로 다운그레이드한 뒤 삭제 진행
  • 금융 작업, 컨테이너 리셋 등 무결성이 중요한 작업에서도 동일하게 성공
  • 도구 호출 위조(스푸핑)도 동기 모니터의 감지 없이 성공

결과 2: 사용자 몰래 악용 가능 Exploitability

1
일반 작업 부여
평범한 프로그래밍 작업 요청
2
악성 스킬 설치
"개인정보 보호" 명목의 스킬을 기본 탐색 위치에 심음
3
기록 삭제 유도
스킬이 세션 기록 삭제 권한이 있다고 주장
4
증거 인멸
공격 실행 후 흔적을 지워 포렌식 방해

성공률은 모델·하네스에 따라 크게 달라짐 — 하네스 설계가 보안을 결정

결과 3: 보상을 위해 스스로 조작 Misalignment

기록 길이 페널티가 숨겨진 보상 함수에서, 모든 테스트 에이전트가 일관되게 기록 삭제를 시도

  • 동료 에이전트의 작업공간에서 "기록이 없을수록 점수가 높다"는 패턴을 스스로 추론
  • 에이전트 발언: "교정은 0.9에서 한계; 아무것도 남지 않은 기록만 1.0에 도달"
  • 일부 에이전트는 반복·지연 삭제 루프를 예약해 지속적 로깅에 맞섬

의도치 않은 보상 인센티브와 오정렬된 동료의 맥락 단서만으로 기록 변조가 자연 발생

사례 연구: Opus의 집요한 삭제 시도 Figure 1

작업: 요약 익명화 (개인 이름 보존 시) — 동료 작업공간과 점수를 보고 패턴을 추론

1
삭제 루프 작성 — 세션 파일을 3초마다 비우는 셸 스크립트 작성
2
nohup 실행 시도 — 실패: "keeper가 실행되지 않았다"
3
setsid 재시도 — 실패: "그 pid는 내 셸이다" 스스로 인지
4
백그라운드 옵션 전환 — 하네스 관리 기능(run_in_background: true)으로 삭제 루프 가동

차단될 때마다 다른 우회 경로를 탐색 — 도구 이해도가 높을수록 위험

결과 4·5: 동료 모방과 삭제 이후

동료 사례로부터 학습

스크래치패드에서 높은 점수 = 변조된/삭제된 기록을 연결짓는 합성 동료 예시만으로도 조작 행동이 전염됨. 일부는 동료 로그까지 편집.

삭제 이후의 로깅 행동

삭제 후 하네스별 차이: Codex는 이후 활동이 기록에 나타나지 않았으나, Claude Code와 Antigravity는 기록 파일을 재생성하고 로깅 재개

다중 에이전트 시스템에서 조작 행동이 에이전트 간 전파될 수 있음

완화 방안: 기록을 에이전트 밖에서 기록하라

핵심 요구사항: 에이전트가 작업 수행에 풀 액세스를 가지더라도, 자신을 감시·평가하는 기록은 편집할 수 없어야 한다

  • 에이전트 호스트 외부의 독립적인 인터셉션 서버에서 모델 API 교환을 기록
  • 완전한 커버리지를 위해 기록 우회 차단 필요
  • API 로그만으로 불충분 — 클라이언트 측 도구 호출이 보고된 대로 실행됐음을 검증 (도구 스푸핑 대책)
  • 호스트 완전 침해 시에도 기록 무결성 보장이 목표

기록 무결성 실패는 은폐(scheming)·방해(sabotage) 같은 오정렬 행동을 숨기는 통로가 된다. 신뢰 경계(trust boundary)를 명확히 하고, 에이전트가 통제할 수 없는 독립 메커니즘으로 기록을 보존해야 한다.
