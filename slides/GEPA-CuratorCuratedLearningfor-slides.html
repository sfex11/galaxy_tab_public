배경: LLM 에이전트의 재귀적 자기 개선

LLM 에이전트는 복잡한 환경과 지속적으로 상호작용하는 멀티턴 워크로드에 활발히 사용되고 있습니다.

반추형 프롬프트 최적화 (Reflective Prompt Optimization)

1
환경에서 실행
에이전트가 도구를 사용해 작업 수행
2
궤적 분석
Reflector가 결과 궤적에서 교훈 도출
3
프롬프트 수정
교훈을 반영해 프롬프트 개선

이 피드백 루프를 통해 경험이 점진적으로 에이전트의 행동을 개선합니다 — 단, 경험에 "신호"가 있다는 가정이 전제입니다.

문제: 모든 실패가 유용한 학습 신호일까?

에이전틱 환경에서는 실행이 하네스와 외부 환경을 거치고, 성공 판정은 LLM-as-a-judge에 의존합니다. 실패의 원인을 프롬프트로 정확히 귀속하기 어렵습니다.

실패의 다양한 원인

  • 프롬프트의 실제 약점
  • 하네스(harness)의 한계 및 도구 사용 불가
  • 확률적(stochastic) 실행 노이즈
  • 노이즈가 섞인 LLM 판정

노이즈 신호의 위험

외부 요인으로 인한 실패를 Reflector가 프롬프트 결함으로 잘못 귀속하면, 불필요하거나 오히려 유해한(harmful) 프롬프트 업데이트가 발생할 수 있습니다. 실제 환경의 모호하거나 불가능한 작업도 추가 노이즈를 만듭니다.

동기 부여 사례: 쇼핑 에이전트의 두 가지 실패

유용한 신호

필수 옵션을 놓쳐 실패

장바구니에 담기 전 필수 항목을 확인하지 않아 실패한 경우 → "진행 전 필수 필드 확인"이라는 실질적인 프롬프트 개선으로 이어집니다.

유해한 신호

환경 버그로 실패

구매 버튼이 일시적으로 오작동하는 고장 난 환경 때문에 실패한 경우 → Reflector가 "다른 구매 방법을 찾아야 한다"는 잘못된 교훈을 학습할 수 있습니다.

결론: 어떤 작업과 경험이 프롬프트 최적화에 입력되는지 선별(curation)하는 것이 필수적입니다.

검증 기반 게이팅만으로는 부족하다

기존 방법(GEPA, ACE 등)은 홀드아웃 검증 세트로 나쁜 변이를 거부하지만, 두 가지 근본적 한계가 있습니다.

1

집계 점수의 노이즈

게이팅 결정이 집계된 평가 점수에 의존하는데, 실행·평가의 확률성 때문에 나쁜 변이가 수용되고 좋은 변이가 거부될 수 있습니다.

2

사후(post-hoc) 개입

검증 게이팅은 변이가 생성된 이후에만 작동하므로, 반추(reflection)와 변이 자체의 품질을 근본적으로 개선하지 못합니다.

Reflector에게 추가적인 맥락 정보를 제공해 근본적 품질을 높여야 합니다.

GEPA-Curator: 두 가지 핵심 구성요소

기존 프롬프트 옵티마이저 위에서 작동하는 에이전틱 데이터 큐레이터(curator)로, 어떤 경험이 최적화를 이끌지 선별합니다.

1
작업 큐레이션
노이즈·결함이 의심되는 작업을 미니배치에서 제외하고 깨끗한 신호를 줄 작업만 선별
2
롤아웃 실행
선별된 작업에 대해 에이전트가 환경에서 경험 수집
3
선행 성공 검색
해당 작업의 과거 성공 궤적을 선택적으로 검색해 맥락으로 제공
4
반추 및 변이
더 풍부한 맥락을 갖춘 Reflector가 고품질 프롬프트 변이 생성

① 작업 큐레이션 (Task Curation)

미니배치 작업을 무작위로 선택하는 대신, Curator 에이전트가 학습 신호의 품질을 사전에 평가합니다.

  • 노이즈가 있거나 신뢰할 수 없는 신호를 제공할 가능성이 높은 작업을 선제적으로 필터링
  • 모호하거나 실행 불가능한 작업, 고장 난 환경의 작업 제거
  • 깨끗한 신호를 제공할 작업으로만 미니배치 구성
  • 데이터 조합(data composition) 분석에서 부정적 전이(negative transfer) 사례 확인

잘못된 입력 경험은 그 자체로 학습 신호가 아니라 옵티마이저를 오염시키는 원인입니다.

② 선행 성공 검색 (Prior Success Retrieval)

Curator가 과거의 성공적인 궤적을 선택적으로 검색하여 프롬프트 옵티마이저에게 추가 맥락으로 제공합니다.

왜 성공 궤적인가?

Reflector에게 성공 사례를 제공하면 프롬프트가 과거에는 성공했고 지금은 왜 실패하는지를 정확히 파악할 수 있는 맥락이 생깁니다. 이는 변이의 근본 원인 진단 정확도를 높입니다.

선택적 검색

모든 이력을 제공하는 것이 아니라, 현재 작업과 관련성 높은 성공 궤적만 선별하여 컨텍스트 오버헤드를 줄이고 신호 대 잡음비를 높입니다.

작업 큐레이션이 "무엇을 배울지"를 정한다면, 선행 성공 검색은 "어떻게 더 잘 배울지"를 돕습니다.

실험 설정

평가 벤치마크

  • WebArena — GitLab, Reddit, 쇼핑 등 4개 실제 웹사이트 (GoBrowse)
  • ALFWorld — 텍스트 기반 가상 가사 작업
  • AppWorld — 앱 기반 에이전틱 작업
  • τ-bench — 고객 서비스형 도구 사용 작업

옵티마이저 모델

두 가지 강력한 모델로 최적화를 수행:

  • Gemini 3.1 Pro
  • Claude Opus 5

베이스라인: GEPA, ACE

주요 결과

GEPA-Curator는 평가된 모든 베이스라인의 평균 성능을 능가하거나 일치했습니다.

  • 서로 다른 옵티마이저 모델에서도 효과가 유지 → 큐레이션의 모델 불변적(model-agnostic) 이점 시사

분석: 큐레이터는 무엇을 선별하는가?

작업 선택 분석

Curator의 작업 선택 결정을 분석한 결과, 노이즈·신뢰성 문제가 의심되는 작업을 일관되게 걸러내며, 데이터 구성의 차이가 성능에 큰 영향을 미침을 확인했습니다.

효율성 및 비용 분석

큐레이션으로 불필요한 롤아웃과 반추를 줄여 전체 최적화 비용을 절감합니다. 추가 Curator 호출 비용을 상쇄하고도 남는 효율 개선을 보고합니다.

확장: Meta-Harness-Curator

큐레이션 아이디어를 프롬프트가 아닌 하네스 코드 자체의 최적화로 확장한 실험에서도 유사한 이점이 확인되어, 접근법의 일반성을 보여줍니다.

결론

  • 에이전틱 실패는 프롬프트 약점뿐 아니라 하네스 한계·실행 노이즈·판정 노이즈에서 올 수 있으며, 모든 실패가 유용한 학습 신호는 아니다
  • 작업 큐레이션으로 노이즈 작업을 사전에 제거하고, 선행 성공 검색으로 Reflector에 풍부한 맥락을 제공
  • 4개 벤치마크 × 2개 옵티마이저 모델에서 GEPA 대비 최대 20.7%, ACE 대비 최대 21.2% 향상
  • 큐레이션은 비용 효율적이며, 하네스 최적화로도 확장 가능

자기 개선 에이전트의 핵심은 "더 많은 경험"이 아니라 "어떤 경험을 배울지 선별하는 능력"입니다.
