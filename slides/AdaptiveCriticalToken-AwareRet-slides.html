Adaptive Critical Token-Aware Retrieval
for Repository-Level Code Generation

ACToR: 생성 과정에서 핵심 토큰(Critical Token)을 식별하고, 필요한 순간에 맞춤형 저장소 컨텍스트를 검색하는 적응형 프레임워크

RepoExec +8.4% CoderEval +15.4%

배경: 저장소 수준 코드 생성

실제 개발 환경의 요구사항

생성된 코드는 단순히 작업 요구사항을 만족해야 할 뿐 아니라, 프로젝트 고유의 API·의존성·데이터 구조·코딩 규약과 일관성을 유지해야 함

현실적 제약

실제 저장소는 LLM의 입력 길이 제한을 초과하는 경우가 많아 전체 저장소를 프롬프트에 담을 수 없음

→ 해결책으로 검색 증강 생성(RAG)이 널리 채택됨: 저장소에서 작업 관련 컨텍스트를 검색하여 생성 프롬프트에 주입

기존 RAG 접근법과 한계

컨텍스트 품질 향상

  • RepoCoder: 이전 라운드 생성 결과로 반복적 쿼리 구성
  • Cocomic: 프로젝트 컨텍스트 그래프 기반 의존성 탐색
  • DRACO: 데이터플로우 분석으로 세밀한 코드 엔티티 검색

검색 의사결정 개선

  • RepoFormer: 작업별 검색 트리거 여부 판단
  • RLPG: 작업에 필요한 의존성 컨텍스트 유형 식별
  • ProCC: 검색 프롬프트 구성 전략 동적 선택

핵심 한계: 기존 방법은 컨텍스트를 작업(task) 수준으로만 제공하며, 생성 중 토큰 단위의 핵심 판단 지점을 명시적으로 모델링하지 못함

핵심 개념: Critical Token

코드 생성 오류는 모든 토큰에 균일하게 누적되지 않고, 소수의 결정적 위치에 집중됨. 이 위치에서 잘못된 토큰이 생성되면 이후 코드가 잘못된 의미 경로를 따라가 기능적 실패로 이어짐

소수

전체 생성 위치의 약 5~11%만이 핵심 토큰으로 나타남 (모델 전반)

결정적

핵심 토큰 오류는 모델의 핵심 구현 논리 판단을 바꿔 전체 결과를 실패로 유도

다양한 형태

API 이름·변수 참조·인덱스 식·제어 흐름 토큰·주석의 의미 단서 등 구문 형태 제한 없음

동기 부여 사례 1: 치명적 오류 vs 국소적 오류

CoderEval popitem 함수 — 캐시에서 가장 오래된 항목 제거·반환

Critical Token 오류

next(iter(self._order)) 대신 self를 생성 → 모델이 이후 코드를 잘못된 객체(self.buffer.popitem...) 중심으로 구성 → 삽입 순서 삭제 논리 이탈, 함수 전체 실패

비(非)핵심 토큰 오류

타입 관련 국소적 세부사항만 왜곡됨 → 주요 제어 흐름·데이터 흐름 구조는 유지되어 전체 기능에는 영향 없음

사례 2: normalize_cmd — 핵심 토큰의 다양성

핵심 토큰은 고정된 구문 형태에 국한되지 않음 → 사전 검색 1회나 고정 구문 규칙만으로는 진짜 결정적 토큰을 커버할 수 없음

ACToR 전체 파이프라인

1
오프라인 학습
데이터 구성 → 핵심 토큰 평가 → 라벨 균형 → 분류기 학습
2
가중 밀집 검색기
위치 인식 가중 풀링으로 생성에 유익한 컨텍스트 우선 검색
3
핵심 토큰 안내 추론
생성 중 핵심 토큰 식별 시 온디맨드 검색 트리거

적응형: 정적 사전 검색이 아닌, 생성 과정 안에서 동작

정밀 타겟팅: 모델이 컨텍스트가 필요한 결정적 위치에만 정확한 정보 제공

오프라인 학습: 핵심 토큰 분류기

1. 데이터 구성

저장소 컨텍스트 유무에 따른 생성 결과를 비교하여, 올바른 생성에 결정적으로 기여하는 토큰 위치 수집

2. 토큰 평가

토큰별 생성 영향도를 정량 평가하여 어떤 위치가 최종 결과의 정답성을 좌우하는지 측정

3. 라벨 균형

핵심/비핵심 토큰의 클래스 불균형을 완화하여 신뢰할 수 있는 분류기 학습 보장

4. 분류기 학습

추론 시점에 각 생성 위치가 핵심 토큰인지 실시간 판별하는 분류기 훈련

→ 이 분류기가 온라인 추론에서 "지금 검색이 필요한 순간"을 판단하는 핵심 엔진

온라인 추론: 두 가지 핵심 기법

위치 인식 가중 밀집 검색기

  • 밀집 검색기의 풀링 과정에 위치별 가중치 부여
  • 생성에 더 유익한 컨텍스트를 임베딩에서 우선 반영
  • 컨텍스트 임베딩 정제로 검색 정밀도 크게 향상

핵심 토큰 안내 추론

  • 자기회귀 생성 중 분류기가 핵심 토큰 위치를 실시간 식별
  • 해당 위치에만 온디맨드 타겟 검색 트리거
  • 불필요한 검색 최소화 → 효율성과 정확성 동시 확보

실험 설정

벤치마크

RepoExec · CoderEval — 대표적 저장소 수준 코드 생성 벤치마크 2종

비교 대상

RepoCoder, Cocomic, DRACO, RepoFormer, RLPG, ProCC 등 최신 저장소 수준 RAG 방법론들

  • RQ1 전체 성능과 효율성
  • RQ2 구성 요소 절제 연구
  • RQ3 민감도 분석
  • RQ4 핵심 토큰의 구성과 구문 특성

두 벤치마크에서 일관된 성능 우위

효율성: 필요한 시점에만 검색하여 오버헤드 통제

절제 연구: 핵심 토큰 안내와 가중 검색기 모두 기여 확인

민감도: 다양한 설정에서 강건한 성능 유지

핵심 토큰의 정량적 분석

비중은 작지만 영향은 크다

핵심 토큰은 전체 생성 위치의 약 5~11%에 불과하지만, 모델의 오류와 불확실성이 이 소수 위치에 집중됨

구성과 구문 특성

API 이름·변수 참조·인덱스·제어 흐름 토큰 등 다양한 구문 역할로 나타나며, 주요 생성 실패가 이 위치들과 직접 연결됨

→ 시사점: 저장소 컨텍스트를 한 번만 사전에 제공하는 방식 대신, 생성 시점의 희소한(sparse) 검색 갱신이 필요하다는 근거

케이스 스터디와 위협 요소 분석(내부/외부 타당성)으로 접근법의 신뢰성을 보완적으로 검증

기여 요약

  • 핵심 토큰 개념 도입 — 저장소 수준 코드 생성에서 최종 코드 품질에 미치는 결정적 영향을 최초로 체계적 정량화
  • 타겟 검색 프레임워크 — 핵심 토큰을 위한 온디맨드 검색으로, 생성의 가장 중요한 단계에 정확하고 시의적절한 컨텍스트 공급
  • 위치 인식 가중 풀링 — 컨텍스트 임베딩 과정을 정제하여 검색 정밀도 대폭 향상
  • 광범위한 실험 검증 — 대표 벤치마크에서 기존 SOTA를 유의미하고 일관되게 능가

핵심 메시지: 코드 생성 오류는 무작위가 아니라 소수의 결정적 위치에서 발생하므로, 검색도 그 위치에 맞춰 적응적으로 이루어져야 한다
