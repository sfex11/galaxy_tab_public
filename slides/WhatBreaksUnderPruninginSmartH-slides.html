What Breaks Under Pruning in Smart Homes, and When?

스마트홈 도구 호출에서 프루닝이 무엇을 깨뜨리고, 언제 깨뜨리는가?

아키텍처와 태스크 복잡도에 따른 LLM 열화 평가

Alexa Home AI, Amazon.com · University of Washington

배경: 스마트홈의 LLM과 프루닝

  • LLM은 스마트홈 제어의 자연어 인터페이스 — 사용자 요청을 기기·기능·상태에 기반한 구조화된 액션으로 변환
  • 하지만 LLM 배포는 상당한 메모리·연산 비용을 수반
  • 구조화 프루닝은 레이어·채널·전문가를 제거해 하드웨어 친화적인 형태로 비용 절감
핵심 질문: "얼마나" 프루닝할 수 있는가?가 아니라 "무엇이" 깨지는가?

연구 공백과 기여

기존 연구의 한계

기존 프루닝 연구는 집계 정확도(aggregate accuracy)만 평가하여 능력별 열화를 가림

스마트홈 벤치마크는 프루닝되지 않은 모델만 연구

본 논문의 기여

① 액션 컴포넌트 × 태스크 복잡도의 세분화된 평가 프레임워크

② 3개 아키텍처 계열 × 4종 프루닝 × 3개 데이터셋 체계적 평가

③ 배포 관점의 실패 패턴 실증: 프루닝 절벽, 구체성 우선 열화, 과잉 거절

평가 프레임워크 개요

4개 LLM에 depth·width·hybrid·expert 프루닝 적용
2

3

두 관점을 통해 얼마나 신뢰성이 손실되는지뿐 아니라 무엇이, 어떤 조건에서 깨지는지 측정

문제 정식화: 액션의 4가지 컴포넌트

스마트홈 태스크 복잡도 분류 (5단계)

범주정의예시 / 요구 사항
Simple단일 기기에 단일 액션"주방 조명 꺼줘"
Medium복수 액션/기기 또는 명확화 필요모호한 요청에 되묻기
Complex이전 대화 맥락 의존지시 대명사 해소, 반복·되돌리기
Partially Executable일부만 실행 가능유효 부분 실행 + 무효 부분 거절
Infeasible전부 실행 불가실행 회피 및 요청 거절

실험 대상: 모델과 프루닝 방법

4개 LLM (Qwen 계열)

  • Qwen3-4B — dense Transformer (36 layers, GQA)
  • Qwen3.5-4B / 9B — dense hybrid (Gated DeltaNet + full-attention)
  • Qwen3.6-35B-A3B — sparse MoE (35B 중 토큰당 약 3B 활성화)

4종 프루닝

  • Depth — ShortGPT (Block Influence), Angular (경계 표현 유사도)
  • Width — FLAP (변동 기반 중요도로 채널 프루닝)
  • Hybrid — 2SSP (depth + width 결합)
  • Expert — MoE 전문가 프루닝

결과 ① Dense는 좁은 안전 구간, MoE는 높은 내성

Dense 모델

좁은 안전 프루닝 구간(narrow safe region) 이후 급격한 성능 절벽(sharp degradation)

임계점을 넘는 순간 복수 액션 컴포넌트가 동시에 붕괴

MoE 모델

전문가 제거에 대해 훨씬 큰 프루닝 허용 범위 — 완만한 열화 곡선

동일 작업량에서 dense 대비 안정적인 신뢰성 유지

프루닝 비율 선택 시 아키텍처별 안전 구간을 반드시 확인해야 함

결과 ② 의도보다 구체성이 먼저 무너진다

1
스키마 수준 의도(schema-level intent) — operation·argument 같은 구조적 결정은 비교적 오래 유지
2
그라운딩된 구체성(grounded specificity) — device와 value 예측이 먼저 열화

예: "조명 켜"는 이해하지만 어느 방의 조명인지, 몇 단계로 틀리는 방식

→ 집계 정확도가 견고해 보여도, 실제 기기 제어 품질은 이미 저하되었을 수 있음

결과 ③ 예측 불가능한 민감도와 과잉 거절

기준 정확도 ≠ 프루닝 민감도

프루닝 전 태스크 난이도(baseline accuracy)는 프루닝 후 열화 정도를 신뢰 있게 예측하지 못함

쉬운 태스크가 반드시 프루닝에 강한 것은 아님

Dense 공격적 프루닝의 부작용

단순 정확도 하락을 넘어 행동의 질적 변화 발생

실행 가능한 요청까지 체계적으로 거부하는 과잉 거절(over-refusal)로 붕괴

핵심 발견 요약

  • 프루닝 절벽 — dense 모델은 좁은 안전 구간 후 급격히 붕괴, MoE는 넓은 내성
  • 구체성 우선 열화 — device·value가 operation·argument(스키마 의도)보다 먼저 손상
  • 태스크 의존 민감도 — 프루닝 전 난이도는 프루닝 민감도를 예측하지 못함
  • 과잉 거절 — 공격적 dense 프루닝 시 실행 가능 요청의 체계적 거부로 질적 붕괴
배포용 프루닝 모델 선정 시 집계 정확도만으로는 부족 — 컴포넌트·복잡도별 평가가 필수

결론

프루닝의 영향은 액션 컴포넌트와 태스크 복잡도의 세분화된 평가를 통해서만 제대로 파악할 수 있으며, 아키텍처 선택(dense vs. MoE)이 배포 안전성을 좌우함
