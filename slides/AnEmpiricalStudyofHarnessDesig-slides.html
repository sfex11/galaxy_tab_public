배경: 하니스가 성능을 결정한다

LLM은 코딩 하니스(coding harness)라는 소프트웨어 계층 안에서 동작합니다. 모델을 고정한 채 하니스만 바꿔도 성능이 크게 달라집니다.

계획 (Planning)

작업 구조를 유지하고 진행 상황을 추적하는 스캐폴드

행동 공간 (Action Space)

모델의 의도를 실행 가능한 작업 공간 연산으로 변환하는 인터페이스

컨텍스트 관리

유한한 창 안에서 어떤 상호작용 기록을 유지할지 결정하는 정책

문제: 기존 연구는 하니스를 통째로(monolithic) 평가 → 성능 차이가 계획, 도구 설계, 컨텍스트 관리 중 어디에서 오는지 알 수 없음

연구 질문

하니스 구성 요소는 모든 설정에서 일반적으로 유용한가,
아니면 모델 능력 · 과제 유형 · 자원 예산에 따라
효과가 달라지는가?

  • 기존 연구는 완성된 시스템 간 비교 → 여러 메커니즘이 뒤섞여 구성 요소별 기여 분리 불가
  • 본 연구는 실행 루프를 고정하고 세 구성 요소만 독립적으로 변경
  • 각 개입(intervention)의 조건부 효과를 분리해 추정하는 모듈형 프레임워크 제시

5가지 컨텍스트 관리 전략

전략핵심 메커니즘
T0추가 압축 없음 — 컨텍스트 창 초과 시 실행 종료
T1오래된(stale) 도구 관찰을 생략(elision)
T2T1 + 외부 저장소와 recall_event로 생략된 내용 복구 가능
T3생략 없이 LLM 요약(summarization)만 사용
T4단계적(staged) 정책 — 요약을 호출하기 전에 생략을 먼저 적용

모델 · 과제 · 실행 루프 · 비에블레이션 요소를 고정한 채 각 전략의 효과만 비교

핵심 발견 1

컨텍스트 관리: 예산이 타이트할수록 가치 상승

  • 컨텍스트 창 예산이 작을수록 컨텍스트 관리의 이득이 커짐
  • 효과의 대부분은 컨텍스트 오버플로우로 인한 조기 종료 방지에서 발생
  • 에이전트가 코드 수정 및 검증 단계까지 진행할 수 있도록 함
  • 창이 넓어질수록 정확도 이득은 감소

컨텍스트 관리는 에이전트 행동 자체를 바꾸지 않고 실행 궤적을 더 오래 지속시킨다

핵심 발견 2

T4가 최고의 정확도–비용 균형

  • 생략(elision) → LLM 요약의 단계적 적용(T4)이 컨텍스트 전략 중 최고 효율
  • 다른 관리 전략과 비슷한 성공률을 유지하면서 피크 컨텍스트와 요약 호출 감소
  • 생략된 내용을 복구하는 recall 메커니즘은 거의 사용되지 않음
  • 복구 장치는 생략만 사용할 때 대비 정확도 향상 없이 기계적 복잡성만 추가

단순한 생략이 회복 가능한 정교한 장치보다 효율적일 수 있다

핵심 발견 3

계획: 약한 모델의 스캐폴드 → 강한 모델의 비용 절감

약한 모델

궤적이 편집 시도까지 살아있게 유지 → 성공률 상승 (추가 비용 수반)

강한 모델

중복된 편집 후 검증을 제거 → 비용 절감 (정확도는 거의 변화 없음)

모델 능력이 커질수록 계획의 역할이 정확도 스캐폴드에서 효율 보조 도구로 이동

핵심 발견 4

행동 공간: 사전 정의 도구 vs bash 전용

사전 정의 도구 세트

bash 능력이 약한 모델의 성능을 끌어올림 — 셸 명령에 대한 의존도 감소

bash 전용 인터페이스

bash 능숙 모델은 호출당 여러 작업을 결합 → 비용 대폭 절감, 특히 터미널 중심 과제에서 효과적

  • bash 전용은 더 큰 단위의 코드 작성과 더 적은 상호작용을 가능하게 함
  • 정확도–비용 균형은 과제 유형에 따라 달라짐

궤적 수준 분석: 효과는 왜 발생하는가

컨텍스트 관리

실행 궤적을 연장하지만 에이전트 행동은 거의 변하지 않음 — 128k에서도 궤적 형태가 유지됨

계획

궤적이 어디서 멈추는지를 바꿈 — 약한 모델은 편집 시도까지 도달, 강한 모델은 편집 후 검증 축소

행동 공간

코드가 작성되는 세분성(granularity)을 변경 — bash 전용은 더 큰 코드 작성 액션과 더 적은 상호작용

세 개입은 서로 다른 메커니즘으로(지속 · 종료 지점 · 세분성) 성능에 기여한다

결론 및 시사점

  • 하니스 구성 요소의 효과는 모델 능력 · 과제 유형 · 예산에 따라 조건부
  • 타이트한 예산 → 컨텍스트 관리, 약한 모델 → 계획·사전 정의 도구, bash 능숙 모델 → bash 전용 인터페이스
  • 모델 및 예산을 인지하는(model- and budget-aware) 하니스 설계 지침 제공
  • 미래 하니스 구성 요소를 평가할 수 있는 모듈형 프레임워크 공개

하니스를 하나의 덩어리가 아닌, 조정 가능한 구성 요소의 집합으로 바라보자
