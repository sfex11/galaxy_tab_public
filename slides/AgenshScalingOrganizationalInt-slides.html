기존 방식: 메인 에이전트가 계획 → 작업 분해 → 할당 → 관리

핵심 한계: 시스템 확장성은 오케스트레이터가 워커를 관리·조정·통합하는 능력에 근본적으로 제한됨

멀티 에이전트 협력 루프 (5단계)

각 워커가 동시·비동기로 반복 실행하는 협력 사이클

1
컨텍스트 수집
목표·동료 진행상황·메시지·발견 읽기
2
하위 작업 클레임
CLAIM을 공유 컨텍스트에 게시
3
행동 실행
도구로 작업 수행, 중간 발견 공유
4
결과 검증
수용 기준 충족까지 접근 수정
5
진행 병합
공유 워크스페이스에 통합·공고
  • 클레임 충돌 시 직접 메시지로 해결, 병합 충돌 시 최신 진행 반영 후 재병합
  • 모든 워커가 비동기 진행 — 동료 대기 없이 지속 작업

조직 인프라의 3가지 조정 메커니즘

공유 워크스페이스

  • 조직의 진행 중·통합된 작업 보관
  • 동시 쓰기 + 비동기 읽기 지원
  • 버전 이력 보존 및 병합 지원
  • Git 플랫폼으로 구현 — 비공개 체크아웃/브랜치 → 메인 브랜치 통합
  • Issue·Pull Request로 변경 출처 추적, 충돌 감지

메시지 인터페이스

  • 공유 태스크 채널: 팀 전체 공지
  • 직접 메시지: 긴급 1:1 통신
  • 낮은 우선순위 → 루프 시작 시 전달
  • 높은 우선순위 → 인프라 도구 호출 직후 전달

공유 컨텍스트

  • 동료들의 재사용 가능한 발견 보존
  • 작업 의도(CLAIM) 보존
  • 다음 하위 작업 선택 시 활용

실험 설정

벤치마크

  • ProgramBench: 가장 어려운 애자틱 소프트웨어 엔지니어링 벤치마크 중 하나
  • 참조 소프트웨어의 동작을 인터넷 없이 재현
  • 6시간 예산 제약
  • 가장 어려운 5개 과제: 수천 개 파일, 수백만 바이트 소스 코드

구성

  • 모델: GPT-5.6-sol (high)
  • 확장 범위: 1 → 128 → 1,024 에이전트
  • 이벤트 기반 런타임 + 공유 컨텍스트 전달
  • 대규모 배포 및 단일 에이전트 기준선 비교

측정 지표: 최종 테스트 통과율(test-pass rate)

기존 연구와의 차별성

구분기존 멀티 에이전트 프레임워크Agensh
조정 구조 중앙 오케스트레이터가 계획·분해·할당 중앙 오케스트레이터 없음, 자기조직화
확장성 오케스트레이터 용량에 제한 1,024 에이전트까지 검증
조정 방식 훈련된 오케스트레이터 필요 가벼운 인프라(워크스페이스·메시지·컨텍스트)
  • 관련 분야: 멀티 에이전트 조직·협력 하네스, 공유 컨텍스트, 분산형 조정

결론

에이전트 수 = 새로운 스케일링 차원

  • 중앙 오케스트레이터 없이도 1,024 에이전트 규모로 확장 가능한 멀티 에이전트 하네스 제시
  • 5단계 협력 루프 + 3가지 조직 인프라(워크스페이스·메시지·컨텍스트)
  • 1→128 에이전트: 평균 통과율 19.31% → 28.78% (약 49% 상대 향상)
  • pandoc: 33.89% → 55.06%
  • 조직 성장에 따라 전문화·표준화 등 자기조직 협력이 창발
