ReTrace

Distilling Tool-Using Agents into Planner-Free Workflows

도구 사용 에이전트를 플래너 없는 워크플로우로 증류하기

Kaiyuan Hou, Yang Ping Kuo, Indranil Bhattacharya, Rohith Nama, Arushi Gupta,
Carlos D. Castillo, Prathap Ramachandra, Xiaofan Jiang, Francesco Carbone

Columbia University Amazon

arXiv: 2611.14492

문제: 런타임 계획의 대가

비즈니스 프로세스 자동화는 같은 SOP(표준 운영 절차)를 새로운 입력마다 반복 실행합니다. LLM 에이전트는 자연어 SOP를 따를 수 있지만, 모든 실행의 모든 단계마다 LLM을 호출해야 합니다.

91.8%

프로덕션 플랫폼의 5,115개 자동화 중 런타임 계획 에이전트가 차지하는 비율

7 / 10

가장 자주 실행된 자동화 10개 중 고정 워크플로우의 수

37–43%

3~5개 도구를 쓰는 에이전트가 다음 단계 선택에 소비하는 실행 시간 비율

자주 실행되는 절차라면 워크플로우를 한 번만 만들어 두는 것이 유리 — 구축 비용은 약 75회 실행 후 회수

핵심 통찰: 도구 호출만으로는 부족하다

"에이전트가 주문을 조회한 뒤 사람에게 에스컬레이션했다 — 트레이스만으로는 배송 상태가 에스컬레이션의 원인인지 알 수 없다."

  • 에이전트의 추론(reasoning)은 각 도구 호출과 함께 "왜" 그 행동을 했는지 설명
  • 추론은 로그에 never 실행된 대안 경로까지 언급할 수 있음
  • 원시 트레이스를 더 많이 주는 것은 역효과 — 긴 트레이스가 많으면 워크플로우 생성기가 오히려 worse 코드를 작성

ReTrace 개요: 에이전트 실행 → 실행 가능한 워크플로우

1
SOP + 트레이스
자연어 SOP와 추론을 포함한 소수의 에이전트 실행 로그
2
규칙 문서
조건·도구·입력 출처를 통합한 컴팩트한 규칙 문서 (증거 연결)
3
워크플로우
실행 시 코드가 다음 단계 선택 — LLM 호출 없음

LLM은 1회성 구축에만 사용 — 런타임에는 코드가 단계를 선택합니다 (도구 내부에서 분류 등을 위해 모델을 호출하는 것은 가능)

방법: 3단계 구축 파이프라인

1. 추출 (Extraction)

각 트레이스를 단계별로 읽어 조건, 도구, 입력 소스를 추출 — 추론이 알려주는 "행동 조건"을 복원

2. 병합 (Aggregation)

여러 트레이스의 조건을 컴팩트한 규칙 문서로 통합 — 모든 규칙을 트레이스의 증거에 연결

3. 합성 (Synthesis)

규칙 문서에서 실행 가능한 워크플로우를 생성하고 일관성 검사 수행

마지막 단계만 대상 플랫폼에 의존 → 동일한 규칙 문서로 Python 코드(공개 벤치마크)와 타입 기반 워크플로우 그래프(프로덕션 플랫폼) 모두 생성 가능

주요 기여

①

에이전트 추론에서 규칙으로
추론 + 도구 기록을 결합해 행동 조건, 입력 출처, 미실행 대안을 복원

②

하나의 규칙 문서, 여러 플랫폼
동일 파이프라인으로 두 공개 벤치마크용 Python 코드와 프로덕션용 워크플로우 그래프 생성

③

프로덕션 + 공개 벤치마크 검증
에이전트 대비 3~5점 이내 성능, 기업 비용 24% 절감, 작업당 시간 170s → 1.3s

추론 제거 시 Internal -8.8pt, τ²-bench -6.2pt — 추론이 워크플로우 품질의 핵심

실험 설정

τ²-bench

공개 도구 사용 벤치마크 — 에이전트 대비 작업 성공률과 실행 시간 측정

SOP-Bench

SOP 준수 능력을 평가하는 벤치마크 — few-shot 생성과 비교

Internal (79개 절차)

기업 프로세스 자동화 프로덕션 플랫폼의 실제 절차

  • 비교 대상: 런타임 계획 에이전트, few-shot 워크플로우 생성, 트레이스 재사용 기법(AWM, ExpeL 등)
  • 메트릭: 작업 성공률 / 완료율, 작업당 실행 시간, 작업당 운영 비용

주요 결과: 에이전트에 근접, 비용은 대폭 절감

벤치마크ReTrace에이전트 / 비교시간비용
Internal (79개) 93.8% 완료 96.8% (에이전트) — -24% 작업당
τ²-bench 75.8% 성공 80.6% (에이전트) 1.3s vs 170s —
SOP-Bench (8개) 80.6% 83.6% (few-shot) — —

프로덕션과 τ²-bench에서 에이전트 대비 각각 3점, 5점 이내 성능을 유지하면서 지연과 비용을 크게 절감

수리(Repair): 학습 실패 피드백으로 워크플로우 개선

훈련 입력에서 발생한 실패를 피드백으로 사용해 워크플로우를 최대 3회 수리합니다.

벤치마크수리 전수리 후 (3 rounds)에이전트시간
τ²-bench (k=2) 66.7% 81.2% 80.6% (n.s.) 1.3s
SOP-Bench 80.6% 87.8% 85.5% 0.40s vs 46.6s
  • τ²-bench: 수리 후 에이전트와 통계적으로 동등 — 플래너 없이 에이전트 수준 달성
  • SOP-Bench: few-shot 생성(83.6%)을 뒤처지던 ReTrace가 수리 후 에이전트(85.5%)를 능가

분석: 에이전트의 추론은 무엇을 더해주는가?

추론 포함 vs 제거

추론을 제거한 트레이스로 구축하면 Internal -8.8pt, τ²-bench -6.2pt 하락 — 조건과 입력 출처 복원이 붕괴

예외: SOP-Bench

SOP-Bench에서는 추론 제거가 +1.7pt — SOP 라벨과 모순되는 추론이 오히려 방해하는 경우 존재

트레이스 수를 늘리는 것에도 한계가 있음 — 전체 트레이스는 어느 정도까지만 도움되고, 추론을 제거하면 입력은 짧아지지만 작은 k에서 성능이 크게 하락

에이전트 대비 절감

손익분기: 구축 비용은 약 75회 실행 후 회수 — 실제로 상위 워크플로우들은 3개월간 297k~528k 회 실행됨

실무자를 위한 교훈

  • 실행 빈도가 판단 기준 — 자주 실행되는 절차일수록 워크플로우 컴파일의 경제성이 커짐 (약 75회 실행이 손익분기)
  • 추론이 포함된 트레이스를 확보 — 도구 호출만으로는 조건과 입력 출처를 복원할 수 없음
  • 트레이스 수는 소량이면 충분 — 대략 8개 내외의 트레이스로 병합하고, 너무 많은 긴 트레이스는 오히려 해로움
  • 수리 루프를 도입 — 훈련 실패 피드백 3회 수리만으로 큰 폭의 성공률 향상 (66.7% → 81.2%)
  • 플랫폼 독립성 활용 — 규칙 문서는 재사용 가능, 대상 플랫폼별로 마지막 합성 단계만 교체

결론

  • ReTrace는 SOP와 소수의 에이전트 트레이스에서 플래너 없는 실행 가능한 워크플로우를 구축
  • 에이전트의 추론을 활용해 도구 호출만으로 알 수 없는 행동 조건과 입력 출처를 복원
  • 프로덕션 79개 절차에서 93.8% 완료(비용 -24%), τ²-bench에서 75.8%→81.2%(수리 후), 실행 시간 170s → 1.3s
  • LLM 호출은 1회성 구축에만 — 런타임에는 코드가 다음 단계를 선택해 지연과 비용 문제 해결
